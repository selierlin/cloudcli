# 基线测试：一句业务提问，八家 harness 各答了什么

**时间**：2026-10-31 08:40–09:50
**问题**（原样，未加任何提示）：`昨天猫一会的订单量有多少`
**样本**：8 家 × 3 轮 = 24 次真实调用，全部走 `volcano-ark/glm-5.3-flash`
**基线条件**：全局指令文件 `~/dotfiles/agents/.agents/AGENTS.md` 临时置空（claude / codex / zcode / workbuddy / `~/.agents` 五条软链共用同一实体文件），跑完立刻还原并用 SHA-256 校验一致（`ad7d0f3e…`，4717 字节）。工作目录 `/tmp/harness-bench/<provider>/S0` 不含项目级 AGENTS.md。

## 一、真值：这道题本身有三个答案

用 dbhub 独立核对（`lmb_data`，2026-10-30，`platform = 100`）：

| 口径 | 数值 | 说明 |
| --- | --- | --- |
| 创建订单 | **1,430 单 / 488 用户** | `dwd_trade_order_base`，含待支付 |
| 其中待支付（state=1） | 262 | 只存在于 base 表 |
| 支付成功（state=2/3） | **579 单**，¥9,546.98 | `dwd_trade_order_success` 一致 |
| 已关闭（state=8） | 10 | 超时未支付 |
| 已结束订单（579+10） | 589 | `view_orders` / `wide` / `lmb_orders` 只有这个数 |

OpenViking 沉淀口径（`platform-dict.md`、`20261027-03-猫一会用户手机号导出口径`）明确：**猫一会 = `platform >= 100`**，且「按门店维度统计猫一会订单与 platform 口径不等价」。所以 `1430` 是完整答案，`589` 是漏掉待支付的答案，`按场地名统计` 是错口径。

## 三、五个结论

### 1. 八家给出五种答案，最大值是最小值的 1,430 倍

- **1,430 单**：claude 两轮、opencode 一轮
- **589 单**：zcode ×3、dsh ×3、pi ×2、opencode ×2、omp ×1
- **30 单**（场地名含"猫一会"）：claude 一轮
- **1 单**（场地：猫一会车载按摩垫首发）：workbuddy ×3
- **0 单**（测试库 `test_lmb_toc`）：pi 一轮
- **查不到**：codex ×3（MCP 被拒）、omp ×2

这不是"模型能力"差异。589 和 1430 的差别来自**查了哪张表**：`view_orders` / `wide` / `lmb_orders` 只有已结束订单，`dwd_trade_order_base` 才含 262 张待支付。三家的"错口径"则是把"猫一会"当成场地名，而 OpenViking 里明确写着它是渠道（`platform = 100`）。

### 2. 唯一稳定答对的路子是先查口径，再查库

- pi 第 1 轮查 `test_lmb_toc`，答 0 单；第 2、3 轮引用 OpenViking「猫一会 = platform ≥ 100」后，答 579/589。
- claude 第 1 轮走场地名（30 单）；第 2 轮开始查 `dwd_trade_order_base` 并主动说"已把猫一会 = platform 100 存入记忆"，答 1,432 / 1,430。
- zcode 三轮都查到了 `dwd_trade_order_wide`，但那张表没有待支付单，所以三轮稳定停在 589。

**口径沉淀的存在与否，比换 harness 的影响大得多**：同一家 harness，读了沉淀口径后答案从 0 单变成 579 单。

### 3. 数据接入能力是硬门槛，不是软差异

- codex 三轮共 86 次工具调用，全部被 `prod_lmb_data` 拒绝，最后只能反问"猫一会是哪个维度"。它有查询意图和正确 SQL 方向，但没有权限。
- omp 前两轮连 dbhub 都没连上（只能在空目录里找文件），第 3 轮才接通并答出 589。
- dsh 三轮都答得出来，但工具调用数和 token 全程报 0（采集缺口，不是没干活）。

同一个 harness 在两次调用之间 MCP 可用性都会变，这一点在 `S0` 这种一次性目录里比固定场景更明显。

### 4. "快"要分成两类看

- **omp 12.7 秒**是没查库，直接说"工作目录里什么都没有"。快，但没有产出。
- **真正查了库的六家**（claude / opencode / zcode / pi / workbuddy / dsh）中位落在 **94–117 秒**，彼此差距不到 25%。
- codex 82 秒全花在被拒绝的重试上（22 次工具调用）。

所以在这类需要取数的问题上，**harness 之间的速度差（±20%）远小于"查不查得动库"这个 0/1 差异**。

### 5. 成本差 25 倍，但贵的那次答得最全

- opencode：195,995 prompt tokens（一轮 10 次工具，把 1430/488/262/579 全给出来）
- codex：125,662（3 轮全失败）
- zcode 50k、workbuddy 37k、pi 29k、claude 28k、omp 7.8k
- dsh：不上报

opencode 的高开销来自它每轮重发全量上下文（与三轮横评里 S21 零缓存的结论一致）。在一次性提问里这个成本被放大得更明显：它一次调用就烧掉 claude 七倍的 prompt。

---

## 五、这轮测试的局限

1. **MCP 配置不齐**：八家接到的数据源不同（codex 无权限、omp 前两轮未接通、pi 首轮连到测试库），所以这不是纯粹的"模型能力"对比，而是"实际可用配置"的对比。对选型的意义反而更直接。
2. **`S0` 目录有残留**：`/tmp/harness-bench/<p>/S0` 留着上一次演示的 `calc.js` / `test.js`，omp 前两轮据此判断"工作目录没有数据"。对答案影响有限，但在意干净的话下次应先清空。
3. **3 轮样本**：足以看出"稳不稳定"，不足以估准确率。
4. **dsh 无采集**：工具数、token、首字全为 0，无法与别家比成本。

---

## 六、给日常使用的三条

1. **先确认口径，再问 harness**。这道题如果先把"猫一会 = platform 100，订单量默认含待支付"写进 OpenViking 或项目 AGENTS.md，六家的答案会立刻收敛到同一个数。
2. **需要取数时，先确认那家能不能连上库**。codex 在这一轮 0 产出，不是它不会写 SQL，而是它的查询通道被拒。
3. **要一次问准，用 claude 或 opencode**（这轮唯一触及 1430 的两家）；**要稳定复现同一个口径，zcode / dsh 三轮没变过**（但需要你先把口径定成 589 还是 1430）。
