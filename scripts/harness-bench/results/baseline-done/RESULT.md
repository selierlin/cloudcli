# 第二轮基线提问：生产环境 + 已完成

**问题**（原样）：`昨天生产环境猫一会的已完成订单量有多少`
**时间**：2026-10-31 10:24–11:30 ｜ **样本**：8 家 × 3 轮 = 24 次 ｜ 通道：`volcano-ark/glm-5.3-flash`
**基线条件**：同上一轮，全局 `AGENTS.md` 置空，跑完还原并校验 SHA-256（`ad7d0f3e…`）。

**真值**：`platform = 100` + `state = 3`（`OrderStateEnum.FINISHED`）+ `create_time` 落在 2026-10-30 → **579 单**，实付 ¥5,699.60。已用 dbhub 独立核对，与 `dwd_trade_order_success` 一致。

失败明细：

- `omp#3`：超时 300 秒。
- `opencode#1`：超时 300 秒（`frames=partial`）。
- `opencode#3`：246 毫秒返回，`terminal.kind = error`、`Unexpected error`，正文为空。
- `codex`：3 轮共 78 次工具调用，每次都卡在 `prod_lmb_data` 被拒；第 3 轮耗了 243 秒，最后只能列出场名反问。
- `workbuddy`：三轮都按订单描述匹配「猫一会 + 次卡」，得 190（自有网点另算 207）。名字里带「猫一会」的订单描述成了它的唯一入口。

## 五、结论

1. **问清楚，八家能收敛到同一个数。** 上一轮的五种答案里，至少三种是问题歧义造出来的，不是模型算错。
2. **剩下的偏差全是「入口」问题**：omp 从埋点日志进、workbuddy 从订单描述进、codex 没有入口。数据库名写对、表选对，这三家都能给 579。
3. **日常取数建议用 claude / zcode / dsh / pi**；这轮四家 3/3，口径稳定，速度接近。claude 综合最优（64s、20k tokens）。
4. **opencode 只适合「一次问对、跑得动」的场景**：它答对那次 44 秒、口径最完整，但两次 harness 级失败（超时、空回复）让它不适合无人值守。
5. **codex 在这一轮仍不可用于取数**：三轮全被 MCP 拒绝，方向对、SQL 对、就是拿不到数。
