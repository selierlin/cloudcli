# 基线提问第三轮：注册用户数（2026-10-31）

> 问题：**「截止今天 12 点正式环境猫一会的注册用户有多少」**
> 环境：置空全局 `AGENTS.md`（所有 harness 共用的软链接源），八家 × 3 轮 = 24 次，跑完 SHA-256 校验还原（`ad7d0f3e…`）。
> 复现：`./run.sh`（trap 保证中途失败也会还原）。运行时间 2026-10-31 13:00–14:05。

## 一、这道题有四个真值，不是一个

先用 dbhub 核对（`lmb_data.ods_lmb_account`，与 MySQL 源表 `lmb_toc.lmb_account` 双向一致）：

| 口径 | ≤ 今天 12:00 | 说明 |
| --- | --- | --- |
| **在册账号**（`platform>=100`、`is_deleted=0`、按 `create_time`） | **43,275** | 字典口径：注册时间 = `create_time`；进小程序即建号 |
| 累计账号（含已注销 53 个） | 43,328 | 漏滤 `is_deleted` 就得这个数 |
| **完成注册**（`register_time` 非空，即绑了手机） | **33,563** | 有效 33,515 / 注销 48；差 9,712 = 微信静默授权未绑号 |
| 完成注册（查询时点，≈13:10） | 33,579~33,580 | 未卡 12 点截止的变体 |

「注册用户」在业务上**两个读法都成立**：产品口径（member_type=2 注册会员）支持 33.5k，数据字典口径（注册时间看 `create_time`）支持 43k。所以判分按「落在哪个口径 + 数字对不对 + 有没有把口径讲清楚」三档评，不按单一数字评。

## 四、三条结论

1. **本题最大的坑不是库，是「注册」二字。** 43k（进小程序建号）和 33.5k（绑手机完成注册）都是合理答案，差 9,712 个静默授权账号。dsh 是唯一三轮都主动把两层拆开、且数字全部对上的；pi/zcode 按字典口径答 43,275 并注明 `register_time` 陷阱，也算满分答法。**给业务报数前先问清楚要哪个口径——这道题里口径歧义的贡献比任何 harness 差异都大。**

2. **OV 手机号导出沉淀是「含注销 43,328」这派答案的共同源头。** 它的基线数（42,270）本就未滤 `is_deleted`（导手机号场景不需要），六条 43,328 全部引用了它。字典里「`is_deleted` 要自己过滤」那条，只有直接读字典或查 `view_account`/MySQL 源表的家（claude_r1、pi_r3、opencode_r1、zcode_r1/r3）执行到位。**沉淀文档会传播口径，也会传播口径的省略。**

3. **稳定性问题集中在三家**：omp 两轮凭空拒答（上一轮刚证明能查库）；workbuddy 连续第三轮掉进「按订单描述/场地找用户」的坑（375，真实值差 115 倍）外加一次超时；codex 前两轮 46 次工具调用全被 MCP 拒——但 r3 拿到数了，说明拒绝不是恒定的，无人值守场景不可依赖。
