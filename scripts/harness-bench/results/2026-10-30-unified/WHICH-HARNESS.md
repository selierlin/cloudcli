# 该用哪个 harness —— 选型决策报告

数据：`2026-10-30-unified`，21 个场景 × 8 家 × 2~5 轮 = 568 次真实调用，统一建模 `glm-5.3-flash`
（claude / codex 走火山方舟，其余六家走 copilot.tencent.com）。原始报表见 `REPORT.md`。

## 一句话结论

**日常默认 `pi`；重代码活要更快用 `opencode`、要更稳用 `claude`；`workbuddy` 和 `zcode` 不建议作默认。**

pi 是唯一同时满足「71/71 全过 + 每组耗时都在前二 + 每次调用只花 3502 input tokens」的一家。
唯一需要注意的是它对复杂题目会先长时间思考（S21 思考占比 96%，第一轮憋 26 秒才出正文），
但总时长仍然是第二快，不是拖累。

## 二、按场景的推荐

| 你的任务 | 首选 | 备选 | 别用 | 依据 |
| --- | --- | --- | --- | --- |

## 三、决策树

```
任务来了
├─ 需要数学/逻辑上不能错？
│   └─ 是 → claude（质量兜底）> pi > dsh ；不要 codex
├─ 要动代码，且涉及多个文件？
│   └─ 是 → opencode（最快，16 秒级）
│            └─ 如果一次没改对、要反复试 → pi（方差最小，cv7%）
├─ 一条会话要跑十几分钟、连续改？
│   └─ 是 → opencode 或 pi；超过 2 轮的活别交给 workbuddy/omp（尾部 4 分钟+）
├─ 只是问答 / 读文档？
│   └─ pi（默认）或 dsh（更快，但 S21 有过一次算错）
└─ 大批量、成本第一？
    └─ pi（3502 tokens/次）；远离 zcode、workbuddy（2 万+）
```

## 四、逐家画像

**pi** —— 默认选项。71/71 全过，六个任务组里四组在前二，system prompt 只有 3502 tokens。
代码类任务表现稳定（跨文件重命名 cv7%），唯一短板是 S16「定位修复」方差大（cv54%，最慢 55 秒），
说明它遇到需要来回试错的题目时会想很久。不影响「大多数情况最快」这个结论。

**opencode** —— 重活第一选择。多轮重构 111 秒、跨文件 16.4 秒，都是全场最快，尾部也最小（单轮最差 57 秒）。
质量 70/71，唯一失手是复杂推理里的一条。它的弱点在轻量场景没有优势（4.0 秒 vs pi 3.2 秒），
prompt 是 pi 的 3.2 倍。

**claude** —— 质量与稳定性兜底。71/71，工具类场景全部一次过，S16/S17 的方差只有 4%/14%（别人 30~58%）。
代价是最慢的一档：多轮长任务 98.9 秒、单轮最差 248 秒。适合「不能出错、可以等」的活。

**dsh** —— 最轻快的一家。轻量问答 2.9 秒、长上下文 3.5 秒都是第一，S21 四轮 196 秒也在中上。
但它在 S21 第 4 轮出过一次真错（促销免掉了非最便宜件），复杂任务上不如 opencode/pi 可靠。
另外它不上报 token 用量，成本无法核算。

**omp** —— 质量全过（71/71），但速度全面偏慢（轻量 6.0 秒、S21 244 秒），尾部 253 秒。
没有明显优势场景，作为备选而非默认。

**workbuddy** —— 质量 71/71，但两项都垫底：每次调用 26724 tokens（pi 的 7.6 倍），
多轮长任务 115.8 秒、单轮最差 291 秒。除非有非技术原因（比如就是要用 WorkBuddy 自己的上游账号），
否则不建议作为默认。

**zcode** —— 中等速度、方差最大（跨文件重命名 cv58%、定位修复 cv45%），prompt 21743。
它还长期带着一个已修的产品缺陷（无头模式下权限模式映射错误，导致工具调用被系统性拒绝），
修复前 69 条里 13 条直接跑崩。现在能用了，但仍是「能用但不是首选」。

**codex** —— 除复杂推理外都稳（其余 20 个场景 66/66），但复杂推理只有 3/5，
而且 5 次里有 2 次给出的是 11/7、45/7 这类错误答案。若工作里有数学推导，别用它。

## 五、成本视角

每次调用的固定开销（system prompt + 工具定义），S3 只发一个 `hi` 时测得：

| harness | input tokens | 相对 pi |
| --- | --- | --- |
| pi | 3502 | 1.0× |
| omp | 8308 | 2.4× |
| codex | 9240 | 2.6× |
| opencode | 11199 | 3.2× |
| claude | 13777 | 3.9× |
| zcode | 21743 | 6.2× |
| workbuddy | 26724 | 7.6× |
| dsh | 不上报 | — |

这项工作里绝大多数是「短问题 + 长上下文」的形态，system prompt 会随每一轮重复计费。
按 10 万次调用估算，选 pi 和选 workbuddy 的 input token 差 23 亿量级。
claude 会命中缓存（S3 报告 cacheRead 8832），实际计费低于表面数字，但仍高于 pi。

## 六、五个反直觉的结论

1. **「pi 想太多所以真实工作慢」不成立**。它的思考占比确实最高（S21 96%、第一轮憋 26 秒），
   但四轮合计 124 秒，只输给 opencode 的 111 秒，比其他六家快 1.6~2 倍。
2. **最快的不一定最贵**。opencode 比 pi 慢一点点，但 prompt 是 pi 的 3.2 倍；
   workbuddy 最慢且最贵，两项都垫底，没有互补关系。
3. **格式服从不是能力差异，是环境差异**。八家在同一批格式场景上，只要工作区里有一条
   「每次回复都叫我 X」的个人指令，就会有 2~5 条从通过变失败，八家无一例外。
   排除了这条指令后，26/26 全过。
4. **复杂推理是唯一能把八家分开的能力维度**，其余 20 个场景八家几乎全过。
   差值集中在 S2：codex 3/5，opencode / zcode 4/5，其余 5/5。
5. **难度的分水岭在「第 4 轮」**。同一个重构任务，前三轮八家都在 16~75 秒，
   到第 4 轮（促销叠加折扣）除 opencode 外全部翻倍到三倍——叠加规则才是真正的压力点。

## 七、这份报告不能替你回答什么

以下维度**没有测**，如果你的用法落在这些里面，上面的推荐要打折：

- **会话恢复 / 续跑**（关掉重开、fork 分支）：八家实现完全不同，这是长会话最容易出问题的地方，
  而 bench 每轮都新起进程，完全没压到。
- **权限与安全边界**：只有 zcode 被手工验证过 `guarded` 能拦 `rm -rf`；八家对危险命令的处理差异没进矩阵。
- **并行工具调用**、**MCP 外部工具**、**图片输入**、**大输出（上千行）**、**中途取消**、
  **几千文件的大仓检索**、**上下文接近上限时的压缩**。
- **多会话并发**：同时开几个会话时是否互相拖慢，没测。
- **换模型**：全部结论基于 `glm-5.3-flash`。prompt 开销是 harness 结构决定的，换模型基本不变；
  但速度排序、甚至质量排序都可能变。

方法上的限制：每档 2~5 轮，样本很小。几百毫秒的差距都在噪声里；本报告只依据
「成倍差异」和「过/不过」下判断，不依据 10~20% 的差距。
