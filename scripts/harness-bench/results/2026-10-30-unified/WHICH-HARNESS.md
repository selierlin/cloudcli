# 该用哪个 harness —— 选型决策报告

> **最终版见 `../FINAL-REPORT.md`**（三轮 1168 次调用合并的完整测评）。本文保留为第一轮的详细报表与逐家画像，
> 速度结论已被后两轮改写，阅读时以 FINAL-REPORT.md 为准。

数据：三稿合计 1168 次真实调用，统一建模 `glm-5.3-flash`。
第一稿 `2026-10-30-unified`（21 个场景 × 8 家 × 2~5 轮 = 568 次，claude/codex 走火山方舟、其余六家走 copilot）；
第二稿 `../2026-10-30-valid`（288 次，七家统一到火山方舟）；第三稿 `../2026-10-30-stable`（312 次，
ark 加厚样本 + 四家 copilot 配对镜像）。原始报表见 `REPORT.md`、`VALIDATION.md`、`STABLE.md`。

## 一句话结论

**日常默认 `pi`；要跑很久的会话在 ark 上加 `omp`、在任何上游上加 `claude`；`workbuddy` 和 `zcode` 不建议作默认。**

> **本文是三稿中的第一稿，速度部分已被后两轮改写。**
> 第二稿 `../2026-10-30-valid/VALIDATION.md`（288 次，七家统一到火山方舟）、
> 第三稿 `../2026-10-30-stable/STABLE.md`（312 次，ark 加厚样本 + 四家 copilot 配对镜像）。
> 质量的结论三稿一致；**速度的结论只有「同一套上游内部」才成立，跨上游不可比。**
>
> 第三稿把机制摁实了：换上游改变的不是网速，而是**工具调用轮数**。同一个 opencode 做 S17，
> copilot 上 3 次工具调用 19 秒，ark 上 17 次工具调用 69 秒；zcode 3 → 15 次、32 → 116 秒；
> 而 omp 反向（8 → 10 次，ark 更快）。同一个模型 id、不同的部署，工具使用习惯不同。
>
> 第三稿的最终排序（ark、五场景名次合计，满分 40）：**pi 9 · omp 10 · opencode 18 · claude 20 ·
> codex 22 · workbuddy 31 · dsh 33 · zcode 37**。下游所有耗时请按这个前提读。

pi 是唯一同时满足「三稿质量接近全过 + 每组耗时都在前列 + 每次调用只花 3502 input tokens」的一家。
唯一需要注意的是它对复杂题目会先长时间思考（S21 思考占比 96%），但总时长仍然靠前，不是拖累。

opencode 的「全场最快」是本文最强的一条结论，也是唯一被后两轮完全推翻的一条 —— 它依赖 copilot 那条
上游让它在 3 次工具调用内收工。换到 ark，S21 从 111 秒变成 204~365 秒，prompt token 是 pi 的 30 倍
（不走缓存，每轮重发全量上下文）。**它的成绩属于上游，不属于 harness。**

## 二、按场景的推荐

| 你的任务 | 首选 | 备选 | 别用 | 依据 |
| --- | --- | --- | --- | --- |
| 问一句答一句、查概念 | **pi / dsh** | opencode | workbuddy | 3 秒 vs 9.3 秒，差 3 倍 |
| 数学、逻辑、需要精确推导 | **claude / pi / dsh** | omp | **codex** | codex 5 题只对 3 题，其余几家 5/5 |
| 读大文件、日志、长文档 | **dsh / pi** | opencode | workbuddy | 3.5/4.0 秒 vs 10.4 秒，且 32k 不掉速 |
| 改一处代码、改配置 | **opencode / pi** | claude | workbuddy | 10.3/10.9 秒 vs 25.4 秒 |
| 跨文件重命名、批量重构 | **pi**（ark）/ **opencode**（copilot） | claude | workbuddy | ark 上 codex 31s、pi 41s、omp 43s；copilot 上 opencode 19s、zcode 32s |
| 多人多轮的连续任务（一条会话干到底） | **omp / pi**（ark）/ **pi**（copilot） | claude | zcode / dsh | ark 上 omp 104s、pi 133s；后四家 204~359s，中间空 50 秒 |
| 严格格式输出（JSON、字数、Markdown） | 任一家 | — | — | 八家 26/26 全过，唯一变量是工作区里的个人指令 |
| 成本敏感的批量调用 | **pi** | omp | **opencode / codex / workbuddy / zcode** | S21 四轮 prompt 11k vs 346k，30 倍；后两家不走缓存 |

## 三、决策树

```
任务来了
├─ 需要数学/逻辑上不能错？
│   └─ 是 → claude（质量兜底）> pi ；不要 codex（S2 三轮 21/25，错法一致）
├─ 要动代码，且涉及多个文件？
│   └─ 是 → 先问上游：ark → pi / codex；copilot → opencode / zcode
│            └─ 要反复试错、不能每次都重建路径 → pi（轮数最省）
├─ 一条会话要跑十几分钟、连续改？
│   └─ 是 → ark：omp / pi；copilot：pi（opencode 101s vs pi 99s，但贵 43 倍）
├─ 只是问答 / 读文档？
│   └─ pi（默认）；dsh 更快但不上报 token、且 S21 垫底一档
└─ 大批量、成本第一？
    └─ pi（11k prompt/轮）或 omp（12k）；远离 opencode（346k）、codex（265k）
```

## 四、逐家画像

**pi** —— 默认选项。三稿合计质量最高之一，五场景名次合计 9（全场第一），system prompt 只有 3502 tokens，
S21 四轮 133 秒且 99% 命中缓存。代码类任务表现稳定（跨文件重命名 cv7%），唯一短板是 S16「定位修复」
方差大（cv54%，最慢 55 秒）—— 它遇到需要来回试错的题目时会想很久。这不影响它作为默认。

**opencode** —— **成绩属于上游，不属于 harness。** copilot 上多轮 111 秒、跨文件 16.4 秒全场最快；
换到 ark 变成 204~365 秒和 69 秒，因为工具调用从 3 次涨到 11~17 次。prompt 是 pi 的 30 倍且完全不走缓存。
质量 70~71/71 没问题。结论：只有在 copilot 那条上游上才值得为了速度选它。

**claude** —— 质量与稳定性兜底。前两稿 71/71，第三稿唯一一次失手在 S21 促销规则上。
工具类场景方差极小（S16/S17 的 cv 只有 4%/14%，别人 30~58%）。代价是慢一档、贵 1.7 倍。
适合「不能出错、可以等」的活。

**dsh** —— 轻活快、重活慢。轻量问答 2.9 秒曾经第一，但 ark 上 S17 93 秒、S21 283 秒都在后两名。
它在 S21 第 4 轮出过真错（促销免掉了非最便宜件）。另外它**不上报 token、文本量和工具调用数**，
成本与效率无法与其他七家并列比较。

**omp** —— 第三稿的最大意外。第一稿里它是「没有优势场景的慢家」（S21 244 秒），换到 ark 后
S21 104 秒全场最快、五场景名次合计 10 排第二。质量三稿全过。说明它的工具使用习惯跟 ark 更合。
没有明显优势场景，作为备选而非默认。

**workbuddy** —— 质量 71/71，但两项都垫底：每次调用 26724 tokens（pi 的 7.6 倍），
多轮长任务 115.8 秒、单轮最差 291 秒。除非有非技术原因（比如就是要用 WorkBuddy 自己的上游账号），
否则不建议作为默认。

**zcode** —— 中等速度、方差最大（跨文件重命名 cv58%、定位修复 cv45%），prompt 21743。
它还长期带着一个已修的产品缺陷（无头模式下权限模式映射错误，导致工具调用被系统性拒绝），
修复前 69 条里 13 条直接跑崩。现在能用了，但仍是「能用但不是首选」。

**codex** —— 除复杂推理外都稳（其余 20 个场景 66/66），但复杂推理只有 3/5，
而且 5 次里有 2 次给出的是 11/7、45/7 这类错误答案。若工作里有数学推导，别用它。

## 五、成本视角

每次调用的固定开销（system prompt + 工具定义），S3 只发一个 `hi` 时测得：

| harness | input tokens | 相对 pi |
| --- | --- | --- |
| pi | 3502 | 1.0× |
| omp | 8308 | 2.4× |
| codex | 9240 | 2.6× |
| opencode | 11199 | 3.2× |
| claude | 13777 | 3.9× |
| zcode | 21743 | 6.2× |
| workbuddy | 26724 | 7.6× |
| dsh | 不上报 | — |

这项工作里绝大多数是「短问题 + 长上下文」的形态，system prompt 会随每一轮重复计费。
按 10 万次调用估算，选 pi 和选 workbuddy 的 input token 差 23 亿量级。
claude 会命中缓存（S3 报告 cacheRead 8832），实际计费低于表面数字，但仍高于 pi。

**多轮会话把差距放大到 30 倍。** 第三稿实测 S21 四轮合计 prompt token（input + cacheRead，中位）：

| harness | S21 prompt tokens | 缓存命中 | 相对 pi |
| --- | --- | --- | --- |
| pi | **11,405** | 99% | 1× |
| omp | 12,423 | 97% | 1.1× |
| claude | 19,506 | 99% | 1.7× |
| workbuddy | 33,182 | 100% | 2.9× |
| zcode | 39,678 | 100% | 3.5× |
| codex | 265,355 | **0%** | 23× |
| opencode | **346,539** | **0%** | **30×** |
| dsh | 不上报 | — | — |

opencode 和 codex 完全不带缓存标记，每一轮都重发全量上下文。第一稿里 opencode 在 copilot 上
还能跑到 111 秒，是那条上游的 prefill 足够快把这个成本吃掉了 —— 单看耗时看不见这件事。

## 六、六个反直觉的结论

1. **「pi 想太多所以真实工作慢」不成立**。它的思考占比确实最高（S21 98%），
   但四轮合计 124~133 秒，始终在前二，比其他六家快 1~2 倍。
2. **最快的不一定最贵，最贵的是看起来最快的。** opencode 在 copilot 上最快，但 prompt 是 pi 的 30 倍
   且零缓存；workbuddy 反而只贵 5.8 倍。
3. **格式服从不是能力差异，是环境差异**。八家在同一批格式场景上，只要工作区里有一条
   「每次回复都叫我 X」的个人指令，就会有 2~5 条从通过变失败，八家无一例外。
   排除了这条指令后，26/26 全过。
4. **复杂推理是唯一能把八家分开的能力维度**，其余 20 个场景八家几乎全过。
   三轮合并后只有 codex 稳定出错（S2 三轮 21/25、S21 5/7，错法一致）。
5. **难度的分水岭在「第 4 轮」**。同一个重构任务，前三轮八家都在 16~75 秒，
   到第 4 轮（促销叠加折扣）全部翻倍到三倍——叠加规则才是真正的压力点，也是唯一持续出错的地方。
6. **「换上游」比「换 harness」影响更大，而且机制不是网速。** 同一家 harness、同一个模型 id，
   工具调用轮数会随上游部署从 3 次变成 17 次，耗时差 3.6 倍。排 harness 名次前必须先固定上游。

## 七、这份报告不能替你回答什么

以下维度**没有测**，如果你的用法落在这些里面，上面的推荐要打折：

- **会话恢复 / 续跑**（关掉重开、fork 分支）：八家实现完全不同，这是长会话最容易出问题的地方，
  而 bench 每轮都新起进程，完全没压到。
- **权限与安全边界**：只有 zcode 被手工验证过 `guarded` 能拦 `rm -rf`；八家对危险命令的处理差异没进矩阵。
- **并行工具调用**、**MCP 外部工具**、**图片输入**、**大输出（上千行）**、**中途取消**、
  **几千文件的大仓检索**、**上下文接近上限时的压缩**。
- **多会话并发**：同时开几个会话时是否互相拖慢，没测。
- **换模型**：全部结论基于 `glm-5.3-flash`。prompt 开销是 harness 结构决定的，换模型基本不变；
  但速度排序、甚至质量排序都可能变。

方法上的限制：第一稿每档 2~5 轮，第三稿加厚到 S2 10 轮 / S3 8 轮 / S7、S17 各 6 轮 / S21 3 轮。
几百毫秒的差距都在噪声里；本报告只依据「成倍差异」和「过/不过」下判断，不依据 10~20% 的差距。
另有三处采集缺口：dsh 不上报 token / 文本量 / 工具调用数（全是 0，只有耗时和质量可用），
opencode 全程 thinkingChars = 0（同样是不上报，不能读成「它不思考」）。
