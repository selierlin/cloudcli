# 评估与沉淀线（triage-sediment）

目标：逐条过**精读区**的会话——读一段（**1~5 轮**）→ 判一段 → 落草稿 → 读到尾 → 出清单 → **停**。

**一条会话 = 一个停止点。** 不是「一批一停」，也不是「读完这条顺手读下一条」。翻页的权力在用户手里。

改造理由（2026-10-24）：旧流程「一批 6~10 条、一次读完、出一张表」有两个病：① 整批内容一次性灌进上下文，前面的结论污染后面的判断；② 为了凑批，会把同题会话按「重复」打包判删。逐条 + 逐段 + 读段即落盘，两个病一起治。

## 准备（只做一次）

1. **列候选**。`inventory.py --archived-only`（或按用户给的范围），拿体积、轮数、首问。
2. **`s:` 预筛**：`sediment_refs.py`（`--archived-only` 可选）。结果**只用来给 ③ 提供线索**，不作准入，也不作删除许可（见 `cleanup.md` §已沉淀）。
3. **排顺序并逐条打勾**，排完把总数记下来：
   - 同项目 / 同 provider 排在一起（只是读的便利，**不是合并判定的理由**）；
   - fork 家族**父先子后**（子会话的前缀可直接复用父的段落记录）；
   - **按清单逐条打勾，不按 provider 手感挑**——踩过：opencode 那条归档会话连着 8 轮治理没被带出来，因为每轮都在 workbuddy 里挑。每读完一条核一次「已处理 + 剩余 = 总数」，差额就是漏掉的。

## 逐条循环

4. **起一条**：建草稿（§草稿），取 `project_path`、`updated_at`、真实轮数；fork 子会话先算分叉点（§fork）。
5. **段循环**：按 §分段读法 读 1~5 轮 → 走三问（§价值判定）→ 写草稿 → 更新 `read:` 行 → 回第 5 步。
6. **读到尾 → 出清单 → 停**（§单条清单）。
7. 用户回话后 → 落地本条的沉淀与删除 → 取下一会话，回第 4 步。

**不预读、不代替拍板、边界不自己选。** 用户说「继续」= 读下一条会话。**「按你推荐的」只授权当前这条**——下一条照样要贴清单、照样要等回话。

## 单条清单（读到尾就给这三块，然后停）

```
第 7 条 · 66dc5b0b · 已读完 28/28 · 草稿 drafts/66dc5b0b.md

沉淀建议：
  bank:knowledge  「核销口径：已完成但无核销记录的三种成因」
  db:04-recharge-refund  核销状态字段的判定链路（+3 行）

冲突项（需你拍）：
  与会话 14:10 那条口径相反：本会话判「按支付时间」，那条判「按核销时间」

删除建议：①②③ 全成立 → 可删
  将删：DB 行 1 · transcript 1（7.4M）· superseded 0 · WorkBuddy 目录 1（1.3M）
```

- **沉淀建议**写 `kind` + 落点 + 一句话标题；落点必须写全（`bank:case` 与 `db:<域文件>` 同时有时两条都写，只写 bank 会让 db 那半在删除时静默丢失）。
- **冲突项**：本会话口径与 OV/bank 现有口径相反的，单列。**不许静默覆盖**，也不许后写的自动压过先写的。
- **删除建议**：仅当 ①②③ 全成立；附明细（DB 行 / transcript / superseded / 共享库行 / 残留目录）。这份清单即干跑输出，用户点头直接执行，不再二次干跑。
- 体积估算**把同名目录一起算进去**（workbuddy 的 `<psid>/` 里有子代理与 tool-results）：只算 `.jsonl` 会低估，实测一条估 30.9M、实删 41.7M。执行时以 `purge.py` 干跑输出的「文件 N，目录 N，约释放 X MB」为准，差得多就说明「是有目录」。


## 分段读法（段 = 1~5 轮）

精读区**没有「短会话一次读完」的例外**，统一按段走：

```bash
python3 scripts/extract.py <path> --max 200 --start 1 --limit 5
python3 scripts/extract.py <path> --max 200 --start 6 --limit 5
```

**怎么定切点**

- 默认 5 轮；话题中途断了（换主题、换文件、换故障）就在断点切。
- 只看 1 轮就够定性时只读 1 轮，**不用凑满 5 轮**。
- `--max 200` 只压单条答案长度；控制上下文靠段的**条数**，别靠把短会话截断。

**纪律**

- 每次只把一段放进上下文，**读完立刻写草稿、丢掉细节**。
- 段与段之间只带「一条结论 + 轮次区间」，不复述上一段内容。
- 上下文被压缩后：先读草稿 `read:` 行恢复进度，再续读；**草稿与记忆冲突时信草稿**。
- 每段回给用户一行（`第 x–y 轮 · 本段：… / 无`），让他能随时叫停。

## 草稿（抗压缩锚点）

路径 `~/.memory-bank/<project>/drafts/<sid前8位>.md`；项目按 `sessions.project_path` 反查（**别按 provider 猜**）。

```markdown
---
sid: <完整 session_id>
provider: workbuddy
project: <project_path>
started: <updated_at>
read: 1-15 / 40
---

## 第 1–5 轮
- 有价值：<一句话> — 原句「…」

## 第 6–10 轮
- 无
```

- **只用 `sid:` 前缀，禁写 `s:`**。`sediment_refs.py` 扫 `~/.memory-bank/**/*.md` 的 `s:` 引用，草稿带 `s:` 会被当成「已沉淀」，给未定稿的会话凭空发删除资格。
- **只写不可重建的部分**：不复述过程，不抄代码现状，不记「我当时怎么试的」。
- 正式条目落地后**删掉草稿**，别让它长期躺在 bank 里被当成沉淀。

## 已沉淀判定：`s:` 引用

- 判定来源＝`session-sediment` 写进 `~/.memory-bank/<project>/entries/*.md` 的 `s: <provider>:<id>` 行，**不是** cloudcli DB 字段。
- 正则：`s:\s*([A-Za-z]+):\s*`?([0-9a-fA-F][0-9a-fA-F\-]{3,})`。
- 同一引用可能匹配**多条**会话（如一条原始会话 + 它的一条 fork）——都算命中，分别处置。
- **大量 `s:` 引用指向早已删除的会话**（引用悬空、只剩沉淀），是正常态，不用追、不用清。
- 删已沉淀会话前确认「对应条目确已在 OV 里」——本地 `entries/` 有、OV 查不到 = **漏推**，此时删会话是真丢，必须先补推再删；反向（OV 有、本地无）不是断档，是别台机器的产出，不追、不补、也不写进报告。
- 一条会话可能「内容值得沉淀但从未沉淀」——`s:` 命中为空不等于无价值，两者别混。

## 同主题多会话：先对齐时间，再下结论

同一处代码常被反复问「这版改对了吗」，**后一次才是最终结论**（实测踩过：15:22 那条判「不对」，4 分钟后 15:27 那条判「对」——它们是同一行的两个版本）。

- 判价值前先比 `updated_at`；已删会话可从快照库查：`sqlite3 "file:<backup>?mode=ro&immutable=1"`。
- **以最晚那条为准**；写沉淀时把「前一版被判有问题 → 后一版确认」的时序写清，不要把过时判断沉进去。
- 两条都只是单点确认、结论又跟随代码时，可以都删——但删之前必须确认没有把最终结论一起删掉。

## fork 父子：读可以复用，判定必须独立

fork 出来的子会话**前半段是父 transcript 的原样复制**（实测父 61 轮 / 子 40 轮，前 39 轮 USER 文本逐字相同）。

```python
# 比对 USER 序列找分叉点（需先 import scripts/extract.py）
a = [u[:40] for u, _ in extract.parse_jsonl(parent, prov)]
b = [u[:40] for u, _ in extract.parse_jsonl(child, prov)]
n = 0
while n < min(len(a), len(b)) and a[n] == b[n]: n += 1
```

- **读复用**：子会话从第 n+1 轮起读，前 n 轮在子草稿里写一行「第 1–n 轮沿用父会话的段落记录（未新增）」。
- **判定不复用**（SKILL.md 铁律 7）：子会话的清单、删除建议、冲突项各自出，不能因为「前缀相同」直接抄父的结论。分叉点之后的内容是父会话没有的。
- 父子在同一轮治理里成对安排（父先子后），但**各有各的停止点**。
- 父删子留会留下悬空 `forked_from_session_id`（转录是独立副本，不会坏，但语义脏）；子删父留则关系断一半。**两边都想删时，确认后再一起执行**。
- 父已不存在（悬空 fork）时按独立会话读，别去找父。
- 非 fork 的「同题多条」（题目相同、无 `forked_from_session_id`）更要注意：**它们是不同会话，各自完整读**，不能按「像重复」并案。

## 项目归属：按 `project_path` 反查 bank 目录

写沉淀前先取 `sessions.project_path`，映射到 `~/.memory-bank/<project>/`；没有对应目录就新建（`entries/` + `_index.md`），并在 OV 侧先 `ov mkdir`。

- **别按 provider 猜项目**：同一条 workbuddy 会话可能属 cloudcli、ToC-Admin、rea、ai-center 中任一个，判据只有 `project_path`。
- 已有同主题条目时**更新而不是新建**（先 `grep` `entries/` 标题与正文，再 `ov find`）。


## 价值判定：三问（完整判据见 `SKILL.md` §2）

| # | 问题 | 谁答 | 作用 |
|---|---|---|---|
| ① | 结论能从代码/库/git 现状重建？ | 我，看代码 | 只能否决：「不能重建」→ 有价值；「能重建」**不批准删除** |
| ② | 有代码外信息吗？ | 我，读这段 | **有 → 直接判有价值**，不再问 ③ |
| ③ | OV 里已有、且比这段更全？ | 查了才知道 | **删的必要条件**；没查就没有删除资格 |

**判删 = ①②③ 同时成立。** 证据锚点（SKILL.md §2.2）：说有价值必须引原句 + 轮次；说无价值必须写 `读了第 x–y 轮` + `ov find … → 未检索到`。缺一样，处置留空。

### ② 命中：这些一律算有价值（先把「类型学」放一边）

- **被否掉的方案及理由** —— 代码只有赢家，看不出为什么没走另一条路。
- **踩坑路径** —— 什么姿势会静默失败（实例：批量下载 `027c747b` 的 B 方案漏了 `<style>`，线上静默无样式，是肉眼发现的；代码里永久无痕）。
- **一次性不可逆写操作的口径** —— 权限边界、回读校验（实例：gitlab 314 条批量改写的口令与 PAT 权限边界）。
- **权宜标记** —— 临时固定值 vs 正式值（实例：退款脚本里固定 phone 是权宜值）。
- **一次性 ops / 分析 / 脚本** —— ⚠️ **只看类型不够**。会写远端的（批量改 gitlab 描述、批量改配置、导入 OV）、或脚本里留了临时值的，那份口径在代码里查不到 ⇒ 先落 `bank:knowledge` 一句话再删。纯本地、结论用完即弃的（日志一次性分析、同比环比）才可能直接删。

### ①②③ 同时成立才可删

- **已被覆盖**：主题与 bank 条目 / OV 条目一一对应（如「输入框弹起」→ `20260916-01 移动端键盘避让`）。**判时要真找到条目并比对详略**，别凭印象；条目更浅 → 不算覆盖。
- **信息极薄**：重查一次只要一分钟 ⇒ 可删，但**在清单里写明「重查成本」**，别默默删。

两种**免三问**的情形（按定义不适用，不是例外放水）：

- **transcript 已丢的孤儿行**（`jsonl_path` 为空且非 zcode）——没有内容可判，直接删。
- **含明文密钥 / 敏感信息的转写**——安全优先，直接删；沉淀流程本身也有隐私边界，但会话文件留着就是风险。

2026-10-24 实测：按旧的「类型清单」写法，一批 8 条里 3 条被误判（gitlab 批量改写的口令/PAT 权限边界、退款脚本的固定 phone、B 方案漏 CSS 的踩坑路径），全是代码里查不到的。这就是把「操作是一次性的」当成「没有知识」的代价。

**优先级**：「下次干活前必须先知道的 → memory-bank」优先于「一次性 ops / 改动已落地」的类型学。两者冲突时按前者。

### 值得沉淀

未来最可能被检索、且不能从代码/git 直接复原的内容：

- 业务规则与实现口径（抽奖规则、数据导出任务中心、Redis key 规范…）；
- 架构/技术决策（服务拆分边界、共库共 jar、写权唯一…）；
- **决策的被否分支与理由**、**一次性写操作的执行口径**（权限边界、回读校验）——这两类代码/仓库里永远查不到，是 ② 里最容易漏的；
- 字段 / 接口 / 数据口径（OpenAPI 签名模式、token 回填…）；
- 排障根因（`drawPrize` off-by-one、对账不平口径…）；
- 进行中的任务与恢复点（状态带 `investigating`/`active`，后续需再更新）。

### 边界（停下问）

主题「bank/文档里多半已有」但没确证时，**别自己拍**——列出候选、说明理由，交用户一句话定。这类「多半已有」的候选，用户往往一句「删掉」即可；但**在用户说这句话之前，它不算删的许可**（③ 没查或查不清 ⇒ 不成立）。

## 抽取脉络（判断辅助）

判断一条会话的内容时，抽它的提问脉络（USER 轮 + 末答），别只看名字。

**路径别手抄 `sqlite3` CLI 的列输出**：默认 column 模式会把空格渲染成 `·`、把中文渲染成 `\u{...}`，抄出来必然「文件不存在」。要路径就用 `python3` 读库（`os.path.exists` 直接判）、或 `sqlite3 -json`。

```bash
# 精读的唯一读法：一次一段（1~5 轮，--start 是 1-based）
python3 scripts/extract.py <path> --max 200 --start 1 --limit 5
python3 scripts/extract.py <path> --max 200 --start 6 --limit 5
# zcode 从自己的库读（--id 可重复）
python3 scripts/extract.py --provider zcode --id sess_aaa
# opencode 也走 zcode 解析器，但要指它的库（jsonl_path 恒 NULL，没有文件可给）
python3 scripts/extract.py --provider zcode --db ~/.local/share/opencode/opencode.db --id ses_xxx
# 多条路径一起给＝成批读：只用于「秒杀区核名」这类诊断，不要用在精读
python3 scripts/extract.py <a.jsonl> <b.jsonl> --max 120
```

各 provider 的行结构差异（`extract.py` 已内置，供排障参考）：

| provider | 行特征 | 用户消息在 | 助手答案在 |
|---|---|---|---|
| claude | `type` = `user`/`assistant`，`message.content` 块 | `type=='user'` | `type=='assistant'` 的 text 块 |
| workbuddy | `type=='message'` + `role`，content 块 `input_text`/`text` | `role=='user'` | `role=='assistant'` |
| codex | `type=='event_msg'`，`payload.type=='item_completed'`，`item.type` | `item.type=='UserMessage'` | `item.type=='AgentMessage'`（取 `phase=='final'`） |
| zcode | sqlite `message.data.role` + `part.data.type` | role=='user' | role=='assistant' 的 `text` part |

过滤噪声：跳过以 `<` 开头、`Caveat:`、含 `tool_result`/`environment_context`、以及重复的用户消息。

## 交接给 `session-sediment`

选定后，**本 skill 不写条目**。调用用户级技能 `session-sediment`（`/session-sediment`），它负责：

- 先按主题检索已有条目（本机 `entries/` + OV），决定**更新**还是**新建**；
- 选 `kind`（`checkpoint`/`knowledge`/`case`）与模板，建事实账本、过质量门；
- 写 `s: <provider>:<id>` 引用、落 `~/.memory-bank/<project>/entries/`、更新 `_index.md`；
- 同步 OV `viking://resources/<project>/session-sediments/`。

交给它时把「**这一条**会话、归到哪个项目、草稿路径、拟定 kind、是否有同主题旧条目」说清——**一次一条**，别攒成一批再交（攒批就回到了「一批一停」的旧病）。草稿 `drafts/<sid>.md` 作为原料一并交出，正式条目落地后删掉草稿。

**注意 OV 行为**：`ov add-resource` 对**已导入**条目不覆盖，会生成 `..._1` 并列副本；正确做法是先 `ov rm -r` 旧条目、`--wait` 等任务 `completed`，再重导（细节见 `session-sediment` 与 `reference_openviking_import_shape`）。

**新项目第一次沉淀**：`--parent` 指向不存在的目录会直接 `[NOT_FOUND] Resource not found`。先 `ov mkdir viking://resources/<project>/session-sediments/` 再导。`@` 等字符在生成 URI 时会被替换成 `_`（文件名与 bank 条目名不变，别以为导错了）。

**「沉淀后删」在本条落地时就做掉**：条目写进 bank + OV 之后，把这条会话的 sid 立刻加进删除清单执行，别只在报告里写「已沉淀（可删）」。一旦留到下一轮，它就会沉在池子里被反复重读（踩过：一条已沉淀会话连过 5 轮治理还在列表里）。

## 收尾

- 沉淀完成后，源会话通常「留着只占地方」——**提议**按应用内「永久删除」语义清掉（DB 行 + 磁盘 transcript + superseded），由用户决定。
- 检查 `~/.memory-bank/*/drafts/` 是否有残留草稿：正式条目已落地的删掉；未落地但用户叫停的，留着并在报告里点名。
- 报告里给：本轮读了哪几条、删了几条、释放多少、`integrity_check`、快照路径、以及「还剩哪些会话没读」。
