# Provider 适配验证

用于检查 Provider 从原始事件到 CloudCLI UI 的完整链路，重点关注工具调用状态、计划/Todo 展示、事件去重、输出结果和错误状态。它既适用于新增 Provider，也适用于升级 SDK 或修改现有适配器后的回归验证。

## 先明确适配边界

- 先确认当前 Provider 的官方事件模型或 SDK 类型，再判断 CloudCLI 是否漏掉了事件；不要把另一个 Provider 的事件名称或语义直接套过来。
- 区分三类内容：Provider 原生事件、CloudCLI 的统一中间结构、前端渲染组件。原始事件不存在时，不应通过适配层伪造原生能力。
- Provider 的名称、版本、认证方式和事件字段可能变化。需要这些具体信息时，优先读取项目当前依赖和 Provider 官方文档/源码。
- 验证任务默认采用只读操作。除非用户明确授权，不要修改项目文件、安装依赖、提交代码或调用有外部副作用的工具。

## 验证流程

### 1. 检查原始事件到统一结构的映射

针对当前 Provider 找到以下链路：

```text
Provider SDK/CLI 事件
        ↓
Provider 适配器
        ↓
CloudCLI 统一消息或工具结构
        ↓
会话状态存储
        ↓
工具、Todo/Task、消息渲染组件
```

至少核对这些字段是否被保留或正确转换：

- 稳定的事件或工具 ID；
- 工具名称、输入参数和输出结果；
- `started`、`updated`、`completed`、`failed`、`denied`、`cancelled` 等生命周期状态；
- 计划或待办的文本、完成状态和顺序；
- 错误信息、拒绝原因和终止原因；
- 使用量或其他 Provider 特有字段（若 CloudCLI 需要展示）。

### 2. 编写或运行适配器测试

优先使用真实的最小事件样本，而不是只测试最终拼装出的消息。至少覆盖：

- 普通文本消息的增量更新；
- 一个工具从开始到结束的完整生命周期；
- 同一工具的开始、更新和完成事件被合并，而不是产生多条重复消息；
- 工具成功、有输出、失败、拒绝或没有输出的情况；
- Provider 原生计划/Todo 事件（如果该 Provider 支持）；
- 不认识的事件不会导致整个会话中断。

如果 SDK 升级后增加了事件或字段，先补最小回归样本，再修改适配逻辑。

### 3. 验证前端状态和渲染

检查会话状态是否按稳定 ID 更新已有消息。重点观察：

- 同一工具在界面上只出现一行；
- 运行中状态会进入终态，不会永久停留在 `Running`；
- 展开工具后能看到输入、输出和错误；
- Todo/Task 只在收到相应的结构化数据时渲染为任务项目；
- 普通文本形式的“计划”不能误判成结构化 Todo；
- 会话结束、失败或取消后，不会残留可交互的运行中状态。

### 4. 做一次新会话的端到端验证

修改 Provider 代码、SDK 版本或服务端配置后，先重启实际加载适配器的进程，再创建新会话。旧会话不会补发已经错过的实时事件。

可使用下面的通用只读提示词；其中“原生结构化任务/计划”是条件要求，不支持时应由 Provider 自然表现，而不是强行伪造：

```text
请对当前项目做一次只读检查，不要修改、创建、删除文件，也不要安装依赖或提交代码。

如果你支持原生的结构化任务或计划机制，请使用它；如果不支持，请不要用普通文本冒充结构化任务。

请依次完成：
1. 确认当前工作目录和 Git 分支；
2. 检查当前工作区是否存在未提交改动；
3. 检查一个与当前 Provider 适配相关的版本或配置；
4. 运行一项相关的只读测试或检查。

每完成一项就更新任务状态，所有步骤完成后再总结结果。
```

如果只验证工具调用生命周期，可以改用连续执行多个只读命令的提示词，观察每条命令是否经历“运行中 → 终态”，以及是否出现重复行。

## 出现问题时的定位顺序

不要只看最终 UI，按以下顺序缩小范围：

1. Provider 是否真的产生了预期的原始事件；
2. 适配器是否丢失了 ID、状态、输出或错误；
3. 会话状态是否按 ID 合并实时快照；
4. 消息映射是否把 Provider 状态转换成统一状态；
5. 渲染器是否错误地回退到了旧状态或结果推断。

必要时查看浏览器开发者工具中的 WebSocket/实时消息：同一逻辑工具的多个事件应使用稳定 ID，状态应从进行中走向成功、失败、拒绝或取消等终态。若原始事件中根本没有结构化 Todo，界面显示普通文本计划通常不属于适配缺陷。

## Provider 差异的维护方式

通用规则放在本 Skill 中。只有某个 Provider 的事件模型、登录方式或验证步骤反复出现且明显不同，才在 `references/<provider>.md` 增加专用说明，并从这里链接过去。不要为了单个会话 ID、一次性的版本号或临时提示词创建专用规则。

## 验收标准

- 适配器测试覆盖关键生命周期和失败路径；
- 类型检查、相关单元测试和前端测试通过；
- 新会话中工具状态能正常结束，输出和错误可见；
- 原生计划/Todo 能按结构化数据展示，非原生计划不会被误报；
- 没有因一次未知事件导致整个会话中断；
- 仍保留用户工作区中与本任务无关的改动。
