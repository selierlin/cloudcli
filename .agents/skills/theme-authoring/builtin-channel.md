# 通道 A：内置配色主题（从参照物产出一套）

通道 A 的产品是两样东西：`BUILTIN_THEMES` 里一条注册项 ＋ `src/index.css` 里一组
`[data-theme="<id>"]` 块。改的是 **L1 家族的值**，所以判据是「重新赋值了哪些
`--palette-*`」，不是「写了多少条 CSS」。

守卫比通道 B 多，但它们**只覆盖源码**：「写完了」到「它对不对」之间还隔着两步——
`npm run test:theme-tokens` 与真机读数。

本文是**从外部参照物（别人的主题包 / 编辑器配色）产出一套内置主题**的程序：

| 阶段 | 内容 |
|---|---|
| 产出 | M1–M6：选参照物 → 定形态 → 产板令牌 → 定 `coverage` → 过对比度 → 定作用域 |
| 验证 | V1–V4：驱动方式 / 过渡时机 / 变异集 / 基线对账 |
| 回写 | D1：设计文档三处 |

行号是写作时的定位起点，会随重构漂移——以「谁写的」为准。

**两条贯穿全篇的纪律**：

1. **判据优先于清单。** 契约已有定义的地方，本文只写**去哪读**，不复述内容——
   复述出来的第二份真相在契约演进时收不到警报（理由见 M4）。
2. **参照物自己会被自家契约拦下，这是常态。** 已连续三套命中，所以它是产出阶段的
   **固定一步**，不是例外（见 M5）。

## 产出

### M1 · 开工第一问：参照物注册了几个主题？

拿到一个主题包，**先清点它注册了几个主题**，不要看见一个文件就开抄。

- IntelliJ 形态：jar 内可以有多份 theme JSON，由 `plugin.xml` 的 `themeProvider`
  扩展点注册。**认 JSON 里的 `name` 字段，不认文件名**。
- 判据：能**自洽描述外观**的那些是**自足形态**——`parentTheme` 为空（或该字段缺省）、
  `ui` 键最全。
- **自足的可能不止一个**（2-P 的 `One Dark` 与 `One Dark Vivid` 都是，`ui` 都是 57 条）。
  别自己挑：把它们连同各自的 `ui` 键数一并列出，交需求方定——挑哪个是审美决定，
  不是技术判据。
- 挂着父主题的变体只表达**增量**：它省掉的键**来自父主题**。照它写，会把**父主题的颜色**
  静默带进来——不是缺色，是错色。

> 事故（2-P）：`one-dark-theme-6.2.5.jar` 注册 4 个 themeProvider。`One Dark` /
> `One Dark Vivid` 自足（`parentTheme: null`，57 个 `ui` 键）；`One Dark Islands` /
> `One Dark Vivid Islands` 挂 `parentTheme: "Islands Dark"`，只声明 38 个——
> **省掉的那 19 个是 Islands Dark 的颜色，不是 One Dark 的**。
> 前一片 2-O 同样是 IntelliJ jar，另留下一条：包内有多份 theme JSON，
> 当时靠**认 `name` 字段**找到正主——文件名会骗人。

### M2 · 三种来源形态

参照物能提供多少色板，决定工作量落在哪。先归形态，再动手：

| 形态 | 特征 | 做法 |
|---|---|---|
| **借** | 参照物**没有**外壳色板（只有语法 / 终端色） | 板令牌逐字取；外壳 L1 **自造**，与板色对齐色相 |
| **译** | 参照物**自带**完整色板，明暗两套齐 | 逐键翻译到 L1 家族 |
| **译 + 造** | 参照物**自带完整色板但只有暗色** | 暗半逐键翻译；**浅半自造**（见下） |

**「译 + 造」的浅半做法**（本线唯一一次，最值得照做）：

- 保参照物的**色相与饱和**，按**浅底**重解明度——不要直接把亮度翻转。
- **文字三档优先复用参照物自己的灰阶**：同一个灰在两种底上都要能读，所以
  「暗底下的次级灰」往往正是「浅底下的正文灰」，是复用、不是将就。
- 结果会自然地收敛到该参照物所属色系的正统浅色版（本线实测收敛到 Atom One Light
  一族），不必刻意求异。

> 事故（2-P）：保 220°／~13%，浅底取 `#202329` 作正文（15.74:1）、`#5c6370` 作次级
> （6.05:1）。旁证反过来成立：`#5c6370` 在**暗底**上只有 **2.32**——所以它不是
> 「随便一个灰」，是参照物自己为深底准备的另一档。

**先判形态再动手**：三片各命中一种，做法差别很大——形态判错，要么白写（自造了参照物
本来就有的色板），要么漏掉一整半（把「译 + 造」当「译」，忘了造浅半）。

### M3 · 板令牌怎么产出来

板令牌（`--term-*` / `--editor-*` / `--graph-lane-*`）是 `coverage: full` 的必答项
（`MUST_MOVE.full` 含这三个族，见 M4）。它们是**方法**，不是抄写：

**graph lane**

1. 色相**固定序**，与基色同序，不重排。
2. 饱和度统一到一个落在参照物语法色范围内的值。
3. 明度取**让两个底色的较差者最大**的那个点——并把该点的**最差比值报出来**（它是
   这个族的可读性下限，不报等于没验）。

**terminal 16 槽**

- **bright 槽「有值」不等于可照抄**：One Dark 的 `CONSOLE_*_BRIGHT_OUTPUT` 与对应的
  `CONSOLE_*_OUTPUT` **逐字同值**，差异只靠 `FONT_TYPE: 1`（粗体）表现；中性两槽
  （black / white 的 bright）在源里**根本不存在**。这两种情况都得自己派生——照抄会得到
  「十六槽只有八种颜色」。
- **彩色槽的派生**：保色相与饱和，只抬明度。抬多少取**出厂基色自己** normal→bright 的
  步长当量级（**不是参照物的**——它的步长恰恰是 0，正因为同值才需要派生），不取直觉值。
- **中性两槽不走这条规则**（没有可比色相）：回 M5 的老路，去参照物**自己的别处**找——
  2-P 取的是 `startBorderColor` 与 `selectionForeground`。
- `CONSOLE_BACKGROUND_KEY` 为**空值**时，读作「用编辑器页画控制台」——取编辑器页色，
  不要另配一个。

**editor 分档**

先问参照物：它的「编辑器页」与「窗口 / 面板」是**同色**还是**差一档**？差一档时
`--editor-bg` 取**面板**那档。

> 事故（2-P）：`one_dark.xml` 的 bright 与 normal 逐字同值（靠 `FONT_TYPE: 1` 区分）⇒
> 六个彩色 bright 全数派生，色相饱和不动、明度 **+9 点**，量级取自**出厂基色**自己的
> normal→bright 步长（+8.4 ~ +13.2）；两个中性 bright 源里没有 ⇒ 取参照物 UI 的
> `startBorderColor` `#464c55` / `selectionForeground` `#d7dae0`。
> `CONSOLE_BACKGROUND_KEY` 空 ⇒ 取 `#282c34`；`--editor-bg` 取 `ink-900` 而非三套姊妹主题
> 惯用的 `ink-950`。2-O / 2-N 同族，只是各自缺一到两条。

### M4 · `coverage` 取值判据与契约读法

**取值判据**

- 动了强调族**之外**的底 / 板 ⇒ `full`。
- 只动强调族 ⇒ `accent`。
- 徽标存在的意义是让「只动强调的」**不读成一套坏的 `full`**——所以别为了显得完整而
  虚报 `full`。

**读法（不复述清单）**

去 `tests/theme-tokens/theme-overlays.spec.ts` 读 `SURFACES`、`MUST_MOVE` /
`MUST_NOT_MOVE` 三个常量。**开工前必须真读一遍当前 `coverage` 的正向清单**，再决定
动哪些令牌——凭直觉判断会漏。

只在技能里留这份**指针**，不陈述「契约里有什么」：无论是成员名，还是「有一组 /
有一类」这类量词。那类句子在契约演进后会静默变成谎言，正是本文开头纪律 1 要挡的东西。

> 事故（2-N）：我给过一条「graph lane 不用动」的建议，与 `MUST_MOVE.full` 直接冲突
> （契约在 `full` 里含 `...SURFACES.graph`）。**没读正向清单就提建议**是那次的真实过失，
> 也是「必须去读」这个动机的来源。

### M5 · 参照物自己会被 §5.10 拦下：这是固定一步

**产出阶段就要做**，不要留到验证阶段当事后核算：

> 参照物的色值先过 §5.10 六配对。不合格时**不要自造替代色**——去参照物**自己的另一档**
> 里找：同一个语义在参照物的其它角色上往往有合规取值。

「参照物自己不合格」是**常态**，且它与「基色不达标」是**两类不同的问题**：前者换参照物
的另一档，后者要动出厂基色、属于有意视觉变更、得先拍板。

| 片 | 不合格的参照物值 | 实测 | 取用的替代（**均来自参照物自己**） |
|---|---|---|---|
| 2-N | Latte 的 `subtext0` 作次级文字 | 4.37:1 | 参照物自己的 `subtext1` |
| 2-O | 按钮蓝配出厂偏白标签 | 4.34:1 | 参照物自己的 `Button.default.focusedBorderColor` |
| 2-P | `accentColor` 配近白标签 / 注释灰 / 红作填充 | 3.33 / 2.32 / ~1.5 | 参照物自己的 `Button.default.focusedBorderColor` / `BookmarkMnemonicAvailable.foreground` / `errorForeground` |

自造替代色看着更快，代价是**风格断裂**——同一套主题里只有那一处颜色不属于参照物。

### M6 · 浅色半边必须用 `:not(.dark)` 作用域

浅色半边**必须**写成 `[data-theme="<id>"]:not(.dark)`。这不是风格偏好：

泄漏守卫（`theme-overlays.spec.ts` 的「a light-scoped overlay block does not leak into
the dark appearance」）**靠它才生效**——没有 `:not(.dark)` 块的主题会被**整条跳过**
（`if (!blocks.some(...)) continue`），既不检查泄漏，也不因缺失而报错。

> ⚠️ **本条无守卫拦截。** 漏写不会报错，只会让那套主题的泄漏检查**整条失效**。
> 别默认「不写会被测试拦下」——事实是静默跳过（收尾断言只要求「至少有一家被守住」）。

这条是 SKILL.md 列的那 3 条硬约束里**唯一无守**的一条——所以它在 SKILL.md 常驻，理由在这里。

## 验证

通道 A 的验证与通道 B **驱动方式不同**（那是 `verification.md` 的配方，别串用）。

### V1 · 不注入，只「选」

内置覆盖层**本来就在 bundle 里**，不需要、也不应该注入 `<style>`：

```js
// 选覆盖层 + 选明暗 —— 没有第三步
document.documentElement.dataset.theme = '<id>';
document.documentElement.classList.toggle('dark', mode === 'dark');
```

三条通道 A 专属事实：

1. **`tests/transcript-layout/` 的 fixture 不驱动主题。** 它只 `import '@/index.css'`
   与会话 store，包在 `I18nextProvider` / `UiPreferencesProvider` 里；仓库里写
   `<html data-theme>` 的只有 `ThemeContext`（`src/shared/context/ThemeContext.tsx`），
   而该 fixture 不挂它。所以主题**必须**从浏览器侧注入。
2. 判据读**绘制值**，不只读令牌：`getComputedStyle(pane).backgroundColor` 要等于
   `hsl(var(--background))` 的解析值。
3. fixture 的 pane 固定 `height: 640`，视口更高时下半屏是 body 默认色，**不是主题漏画**。

### V2 · 全局 200ms 过渡：暂停一步再读

全站元素带 `background-color` / `border-color` / `color` 的 **200ms** 过渡
（`src/index.css` 里那条 `body, div, section, …` 规则，注释写明是为主题切换有意加的）。

⇒ **任何**「设置完立刻读 `getComputedStyle`」或「连续 N 帧读到同一个值就认为已稳定」
的判据，都可能读到**插值中**的值。

**正确做法**（二选一）：

- 先读 `getComputedStyle(el).transitionDuration`，取最长时长 **+ 250ms** 再读；
- 或拿**同规则但无过渡的探针**当期望（新建一个元素贴上 `hsl(var(--background))`，
  它会瞬时跳到终值）。

**为什么「帧稳定」当不了判据**：总变化量小于 8 位量化步长时，过渡中每帧四舍五入后的
字符串会**连续相同**——「稳了 N 帧」在过渡刚起步时就成立。

> 事故（2-P）：浅色核验时 pane 的真实终值 `rgb(243,244,246)` 与起点 `rgb(247,246,243)`
> **总差只有 4/255**，帧稳定判据在过渡刚开始时就退出了，据此**误判了一次「浅色覆盖层
> 没生效」**。反向旁证：暗色（247→32，大差）在同一个判据下正常收住——
> **「一个模式对、另一个不对」本身就是量化步长不够分的信号**。

> **脚注（诊断分叉）**：真遇到「绘制色与令牌不符」时，先用 CDP
> `CSS.getMatchedStylesForNode` 问浏览器**哪条规则赢了**，别靠推理排除。2-P 实测 pane
> 只命中一条 `.bg-background`，这一步在分钟级清掉了「被别的规则覆盖」这个假设，
> 把方向正确转向**读值时机**（即本条）。

### V3 · 变异测试集纪律

每套新主题配一组变异：**改一个令牌值 → 期望恰 2 条测试转红**（两个引擎各一）。
多于或少于 2 条都说明断言面不对。

两条纪律：

1. **变异值必须真的不同于基色。** 把变异值写成「与该令牌基色相同的值」，`differing()`
   看不到移动 ⇒ **假绿**。
2. **变异锚点对着当前源码抄录**，不要凭记忆——源码形状改了（内联化、重命名），
   旧锚点只会报 `NO-MATCH`。

> 事故：纪律 1 在 **2-O 的变异第 3 组与 2-P 的 M5 连着两次**犯。重复犯错是技能该接管的
> 信号，不是「下次注意」。

### V4 · 基线对账

| 面 | 新增一套 overlay 主题的期望 | 判据来源 |
|---|---|---|
| `theme-tokens` 通过数 | **恰好 +4**（= 2 用例 × 2 引擎） | 对比度测试的 `SUBJECTS` + 覆盖层测试的逐主题循环 |
| `test:client` | **不变**（注册表 / 选择器测试是遍历式，不为新主题增用例） | 2-N / 2-O / 2-P 实测均未变 |
| `npm test` 的失败集 | **不可能因本片改变**（纯前端片） | 用 `git diff <上片 docs commit> HEAD -- server/` **= 0 行** 与 `git status --short -- server/` **为空** 两条同时成立来证明——比 `git stash` A/B 更硬 |

对不上先查**时序**：读数是不是启动于最后一次编辑之前。

## 已发布的实例

每套**覆盖层主题**（`appearance: 'system'` 的那些）在 `src/index.css` 里都有一段
`/* cc-<id> … */` 推导注释（搜 `/* cc-` 即可，行号会漂）。**注释块本身是答案源**——
对照实例读本文，比只看原理快：

| 主题 | 形态 | 从出处产出的 |
|---|---|---|
| `cc-catppuccin` | 借 | 2-N |
| `cc-islands` | 译 | 2-O |
| `cc-onedark` | 译 + 造（浅半自造） | 2-P |

`cc-ocean`（`accent`）与 `cc-polar` 是更早的示范主题，**不是从外部参照物产出的**，
不适用本文的形态分类。
