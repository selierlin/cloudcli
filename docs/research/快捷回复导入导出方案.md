# CloudCLI 快捷回复导入导出方案

> - 状态：**已实施（2026-10-13，含第 1 轮审阅响应）**——见文末「实施记录」
> - 日期：2026-10-13
> - 用途：评审「设置 → 快捷回复」页增加导入/导出的最小方案。审阅重点：**格式取舍（§3 开放问题 1）、导入语义（覆盖 vs 合并）、导入入口选型（文件 vs 粘贴）**。
> - 参考规范：`.agents/skills/frontend-module-standards/SKILL.md`（仅涉及前端）

## 0. 一句话结论

快捷回复整体就是 user preferences 里的一个 JSON key（`quickReplies`），读写链路已经存在，导入/导出**只需在前端加两个按钮 + 一对纯函数**（序列化/解析），后端与存储零改动。

---

## 1. 现状事实（已实测确认）

- 数据模型：`QuickReply = { label?: string; text: string }`，无 id、无排序字段，数组顺序即显示顺序（`src/shared/types.ts:970`）。
- 整个列表是 user preferences 的单个 key `quickReplies`；后端按不透明 JSON 存储、只校验 key 长度（`server/modules/user/user.service.ts:89`），无快捷回复专用路由。写入走前端 400ms debounce PATCH，服务端为 source of truth（`src/shared/userSettings.ts:254`）。
- `null`（从未编辑，渲染 i18n 内置默认 15 条）与 `[]`（用户删光）语义不同（`src/shared/quickReplies.ts:100`）。
- 限制：最多 50 条、label 24 字符、text 200 字符（`src/shared/quickReplies.ts:18-24`）；规范化由 `normalizeQuickReplies` 完成（`src/shared/quickReplies.ts:75`），截 50 条、丢非法项、**不 trim**。
- 管理 UI 在 `src/modules/settings/tabs/QuickRepliesSettingsTab.tsx`，每次操作全量 `writeQuickReplies`；底部已有一条限额提示文案（L161-168）可挂导入/导出按钮。
- 仓库内导入先例：主题粘贴导入（`src/shared/userThemePastes.ts`），同为 user preferences 体系；无现成「导出下载」机制，但 Blob + `a[download]` 是标准做法。

## 2. 设计

### 2.1 格式：导出 JSON（canonical），导入自动嗅探两种

- **导出**：`QuickReply[]` 裸 JSON 数组，含 `label`（无 label 的条目省略字段），即存储的原始形状，无损。文件名 `cloudcli-quick-replies.json`。
- **导入**：trim 后以 `[` 或 `{` 开头先按 `JSON.parse` 解析；**解析失败不报错，回退按行解析**（第 1 轮批注 2：行格式片段首行以 `[` 开头完全可能，如 `[DEBUG] 检查日志`）。解析结果为数组直接用；为对象且 `Array.isArray(obj.quickReplies)` 时取该字段（兼容信封，与开放问题 4 一致）；其余情况同样回退。按行解析：每行 trim 后作为一条 `{ text }`，跳过空行（含全空白行）。
  - 回退的代价：损坏的 JSON 会静默降级为逐行导入（每行文本变成一条 snippet）。确认框展示的「导入 M 条」与 50 条上限是该路径的检查点，且误导入可用旧导出文件回滚，可接受。
- 行格式**不支持 label**。理由：`text` 可含任意字符，任何分隔符（`|`、`：`）都会与正文冲突，引入转义就背离了「一行一条」的简单性；且菜单本就用 `quickReplyLabel` 在 label 缺省时回退显示 text（`src/shared/quickReplies.ts:126`），行格式的定位就是「快速共享纯文本片段」。要保 label 就用 JSON。
- 导入内容统一过 `normalizeQuickReplies`：自动截 50 条、丢非法项、复用现有上限，无需新增校验逻辑。

### 2.2 导入语义：覆盖 + 确认

- 导入 = **整表覆盖**当前列表，弹确认框告知「将替换现有 N 条，导入 M 条」。
- 合并/去重延后：合并需要去重规则（按 text？label+text？重复是否保留两次？），为一个低频操作引入一整套规则不值得（YAGNI）。
- 覆盖写入仍走 `writeQuickReplies`，localStorage 镜像即时生效、debounce 上送服务端，多端同步链路免费获得。

### 2.3 UI

`QuickRepliesSettingsTab` 底部限额提示旁加「导入」「导出」两个 ghost 按钮：

- 导出：`Blob([JSON.stringify(replies, null, 2)], { type: 'application/json' })` + 临时 `<a download>`，零依赖。
- 导入：隐藏 `<input type="file" accept=".json,.txt,application/json,text/plain">`，`FileReader` 读文本 → 解析 → `window.confirm` 确认覆盖 → 写入。
- 解析失败在按钮旁给一行 `text-destructive` 错误文案，不引 toast 等新机制。
- 导入完成后若解析器报告 `skipped > 0`（空行/非法项被丢弃、或超 50 条截断），在错误文案同位置以中性文案提示「已跳过 K 条」，避免内容被静默丢弃而不自知（第 1 轮批注 3）。

### 2.4 「从未编辑过默认列表」时导出什么

导出当前 **effective 列表**（即用户界面正看到的那份，含未编辑时的本地化内置默认）。所见即所得最不意外；把默认固化成用户数据是用户主动选择，可接受。文档在此注明该语义即可。

## 3. 开放问题（附倾向）

| # | 问题 | 选项 | 倾向 |
|---|------|------|------|
| 1 | 行格式要不要支持 `label|text`？ | ① 不支持，行 = text ② 支持，首个 `\|` 分隔 | **①**。② 的歧义（text 含 `\|`）与转义成本不值；要 label 用 JSON |
| 2 | 导入覆盖还是合并？ | ① 覆盖+确认 ② 追加+去重 | **①**。覆盖语义可预测；合并规则复杂度不值 |
| 3 | 导入入口？ | ① 文件选择 ② 粘贴 textarea 对话框 ③ 两者 | **① MVP，② 列延后项**。用户「共享到其他服务器」若走 ssh/聊天复制文本，②更顺手——可依审阅意见改判 |
| 4 | JSON 是否加 `version` 信封？ | ① 裸数组 ② `{version, quickReplies}` | **①**。类型稳定且极简，导入端可顺手兼容②（一个小分支），但导出不产信封 |

## 4. 改动清单与实施顺序

纯前端，预计 4 处：

1. `src/shared/quickReplies.ts` — 新增纯函数 `serializeQuickRepliesExport(replies): string` 与 `parseQuickRepliesImport(raw: string): { replies: QuickReply[]; skipped: number } | { error: QuickReplyImportError }`（嗅探/行解析/normalize 均在此层）。错误只返回 **code 枚举**而非拼好的文案（第 1 轮批注 1），文案映射放 UI 层 i18n；因 JSON 分支失败已回退行解析，当前枚举仅 `'empty'`（trim 后无任何可解析行）一种。
2. `src/shared/tests/quickReplies.test.ts` — 追加解析/序列化用例（JSON 含 label、裸数组、信封对象、行格式多行/空行、首行以 `[` 开头的行格式回退、损坏 JSON 回退逐行、超 50 条截断、全空文本报 `empty`）。
3. `src/modules/settings/tabs/QuickRepliesSettingsTab.tsx` — 两个按钮 + file input + confirm + 错误/跳过文案（i18n code → 文案映射在此层）。
4. i18n：`src/modules/i18n/locales/en/settings.json` 与 `zh-CN/settings.json` 在 `quickRepliesSettings` 下补 6 个 key（export/import/importFile/importConfirm/importEmpty/importSkipped）。（实施时修正：仓库惯例是**仅 en + zh-CN 全量维护**，其余 13 个语言文件省略整个块、走 `fallbackLng: 'en'` 回退——原案「15 个语言文件」有误。）

验收：

- [ ] 导出文件可被再次导入，round-trip 后列表逐条相等（含 label 有无的差异）。
- [ ] 行格式 `.txt` 导入成功，空行被跳过，每行成为一条无 label 记录。
- [ ] 首行以 `[` 开头的行格式文本（如 `[DEBUG] 检查日志`）正确回退逐行导入，不被误判为 JSON 报错。
- [ ] 超 50 条的导入被截到 50 条且 UI 限额提示正确。
- [ ] 发生跳过/截断时（`skipped > 0`）UI 显示「已跳过 K 条」。
- [ ] 全空/无有效行文本给出 `empty` 错误文案，不改动现有列表。
- [ ] 多语言固化场景：UI 语言 A 下未编辑即导出（得到 A 语言的内置默认），导入到语言 B 环境后列表固定为 A 语言文本（第 1 轮批注 4，固定该行为）。
- [ ] 导入覆盖后聊天输入框上方菜单即时反映新列表（订阅链路已有）。

## 5. 风险与回滚

- 风险极低：不改存储结构、不改后端、不动聊天侧读取链路；解析函数有单测兜底。
- 唯一行为变化是「用户主动点按钮」，误导入可通过再导入旧导出文件回滚（这也正是本功能的存在意义）。
- 延后项（备查）：粘贴 textarea 导入；合并/去重导入模式；CLI 端导出命令。

## 审阅批注

### 审阅者：CodeBuddy (GLM)（2026-10-13）

> [!IMPORTANT] §4 `parseQuickRepliesImport` 返回 `{ error: string }`：若 error 是函数内拼好的英文 message，UI 直接展示会绕过 i18n。建议改为返回错误枚举/code（如 `'invalid-json' | 'empty'`），文案映射放在 UI 层 i18n，与第 4 条「i18n 补 key」自然对齐。

> [!TIP] §2.1 嗅探歧义：行格式文件的首行若以 `[` 开头（用户片段文本本身以 `[` 开头是完全可能的），会误走 JSON 分支并直接报错。建议 JSON.parse 失败时**回退按行解析**而非报错，嗅探只作分流提示、解析失败不终止。

> [!TIP] §2.2 skipped 反馈缺口：行格式会跳过空行，normalize 会丢非法项/截断，但确认框只告知「替换 N 条、导入 M 条」。导入完成后若 `skipped > 0`，建议在既有 `text-destructive`（或同位置中性文案）提示「已跳过 K 条」，否则用户无从察觉内容被静默丢弃。

> [!NOTE] §2.4 多语言固化：未编辑过时导出的是**当前 UI 语言**的内置默认 15 条，导入到另一语言环境会固化原语言文本。文档已注明「所见即所得」语义，可接受，仅提醒验收用例最好覆盖一次该场景以固定行为。

> [!NOTE] §2.2 多端并发：覆盖写入走 400ms debounce PATCH，若另一端正在编辑快捷回复，导入可能导致那端改动被覆盖——但这属现有同步链路既有语义，导入只是放大单次写入，不值得为此加锁。

> [!NOTE] §2.3 `window.confirm` 与仓库既有惯例一致（`useCredentialsSettings`、`useMcpServers` 等多处使用），无需改为对话框组件，维持原案。
