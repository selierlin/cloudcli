## 1. 背景与已确认现状

篇幅分布见 §0。由此有两点：`selectors.md`（69 行）与 `verification.md`（187 行）**没有一句适用于通道 A**（`verification.md:3` 自述范围为「用户 CSS 主题」，其主力配方 57-139 行的骨架是「读文件 → 注入 `<style>`」——通道 A 的覆盖层本来就在 bundle 里）；`SKILL.md:35-66` 的通道 A 是一份**操作清单**（注册 → 写块 → 不进 `@layer` → 明暗 → 跑守卫 → 回写 → commit），**不是方法**——它不回答「值从哪来、为什么是这些值、怎么证明它对了」。

通道 A 的方法并非没被记录，而是**记录点不是下次创作的入口**：`src/index.css` 的 5 个注释块（171 行）是绑在实现上的**实例记录**；设计文档的实施记录按片组织（同一方法被 2-N/2-O/2-P 切成三份）；memory 不在仓库、不进技能加载路径。**技能才是入口。**

§4 的每条规则都以下面的编号为证据（引用清单见 §11）：

- **E1 · 泄漏守卫会整体跳过不合规的主题。** `theme-overlays.spec.ts:447` 在主题没有 `:not(.dark)` 块时直接 `continue`；收尾断言（476-480）只要求 `guarded` 非空。现有 5 套都写了，**今天没有裸露面**，但这条约定是**承重的**（守卫覆盖面依赖作者自觉），技能里没写。
- **E2 · `selectors.md:13` 的 `data-theme` 枚举停在 3 个内置 id**（末尾有「…」），注册表 `src/shared/constants.ts:330-380` 现有 **7 个**。
- **E3 · 全局 200ms 颜色过渡让「即时读值」不可信。** `src/index.css:606-615`（`@layer base` 内，注释写明是为主题切换）给 `body, div, section, …` 上了 `transition: background-color / border-color / color 200ms`；实测 `getComputedStyle(pane).transitionDuration = 0.2s`。
- **E4 · 新增一套 overlay 主题对 `theme-tokens` 的增量恰为 +4**（`contrast.spec.ts:43-46` 的 `SUBJECTS` 每套 +1 用例、`theme-overlays.spec.ts:372-373` 的逐主题循环每套 +1 用例，×2 引擎）。实测 2-O `124→128`、2-P `128→132`。

## 2. 目标、指标与非目标

### 2.1 目标

1. 让**通道 A** 在技能里与通道 B **对等**：从「照着一个外部参照物做出一套随包发布、受契约守卫的配色主题」这件事，能在**只读技能**的前提下走完。
2. 把 2-N/2-O/2-P 反复重推的判据固化成**可查的规则**（M1–M6），把三次踩过的验证陷阱固化成**可执行的判据模板**（V 系列）。
3. 不制造第二份真相：凡契约已有权威定义的地方，技能只写**去哪读**与**判据**，不复述清单（该取向已由 §9.1-A3 的裁决落定）。

### 2.2 可验证指标

| 指标 | 判据 |
| --- | --- |
| 通道 A 篇幅对等 | 通道 A 正文行数 ≥ 通道 B 正文行数（当前 32 vs 256） |
| 每条新规则都有事故来源 | 逐条能指到 2-N/2-O/2-P 的具体项；**写不出事故来源的规则一律不收** |
| **盲测通过**（主力验收，见 §6.2） | 把 `src/index.css` 的 5 个注释块与设计文档的 2-N/2-O/2-P 实施记录临时移出视野，让一个未参与本线的读者**只读技能**回答 M1–M4 的四个问题；四项全中即通过 |
| 引用可复核 | §11 的每条 `文件:行号` 在提交时实测通过 |
| 不改产品行为 | 技能那次提交的 `git diff --stat` **只触及 `.agents/skills/theme-authoring/**`**（本方案自身另提交） |

> 「不改产品行为」用**改动范围**证明即可，不必拿测试读数证明——改的是 `.md`，`npm test` 一类读数必然不变，动员整套测试去「证明没误碰源码」是平凡真，证明力为零。

> **一条取舍声明**（第三轮两方裁决，见 §9.2）：**已被契约/守卫覆盖、且漏写即被拒的规则，不进技能正文**——它的价值已由 CI 承担，技能再写只是第二道保险。这解释了为什么「方案没写 `@layer` 禁令」**不等于**「它不重要」：它由 `theme-overlays.spec.ts:291` 的结构断言守着，漏写会**报错**（不是静默失效），故不进正文，只作为「硬约束」被点名（三条定名见 §5）。
>
> 这条声明正是对「写不出事故来源的不收」这个门槛的**补丁**：门槛筛不掉「已被守卫兜住、所以没造成事故」的规则。**唯一例外是无守的那条**——M6 的 `:not(.dark)` 漏写**静默**，它必须进正文。

### 2.3 非目标

- **不删** `src/index.css` 的 5 个注释块。它们是有价值的**实例记录**（含参照物版本号、具体色值、具体偏离理由），M 系列是把**方法**提到技能层，不是把实例记录搬家。
- **不改**任何契约或守卫。M6 只把「约定是承重的」写进技能，**不修 E1 的守卫缺口**（修护栏不属于「补强技能文档」这个范围，另立）。
- **不改**通道 B 的正文（除非采纳路线 3，见 §3）。
- **不做**主题本身的新增、改色或重构。
- **不加**「技能自检脚本」。技能是散文，用盲测（§6.2）验收，不引入需要维护的脚本。

## 3. 候选路线与决策

问题只有一个：**通道 A 的方法正文放哪。**

### 3.1 路线 1：增量补丁

在 `SKILL.md:35-66` 原地扩写 M1–M6，在 `verification.md` 追加 V 系列一节。

- ✅ diff 最小、review 面最窄、无新增文件。
- ❌ `SKILL.md` 从 145 行长到约 300 行，两通道挤在一个文件里，读者进门先要判断「我在哪条通道」。
- ❌ `verification.md` 会出现两套驱动方式（B 注入 `<style>` / A 选 `data-theme`）却只有一个标题层级，容易串读——2-P 已经证明这两种驱动方式的**判据不同**（一个要比对「样式在不在文档里」，一个只要「选对了 id」）。

### 3.2 路线 2：新增分册（**推荐**）

- 新增 `builtin-channel.md`：M1–M6 完整正文 + V 系列的验证配方（通道 A 自足）。
- `SKILL.md` 的通道 A 段收成「**路由 + 3 条不可省略的硬约束**」，并加一张「你在哪条通道 → 读哪个文件」的表。
- 通道 B 的三份文件**一字不动**（除两处旧枚举的顺手修正）。

- ✅ 与通道 B 对等；单一职责；按需加载（做通道 B 时不读 `builtin-channel.md`，省 context）。
- ✅ 通道 B 的正文刚被大量实践校准过，**不碰**它是最安全的。
- ❌ 多两个概念（`SKILL.md` 的指针要维护，别漂）。

### 3.3 路线 3：合并重构

拆成 `SKILL.md`（纯路由）+ `channel-a.md` + `channel-b.md` + `shared/`（令牌体系与对比度守恒两通道共用）。

- ✅ 结构最干净，消除 `SKILL.md` 里两通道混杂。
- ❌ **要动通道 B 的现有正文**（令牌体系、`--n-gray-*` 别漏、`@import` 闸门那张表都在 `SKILL.md` 里，移出去就有失真的风险）。
- ❌ review 面最大，而收益（省掉 `SKILL.md` 里的混杂）并不对应任何一次真实事故。

### 3.4 推荐（第三轮已定稿）

**路线 2**。理由：通道 B 的正文是被实践反复校准过的资产，不该在「给通道 A 补正文」这次顺手动它；而通道 A 是**从 0 到 1**，独立成册成本最低、边界最清晰。

第三轮两方**各自独立背书**路线 2（此前两轮它既无人反对、也无人背书，是唯一仍无外部意见的硬决策；见 §9.2 与文末「牵头结论 · 第三轮」）。另两条的否证：路线 1 的致命伤（`verification.md` 混入两套驱动方式却只有一个标题层级、串读风险）2-P 已实证；路线 3 的收益不对应事故、成本却最大。

## 4. 详细设计

以下每条给出：**现状** → **改成什么** → **证据（事故记录）**。「事故」一律指 2-N / 2-O / 2-P 的具体项。

### M1 · 参照物选择：开工第一问

- **现状**：技能没有这一步。`SKILL.md:35-66` 直接从「注册一项」开始，仿佛参照物已经选好了。
- **改成**：`builtin-channel.md` 的第一节，定成硬规则：

  > 拿到参照物后**第一件事**是清点它**注册了几个主题**，不要看见一个文件就开抄。
  > 判据：能自洽描述外观的那一个，是**自足形态**——`parentTheme` 为空（或等价字段缺省）、`ui` 键最全的那些；挂着父主题的变体只表达**增量**，它省掉的键来自父主题，照它写会把**父主题的颜色**静默带进来。

- **证据**：2-P。`one-dark-theme-6.2.5.jar` 注册 4 个 `themeProvider`：`One Dark` / `One Dark Vivid` 自足（`parentTheme: null`，57 个 `ui` 键）；`One Dark Islands` / `One Dark Vivid Islands` 挂 `parentTheme: "Islands Dark"` 且只声明 38 个——**省掉的那 19 个是 Islands Dark 的颜色，不是 One Dark 的**。同一 skill 内 2-O 的形态：Islands 的 jar 里有多份 theme JSON，**认 `name` 字段、不认文件名**。

### M2 · 三种来源形态与各自做法

- **现状**：不存在。三次都是临场判断。
- **改成**：`builtin-channel.md` 给一张分类表 + 每类的做法：

  | 形态 | 特征 | 做法 | 来源 |
  | --- | --- | --- | --- |
  | **借** | 参照物**没有**外壳色板（只有语法/终端色） | 板色逐字取，外壳 L1 自造 | 2-N |
  | **译** | 参照物**自带**完整色板（明 + 暗） | 逐键翻译到 L1 家族 | 2-O |
  | **译 + 造** | 参照物**自带完整色板但只有暗色** | 暗半逐键翻译；**浅半自造**：保色相与饱和、按浅底重解明度，**文字档优先复用参照物自己的灰阶** | 2-P |

- **证据**：2-P（第三种形态首次出现）。浅半做法实测有效：保 220°/~13%，`#202329` 作正文（白底 15.74:1）、`#5c6370` 作次级（6.05:1）——**同一个灰在暗底上只有 2.32**，所以「复用参照物自己的灰阶」是可行的，不是将就。

### M3 · 板令牌的产出方法

- **现状**：不存在。板令牌（`--term-*` / `--editor-*` / `--graph-lane-*`）是 `coverage: full` 的必答项（契约的 `MUST_MOVE.full` 含这三个族），但技能只字未提怎么产出。
- **改成**：`builtin-channel.md` 给三小节的**方法**（不是清单）：
  - **graph lane**：十色相**固定序**（与基色同序）；饱和度统一到一个落在参照物语法色范围内的值；明度取**让两个底色的较差者最大**的那个点，并把该点的最差比值报出来。
  - **terminal 16 槽**：若参照物只发布 8 槽（或**用粗体而非色值**区分 bright），bright 必须**派生**——保色相饱和、按参照物自身 normal→bright 的步长档位抬明度；若参照物的 `CONSOLE_BACKGROUND_KEY` 为**空值**，读作「用编辑器页画控制台」，取编辑器页色。
  - **editor 分档**：先问参照物的「编辑器页」与「窗口/面板」是**同色**还是差一档；差一档时 `--editor-bg` 取面板那档，而非默认取最深的窗口档。
- **证据**：2-P（`one_dark.xml` 用 `FONT_TYPE: 1` 区分 bright ⇒ 8 个 bright 全部派生，幅度取基色自身 normal→bright 的 +8.4~+13.2；`CONSOLE_BACKGROUND_KEY` 空 ⇒ 取 `#282c34`；`--editor-bg` 取 `ink-900` 而非三套姊妹主题的 `ink-950`）。2-O/2-N 同族。

### V2 · 全局 200ms 颜色过渡：暂停一步再读

- **现状**：`verification.md` 的配方里只有 `page.waitForTimeout(800)` 这种直觉性的等待，没有解释**为什么必须等**，也没有「等多久」的判据。
- **改成**：`builtin-channel.md` 的验证节加一条硬规则：

  > 全站元素带 `background-color / border-color / color` 的 **200ms** 过渡（`src/index.css:606-615`，为「主题切换」有意加的）。
  > ⇒ **任何**「设置完立刻读 `getComputedStyle`」或「连续 N 帧读到同一个值就认为已稳定」的判据，都可能读到**插值中**的值。
  > 正确做法：先读 `getComputedStyle(el).transitionDuration`，取最长时长 `+ 250ms` 再读；或拿**同规则但无过渡的探针**（新建一个元素贴上 `hsl(var(--background))`，它会瞬时跳到终值）作为期望值来对照。

- **为什么「帧稳定」当不了判据**：当总变化量小于 8 位量化步长时，过渡中每帧四舍五入后的字符串会**连续相同**，「稳了 N 帧」在过渡刚起步时就成立。

- **证据**：E3（2-P）。实测 `transitionDuration = 0.2s`；浅色核验时 pane 的真实终值 `rgb(243,244,246)` 与起点 `rgb(247,246,243)` **总差只有 4/255**，帧稳定判据在过渡刚开始时就退出了，我据此**误判了一次「浅色覆盖层没生效」**。反向的旁证：暗色（247→32，大差）在同一个判据下正常收住——**「一个模式对、另一个不对」本身就是量化步长不够分的信号**。
