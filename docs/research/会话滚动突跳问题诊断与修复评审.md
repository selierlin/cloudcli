## 0. 结论先行

1. **这不是一个 bug，是一组几何不稳定叠加出来的现象。** 用户每一次上滑/加载，都可能在一次交互里跨越多个文档高度不可预测的 commit：懒行从 100px 估算膨胀成真实高度、执行过程折叠投影按新窗口成组切换 `hidden`、"加载全部"触发整片 DOM 重挂载。`[实测]` 报告 B 里，同一容器在一次点击后 `scrollHeight` 从 19383 掉到 3065，随后又涨到 10987、13493。
2. **滚动位置有四个互不知情的写入者。** 跟随循环、锚点结算循环、prepend/加载全部还原、懒行自校正，都会直接写 `container.scrollTop`；此外还有底边 resize 补偿和列表侧边栏，不在本文范围。没有人对"最终锚点是否回到原位"做全局校验。`[代码可证]`
3. **谁移动了 `scrollTop` 只能靠启发式猜。** 容差、时间窗、帧计数、写入回读，全部是"猜这一笔是不是平台/惯性/自己造成的"。`[代码可证]` 参数已经增加到 10 个且互相耦合（§4.2）。
4. **当前补丁修的是第 3 条，没有动第 1 条。** 所以在几何再次塌陷/膨胀时，它只能"检测异常并放弃补偿"（`stalled` / `unreachable` / `detached` / `contended`），用户仍停在错误位置——这正是"改了还是有"的原因。`[推断，与 §3.2 的实测吻合]`
5. **验收环境与故障环境不是同一个引擎。** 故障在 iPhone 18.7 的 WKWebView（滚动由 `UIScrollView` 承担），现有自测是 Playwright Chromium。量化、回弹、惯性、`overflow-anchor` 支持全都不一样。用 Chromium 通过不能证明 iOS 通过。`[实测 + 平台事实]`
6. 因此本文建议：**先取证、再定性、最后才改**（§7）。评审需要先回答 §10 的 Q1–Q9，特别是 Q1（是否接受"几何稳定化优先于滚动补丁"）。

## 2. 运行环境与方法论问题

### 2.1 故障环境

`[实测]` 两份可用报告的 UA 与视口一致：

```
Mozilla/5.0 (iPhone; CPU iPhone OS 18_7 like Mac OS X) AppleWebKit/605.1.15 (KHTML, like Gecko) Mobile/15E148
viewport 440 x 956, dpr 3
```

这是 iOS 上的 WKWebView。滚动容器是 `div.chat-messages-pane`（`overflow-y: auto`），其滚动、回弹、惯性由 `UIScrollView` 承担，JavaScript 只能通过 `scrollTop` 请求位置，**无法同步知道平台何时覆盖了它**。

### 2.2 与桌面浏览器的差异（决定"能不能在本地复现"）

| 行为 | iOS WKWebView | Chromium 桌面/模拟 | 对实现的影响 |
| --- | --- | --- | --- |
| `scrollTop` 精度 | 落到设备像素网格，读回被截断（写 2368.859 → 读 2368）`[实测]` | 保留小数 | 每次写入都会被读回比较，容差必须覆盖量化误差 |
| 越界位置 | `scrollTop` 可为负（橡皮筋），平台逐帧弹簧回位 `[实测]` | 通常直接 clamp 到 0 | 负值期间任何写入都会被丢弃或终止弹簧 |
| 抬手后的惯性 | 没有 touch 事件，只有 `scroll` 事件 `[平台事实]` | 同样无事件，但曲线不同 | 无法用输入事件区分"读者在滑"和"平台在滑" |
| 滚动时机 | 合成线程异步，`scrollTop` 的写入可能在 1–2 帧后才被覆盖 `[实测]` | 同步性更强 | 写完当帧读回"成功"不代表下一帧还在 |
| 原生 scroll anchoring | 不支持（Safari 至今未实现）`[平台事实，见既有文档 §3.1 S3]` | 支持，且默认开启 | Chromium 上会出现"浏览器补一次 + 我们补一次"的双付 |
| 生命周期 | 后台/恢复、键盘、安全区都会改变 `clientHeight` | 差异大 | 底边补偿只能在真机验证 |

**结论**：本地 Playwright（chromium）能验证逻辑分支，**不能验证 iOS 的滚动语义**。上一轮"本地全绿、真机仍跳"正是这个原因。

### 2.3 现有验收手段及其盲区

| 手段 | 覆盖 | 盲区 |
| --- | --- | --- |
| Vitest + jsdom 桩（`transcriptScrollOwnership.test.tsx` 等，1524 例） | 分支逻辑、常量边界、写入次数 | jsdom 无合成器、无量化、无惯性；桩的几何由测试自己定义，规则与桩可能一起错 |
| Playwright chromium + CDP 触摸（`/tmp/accept.mjs` 等） | 真实 `pointer`/`touch`、真实布局 | 引擎语义不同；只能证明"Chromium 上不跳" |
| 诊断面板上报（`ScrollDiagnosticsPanel`） | 真机逐帧位置、事件时序 | 需要用户手动上报；第 4 次失败没有报告 |
| 人工观察 | 最终观感 | 无法定位帧级原因，无法回归 |

## 3. 已确认的失败机制

以下每一条都有报告或代码支撑。报告 A = `client-2026-11-03T15-48-09-147Z`，报告 B = `client-2026-11-03T16-52-00-383Z`，两者都来自**补丁前**的构建 `index-C7cuHQWb.js`。

### 3.1 F1：终态错——文档塌陷后跟随循环抢写

`[实测，报告 B]` 时间轴（ms 为报告内相对时间）：

| 时刻 | 事件 | scrollTop | scrollHeight | 说明 |
| --- | --- | --- | --- | --- |
| 5275 | `RS anchor` | 17776 | 19383 | 分页补偿 16158px，锚点从 -50 落到 16108 |
| 8615 | `W follow` | 3065 | 3065 | **文档塌到 3065**，跟随循环把视口写到"底部" |
| 8618 / 8640 / 8656 | `W follow` ×3 | 3065 | 3065 | 连续重写，确认停在尾部 |
| 8818 | `W follow` | 2193 | — | 文档继续变化，跟随继续追 |

读者从 17776 被拉到 3065，位移 -14711px。触发点是"加载全部"：`visibleMessageCount` 从 100 改为 `Infinity`，同时 `hasMoreMessages`、`totalMessages`、`allMessagesLoaded` 在多个 `setState` 中更新；中间 commit 的 DOM 规模远小于前后两端（报告 B 的 mutation 统计：added 1910 / removed 1671，rowMounts 只有 3 / rowUnmounts 15），文档高度塌陷。

塌陷本身**不是滚动层造成的**，滚动层只是受害者：

- `[代码可证]` `visibleMessages` 是尾部切片（`useChatSessionState.ts:2067-2070`），扩容本应让文档变长。
- `[代码可证]` 执行过程投影按窗口重算分组，`isWindowTruncated = turn.boundary === 'partial'`（`utils/executionProcess.ts:146`）；成员行用 CSS `hidden` 收起，组随窗口边界整批切换可见性。
- `[推断]` 中间 commit 里，大量行的折叠状态与懒行挂载状态同时翻转，真实高度尚未测量，`scrollHeight` 短暂只剩一屏多一点。这一条与既有文档《长会话上滑阅读锚点漂移修复方案》§3.1 S5 登记过的机制一致，但**尚未逐帧证明**是同一个原因（§5.2 P1）。

### 3.2 F2：过程跳——三个写入者在 31ms 内各补一笔

`[实测，报告 B]`，同一次上滑分页：

| 时刻 | 事件 | scrollTop | scrollHeight | 增量 |
| --- | --- | --- | --- | --- |
| 12355 | `RS anchor`（还原写 8683px） | 8690 | 10987 | +8683 |
| 12373 | `W lazyRowAnchor` | 9628 | 13493 | +938 |
| 12386 | `W anchorSettle` | 12134 | — | +2506 |

31ms 内累计写入 12127px。三次写入都有各自的理由（还原、懒行膨胀、锚点结算），但**没有任何一方知道另外两方已经补过**；也没有人在末尾校验"锚点是否回到了起始的 53px"。`AS1 stable 12 frames, correctedPx 2506` 说明结算循环认为自己收敛了。

这类失败的特征是：**终态可能正确，过程可见**。用户看到的是 3 帧内内容被推走 3444px，即使最后停在对的位置，也已经"跳"过了。

`[代码可证]` 四个写入点：

| 写入者 | 位置 | 触发 | 是否有全局仲裁 |
| --- | --- | --- | --- |
| 跟随循环 `scrollToBottom` | `useChatSessionState.ts:793` | 内容增长、布局提交 | 只检查 `anchorSettleRef` 等标志，不检查"别人刚写过" |
| 锚点结算 `startAnchorSettle` | `:1147` | 每次还原后逐帧 | 只校验自己上一笔 `lastWrite` |
| prepend/加载全部还原 | `:1580 / :1618 / :1626` | 分页 commit | 无（假定自己是唯一写入者） |
| 懒行自校正 | `LazyMessageRow.tsx:154` | 惰性挂载状态变化 | 无（只检查越界与"测量期间 offset 是否动过"） |
| 底边 resize 补偿 | `useBottomEdgeResizeCompensation.ts:42` | 容器高度变化 | 记录 `programmaticScrollTopRef`，但该 ref 是**单槽**，会被后来者覆盖 |

### 3.3 量化误差被当成惯性

`[实测，报告 A/B 的帧采样]` iOS 写 2368.859375、读回 2368，下一帧比较后判定"位置没落在我写的地方"，于是走动量分支，把 `anchorOffset` 再挪一页，形成 1184 / 1185 / 1184 的帧间振荡，连续 32 帧。

当前补丁的处置：`ANCHOR_SETTLE_LANDING_SLOP_PX = 1.5`、写后读回 `landed`、`lastOffset` 取写后值。`[代码可证]`

### 3.4 越界写入被平台吞掉，循环反复补同一笔

`[实测]` 目标超过 `scrollHeight - clientHeight` 时，写入被 clamp，下一帧测到同样的 drift，再补一次；连续 4 次 2350px 直到贴住尾部。当前补丁的处置：目标越界跳过不写、连续 10 帧够不着则 `unreachable` 收手。`[代码可证]`

### 3.5 Chromium 上原生锚定与 JS 补偿双付

`[实测，编辑记录]` Chromium 在一次 7900px prepend 中自己把 `scrollTop` 从 64 移到 7964，还原再补 7900，内容被推走一整页。当前补丁：`.chat-messages-pane { overflow-anchor: none }`（`src/index.css:1100`）。`[代码可证]`

副作用：这不是"修好 Chromium"，而是**把 Chromium 拉到 WebKit 的语义**——从此所有引擎都完全依赖 JS 补偿，也就把 §3.1/§3.2 的风险放大到所有平台。

### 3.6 机制汇总

| 编号 | 机制 | 证据 | 当前是否有对策 | 残余风险 |
| --- | --- | --- | --- | --- |
| M1 | 一次交互跨多个高度不可预测的 commit（整片重挂载、折叠翻转、懒行估高） | `[实测]` 19383→3065→13493 | 无（只在滚动层止损） | 高：任何补偿公式都建立在"commit 前后几何可比"上 |
| M2 | 多写入者无仲裁、无终态校验 | `[实测]` 31ms 三次写 12127px | 部分（各自加守卫） | 高：新增守卫会让一方放弃，留下错误位置 |
| M3 | 量化误差被误判为动量 | `[实测]` 1184/1185 振荡 | 有（1.5px slop + 回读） | 中：dpr 与系统版本变化后可能重现 |
| M4 | 越界写入被吞、循环重试 | `[实测]` 2350px × 4 | 有（跳过 + unreachable） | 中：放弃后没有兜底 |
| M5 | 惯性期无输入事件，无法区分读者/平台 | `[实测]` 55 帧冻结 vs 1 帧 | 有（6px 阈值 + 300ms 输入窗） | 高：阈值同时受滑动速度与渲染负载影响 |
| M6 | Chromium 原生锚定双付 | `[实测]` 7900px 双付 | 有（关闭 overflow-anchor） | 中：把平台兜底关掉，JS 成为唯一保障 |
| M7 | 负偏移（橡皮筋）期间写入被丢弃 | `[代码可证]` + `[实测]` | 有（`scrollTop < 0` 时等待） | 中：等待窗口与弹簧时长耦合 |

### 4.1.1 范围划分：样式改动与滚动补丁分开

手机端聊天框的**水平内边距**（`ChatComposer.tsx` 的 `pl-2 → pl-3`、`ChatMessagesPane.tsx` 的 `px-2 → px-3`、`index.css` 中 `.chat-composer-shell` 的 `padding-right 0.5rem → 0.75rem`，桌面端仍由 `sm` 断点维持 16px）也在同一工作区。它把手机端消息列与输入框统一到 12px，**只改水平内边距，不改行高、不改容器高度，对纵向跳动零影响**。

它不属于滚动修复，但也不应丢弃：建议**单独提交**（`fix(chat): 手机端消息列与输入框统一 12px`），滚动补丁的评审范围只保留上表。这样两个改动各自有独立的验收标准，出问题时不会互相背锅。

已回退的一项：`SidebarRecentConversations.tsx` 删除 `ChevronRight` 与 `group` 类（侧边栏箭头，与本问题无关），备份见 §4.4。

### 4.3 代价

1. **可读性**：`useChatSessionState.ts` 的核心循环从约 30 行涨到约 300 行，`tick` 里同时处理回弹、惯性、量化、越界、detached、contended、stalled 七种情况，任何新增场景都要在这条链上再插一段。
2. **可测试性**：jsdom 桩只能验证"我写的规则在我写的几何下成立"。1524 例全过不能证明真机不跳，事实上已经反证。
3. **可回退性**：补丁与诊断代码、手机端宽度调整混在一个工作区（§4.1.1 建议分开提交），滚动补丁内部也无法按症状单独回退——诊断埋点、结算循环、还原分支是同一批改动。

## 6. 候选方案

### 方案 A：继续在滚动层加规则（现状）

- 做法：针对第 4 次失败再加一条判定/一个阈值。
- 优点：改动最小，已有测试与诊断可复用。
- 缺点：M1 未处理，几何每次塌陷都会击穿新增规则；参数继续膨胀；每次都要真机复测，无法本地回归。
- 结论：**不建议**作为主路线，可作为止血。

### 方案 B：几何稳定化优先（推荐 Phase 1）

核心规则：**任何一次 commit 不得让"锚点上方的高度"发生超过阈值的变化**；做不到时，必须在同一 commit 内用已知高度占位，而不是让 DOM 先塌再长。

具体可选手段（按侵入性排序）：

1. **禁止"加载全部"的塌陷中间态**：把 `setVisibleMessageCount(Infinity)` 改为分批扩容（每帧 +N，且每批都在 `useLayoutEffect` 内还原）；或把同一次用户操作涉及的多个 `setState` 收进一个 `flushSync`/同一个 transition，避免 React 分多帧提交。
2. **折叠切换时钉住高度**：执行过程组从展开变收起（或反向）时，先给容器写入 `height: <measured>px`，下一帧再放开，避免"成组归零"。
3. **懒行估算高度与真实高度对齐**：占位高度取该行最近一次测量值（已存在于 `LazyMessageRow` 的 `measuredHeight`），不要固定 100px。

- 优点：直接消除 M1，后续滚动规则才有意义；可独立验收（只看 `scrollHeight` 曲线，不需要判断"谁写的"）。
- 缺点：需要动 `ChatMessagesPane` 与 `executionProcess` 的消费点；分批扩容会让"加载全部"变慢（可用视觉提示掩盖）。

### 方案 C：单一滚动协调器（推荐 Phase 2）

核心规则：**只有协调器能写 `container.scrollTop`**；其它模块提交"意图"（我要补偿 N px / 我要跟到底 / 我要钉住某行），由协调器在每帧合并、排序、去重，并在帧末校验"锚点回到原位"。

- 优点：消灭 M2；不再需要靠 `programmaticScrollTopRef` 猜归因；参数收敛到一处。
- 缺点：是一次结构性重构（四个写入点全部改造），风险集中；必须有真机回归能力才能上线。
- 建议：在方案 B 落地、几何可预测之后再做的可能性更大；如果评审认为 B 不足以解决，可先做 C 的最小版（只统一 `scrollTop` 写入口，不改各模块的判定逻辑）。

### 方案 D：改回原生 scroll anchoring，删除 JS 补偿

- 结论：**不可行**。iOS/Safari 至今不实现该特性（既有文档 §3.1 S3 已按 caniuse 逐版本核对），而故障环境正是 iOS。
- 可作为 Chromium 上的对照组（P4），不作为方案。

### 方案对比

| 维度 | A 继续加规则 | B 几何稳定化 | C 单一协调器 | B + C |
| --- | --- | --- | --- | --- |
| 解决 M1（塌陷） | 否 | 是 | 否 | 是 |
| 解决 M2（多写入者） | 部分 | 否 | 是 | 是 |
| 改动范围 | 小 | 中 | 大 | 中大 |
| 可本地回归 | 弱 | 强（几何断言） | 中 | 强 |
| 真机依赖 | 高 | 中 | 高 | 中 |
| 风险 | 症状反复 | 加载变慢 / 投影改动 | 重构引入新缺陷 | 工期长 |

### 7.1 本次采纳的修复（2026-11-04，真机报告定性后）

真机报告 `client-2026-11-04T02-08-11-955Z-e36ece73.json`（iOS 18.7 WKWebView，440×956）把问题收敛到了一个窗口：6 次"加载更早"里，`scrollTop ≥ 300` 的 3 次全部成功，`scrollTop ≤ 0` 的 3 次全部失败。

| 时间 | `scrollTop` at commit | 实测插入 | 结果 |
| --- | --- | --- | --- |
| 5495 | 3212 | 3182 | 写入生效 |
| 5861 | 308 | 283 | 写入生效 |
| 11840 | 6277 | 6278 | 写入生效 |

即：不是公式错，是"插入提交落在顶部回弹窗口"这一个时机问题。采纳两条改动，均不含结算循环的规则变更：

1. `src/index.css` —— `.chat-messages-pane { overscroll-behavior-y: none }`。WebKit 不再为该容器制造负 `scrollTop` 窗口，写入与矩形测量同时恢复正常。选 CSS 而非 Swift 的原因：Capacitor 8.6.0 已对 `WKWebView.scrollView` 设过 `bounces = false`，但那只覆盖 web view 的根滚动，管不到内部的 `overflow-y: auto` 容器。
2. `useChatSessionState.ts` —— `loadOlderMessages` 在 `armScrollRestore` 前调用 `waitForScrollableEdge`（同步快路径 + 最多 600ms 的 rAF 等待）。覆盖 iOS 15（不支持 `overscroll-behavior`）与其它宿主；正常路径不增加一帧延迟。

验收：真机重跑后，报告中 `RS` 事件不应再出现 `scrollTop < 0`，且不应再有"写入延迟 > 200ms 才落地"的补偿。回归用例 `holds a page that lands mid-spring until the edge comes back` 在移除等待后必失败（实测 `scrollTop` 停在 -30，期望 50）。

### 7.2 第二个来源：懒加载行按估算高度挂载

修完 §7.1 后真机报告的 `prependPages` 为 0、没有任何 `RS`，但仍有一次 610px 的净视觉位移：

```
t=8775  scrollHeight 3776→3810 (+34)   跟踪行 top 202→251    scrollTop -29
t=8864  scrollHeight 3810→4421 (+611)  跟踪行 top 303→925    scrollTop -12   ← 净 610px
```

同帧 `MX` 报告视口内新增 1 个节点、高度 1290。`LazyMessageRow` 用 100px 估算占位（`ESTIMATED_ROW_HEIGHT_PX`），一行真实 1290px 的内容展开时误差 1190px；而补偿守卫当时是"测量与提交之间 `scrollTop` 变动超过 1px 就放弃"，惯性只走了 12px 就让它整段放弃。

改为：`layoutShift = 行屏幕位移 + scrollTop 变动`（滚动位移是布局位移的相反数，加回去即隔离出布局部分），`|layoutShift| > 24px` 才写回。理由有两条——纯滚动时 `layoutShift ≈ 0`，自然不写；大块内容展开时即便在惯性中也要纠正，因为 24px 以下不值得为它打断 iOS 的减速，610px 值得。

回归用例 `corrects a large layout shift even while the pane is coasting`（用真机数值 622/12）。把阈值调大让守卫失效时该用例失败（实测停在 2084，期望 2694）。

### 7.3 第三个来源：被挂载的行在视口上方

再上报的 `client-2026-11-04T03-40-11-383Z-57be9e08.json` 里，分页那次已经完美（`RS` 写入即落地、`WV` 位移 0、`AS1 stable`），但仍有 4 次 `VJ`，其中 3 次残差恰好 128px：

```
t=4208  scrollHeight +128  跟踪行 top 711→858  scrollTop -19   净 128px   MX: 上方插入 1 行
```

§7.2 的补偿看的是"被挂载的这一行自己"。这一行在**视口上方**，高度增加时它自己的 `top` 不动、只向下生长，于是 `layoutShift` 算出 0（只剩 -19 的滚动量，低于 24 门槛），而视口里所有内容被推下 128px。

改成测"视口内第一行"（`firstVisibleRow`，与诊断探针 `readNearestAnchor` 同一取法）：任何位置的行变高，只要它推动视口内容，视口内那一行的 `top` 就会如实变化，补偿因此不再依赖被改的行自己。

回归用例 `measures the visible row when the row being mounted sits above the viewport`：挂载行在 -800px 处、自身 `top` 恒定，可见行被推下 128px。改回"测自己"时该用例失败（停在 1000，期望 1128）。

## 8. 验收标准

沿用既有方案的定义（《长会话上滑阅读锚点漂移修复方案》§1.1、§8），本文只补充可程序判定的部分：

| 编号 | 标准 | 判定方式 |
| --- | --- | --- |
| V1 | 用户手势期间，视口不得被程序写入 | 采样 `touchActive` 与 `W` 事件的帧关系，写入数 = 0 |
| V2 | 非手势帧的阅读锚点位移 ≤ 8px | 每帧记录锚点行 `top`，取相邻帧差值 |
| V3 | 单帧 `scrollTop` 变化 > 500px 视为异常（除显式"回到最新"） | `F` 事件序列 |
| V4 | 同一次交互中，`scrollHeight` 相邻帧变化 > 500px 的次数 = 0（首屏除外） | `SH` 事件 + `F` 的 `scrollHeight` |
| V5 | 同一帧内对同一容器的 `scrollTop` 写入 ≤ 1 次 | 给每次写入打帧号与序号 |
| V6 | 任何补偿循环退出时，锚点残差 ≤ 8px；超过则必须记录退出原因与残差 | `AS1` 增加残差字段 |
| V7 | 加载全部完成后，锚点屏幕位置与点击前一致（±8px） | 点击前后各采样一次 |
| V8 | 打开会话落在底部；上滑到顶后分页不改变阅读位置 | 与 V2/V7 同法 |
