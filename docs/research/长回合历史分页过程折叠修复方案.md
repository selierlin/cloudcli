# 长回合历史分页过程折叠修复方案

> 状态：已实施，待手工验收
> 日期：2026-09-15
> 范围：聊天前端历史消息展示投影；不改 Provider、服务端分页协议或会话持久化
> 关联方案：`docs/research/当前正文焦点与执行过程折叠方案.md`

## 0. 结论

长回合的已完成历史会话，首屏即应折叠当前可见的执行过程；不能要求用户先上滑到 user 消息所在的历史页，才识别并折叠。

采用两项配套改动：

1. 已完成历史快照的过程成员投影不再依赖 `isUserScrolledUp`。
2. 当分页窗口从一个**已完成**回合中间开始、尚未加载该回合的 user 消息时，以**当前窗口最后一个普通 assistant 正文**建立临时“截断回合”过程组；加载到 user 锚点后无闪烁地升级为正式回合组。

不自动追溯加载历史来寻找 user 锚点。那会把一次打开长会话变成不受控的分页请求，首屏延迟和网络开销不可接受。

## 1. 问题与复现条件

`visibleMessages` 是消息列表尾部窗口。WorkBuddy 等 harness 的一个 user 回合可能包含数十条 thinking、工具调用和过程正文，超过初始窗口大小。

```text
真实历史：
user Q → thinking → 工具 × N → final text

初始可见窗口：
工具 × N 的后段 → final text
```

当前 `deriveExecutionProcessProjection` 只在可见 `type === 'user'` 消息后开始扫描回合。窗口开头没有 user 时，`turnStartIndex` 为 `null`，整个截断回合不会生成执行过程组。用户上滑到分页顶部后，旧消息被加载；直到 user 消息进入窗口，过程组才被重新计算并折叠。

这会造成两类不符合预期的行为：

1. 打开已完成的长 WorkBuddy 会话时，工具过程先平铺，占满屏幕。
2. `isUserScrolledUp` 被传入尾随过程收束判定；已完成历史会话若在上滑时重新计算，尾随安全工具可能从过程组退出，重新变成平铺行。

## 2. 目标与非目标

### 2.1 目标

| 目标 | 验收含义 |
| --- | --- |
| 首屏收缩 | 已完成长回合即使 user 锚点未加载，当前窗口的过程行默认折叠 |
| 不跳变 | 分页加载到 user 锚点后，过程组不先展开再收起；用户手动选择保持 |
| 历史稳定 | 用户上滑不改变已完成历史会话的过程成员集合 |
| 实时保守 | 活跃会话在用户上滑期间，`complete` 不强制收束新到的尾随过程 |
| 保真 | user、错误、拒绝、运行中工具、权限和提问卡片继续可见 |

### 2.2 非目标

- 不自动连续请求更早分页以定位 user 消息。
- 不将被截断窗口前未加载的消息伪装成已包含在摘要中。
- 不更改已有 Provider 消息归一化、分页接口和 `ChatMessage` 公共类型。
- 不改变用户主动展开/关闭执行过程的语义。

## 3. 方案比较

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 自动加载到 user 锚点 | 只产生正式回合 | 长回合可能触发多页请求、首屏慢、破坏按需加载 | 不采用 |
| 等用户上滑到顶部再折叠 | 无实现成本 | 正是当前缺陷，首屏体验最差 | 不采用 |
| 截断窗口临时组 + 正式组升级 | 首屏立即收缩；无额外请求；可平滑补全语义 | 需要定义临时组稳定 key 与升级规则 | 采用 |

## 4. 展示规则

### 4.1 完整回合

可见窗口内存在 user 起点时，继续使用现有规则：最后一条合格 assistant 正文是焦点；它之前的安全过程成员折叠；已完成历史回合中焦点之后的安全尾随项也可并入过程。

### 4.2 截断回合

当 `visibleMessages[0]` 不是可见 user 回合起点，且从窗口开始到第一个可见 user 起点之前存在合格 assistant 正文时，该前缀候选为一个**左侧截断回合**。只有该前缀可判定已完成时才生成临时组：整体不在处理状态（`!isProcessing`），或前缀之后已有可见 user 起点（表示当前 provider 正在处理的是后续回合）。

```text
窗口起点（未知的 earlier history）
├─ thinking / 工具 / preamble       → 可折叠成员
├─ final text                       → 当前焦点，保持可见
└─ 安全尾随工具（已完成历史）        → 可折叠成员
```

规则：

1. 仅处理窗口的左侧前缀；后续 user 回合仍按完整规则扫描，不能跨 user 合并。
2. 以该前缀最后一条 `isAssistantTextFocusCandidate` 为焦点。
3. 焦点前及已完成历史中的焦点后安全成员均可折叠。
4. 可见的 attention 项（错误、拒绝、停止、运行中工具、`AskUserQuestion`、权限、运行中/失败子代理）不进入成员集合；它们保持独立可见。截断组即使含有可见 attention 项，也默认折叠其安全成员，避免一项异常导致整个长历史过程平铺；摘要同时标示 attention。
5. 摘要文案使用“执行过程（较早记录未加载）”，不能声称已概括整个原始回合。
6. 若左侧前缀没有合格正文，或它是没有后续可见 user 起点的活跃回合，不生成临时组，保持平铺。这是信息不足或焦点会继续漂移时的保守策略。

### 4.3 分页升级

当加载更早历史后 user 起点进入窗口：

1. 重新派生为完整回合组；成员可以向上扩展到新加载的安全行。
2. 正式组以 user `turnKey` 作为 canonical disclosure key；临时组的用户选择通过 alias 迁移到该 canonical key，避免 `user_open` / `user_closed` 丢失。
3. 摘要由“较早记录未加载”切换为普通“执行过程”。
4. 仅新增的、更早的成员按当前组 disclosure 显示；不移动已经挂载的消息行，不重置工具或 thinking 内部状态。摘要行会随真实的 `firstMemberKey` 上移到新加载成员前；这是语义正确的位置变化，交由现有分页滚动锚点保持用户视口，不触发自动跟底。

## 5. 稳定身份与状态设计

现有 `turnKey` 继续表示完整回合的 user 锚点。完整回合继续以 `turnKey` 作为 canonical `disclosureKey`，不改动活跃回合中“新正文推进焦点但用户选择不丢失”的现有语义。仅截断回合使用临时身份：

```ts
type ExecutionProcessGroup = {
  turnKey?: string; // 仅完整回合存在，来自 user intrinsic key
  disclosureKey: string; // 完整回合为 turnKey；截断回合为临时 key
  disclosureAliases: string[]; // 正式组可读取的旧临时 key
  isWindowTruncated: boolean;
  memberKeys: Set<string>;
  firstMemberKey: string;
  hasAttention: boolean;
};

type ExecutionProcessProjection = {
  groups: Map<string, ExecutionProcessGroup>; // key 为 disclosureKey
  memberDisclosureKeys: Map<string, string>;
};
```

截断组使用 `truncated:${tailStableFocusKey}`。`tailStableFocusKey` 从可见窗口尾部为相同 intrinsic key 计数，因此向前 prepend 历史时不会改变已存在焦点的后缀。完整组同时产出同一焦点的截断 alias，使 Pane 能先查 canonical key、再查 alias 并将用户选择迁移到 canonical key。

`executionDisclosure` registry 按 `disclosureKey` 存储；完整回合 key 仍就是 `turnKey`，截断 key 仅在 user 锚点缺失时存在。用户操作始终写入 canonical key；首次读取正式组时，若 canonical key 无值则读取 alias 并迁移。

现有 `messageKeyMap` 也改为尾部消歧：从尾到头为相同 intrinsic key 编号。这样分页 prepend 不会改变已挂载尾部行的 React key；临时 disclosure key 与实际行 key 使用相同的尾部稳定规则。

## 6. 历史与实时的收束边界

过程成员的派生不能直接随 `isUserScrolledUp` 改变。应分成两类输入：

| 场景 | 尾随安全成员处理 |
| --- | --- |
| 首次载入或分页补全的已完成历史 | 始终纳入过程组，不受当前滚动位置影响 |
| 实时运行中 | 保持尾随项可见，等待后续正文或 `complete` |
| 实时 `complete` 到达且用户贴底 | 将尾随安全项收束进过程组 |
| 实时 `complete` 到达且用户上滑或组为 `user_open` | 保持当前布局，不强制收束 |

实现上应将“是否是已完成历史快照”与“本次实时 complete 是否允许收束”拆成独立布尔值/状态，不能复用 `isUserScrolledUp` 作为历史投影开关。

收束状态是**回合级**而非 session 级。推荐在 `ChatMessagesPane` 增加按 canonical disclosure key 存储的最小状态：

```ts
type ExecutionTailClosure = 'historical' | 'closed_live' | 'deferred_live';
type ExecutionTailClosureRegistry = Record<string, ExecutionTailClosure>;
```

- 初始 `isProcessing === false` 的会话视图中，每个已完成组按 `historical` 派生。
- provider 重新开始运行时，已有历史组保持自己的 `historical` 结论；只有最右侧活跃回合使用实时规则，不能以全局 `isProcessing` 让旧尾随成员重新平铺。
- 活跃回合完成时：贴底为该回合写入 `closed_live`；上滑或 `user_open` 为该回合写入 `deferred_live`。
- `deferred_live` 只限制所属回合；后续新 user 回合不受影响。新 user 回合开始时，较早 deferred 回合可在非侵入时机收束，但不得在用户仍阅读其附近时造成布局跳变。

状态必须按 session 重置，并只影响尾随成员；焦点前的历史过程成员仍由纯投影函数同步派生。

## 7. 实施步骤

1. 扩展 `executionProcess.ts`：提取“扫描一个片段”的纯函数，支持完整回合和左侧截断前缀；活跃且未闭合的截断前缀保守平铺。
2. 将 `messageKeyMap` 改为尾部消歧，并让投影输出 `memberDisclosureKeys`（替代 `memberTurnKeys`）、canonical `disclosureKey` 与 alias。
3. 调整 `ChatMessagesPane` registry：所有 toggle、registry 读取、摘要渲染、行反查均改为使用 `disclosureKey`；逐项替换现有 `group.turnKey` 的四处直接读写，不能让截断组的可选 `turnKey` 流入 UI 状态。
4. 将历史快照投影与实时 `complete` 尾随收束拆开；使用回合级 `ExecutionTailClosureRegistry`，移除 `isUserScrolledUp` 对历史成员集合的直接影响。
5. 为 `ExecutionProcessSummary` 增加截断历史文案及 i18n 资源。
6. 补齐单元/组件测试，并以长 WorkBuddy、Claude、Codex 已完成会话做人工验证。

## 8. 测试与验收

### 8.1 单元测试

1. 窗口从已完成长回合中间开始：工具 → final text，立即产生 `isWindowTruncated` 组，工具成员折叠。
2. 截断窗口含 thinking、过程正文、多个工具与 final text：只保留 final text 在组外。
3. 截断窗口含错误、权限、`AskUserQuestion`、运行中子代理：这些项不被隐藏。
4. 加载 user 起点后，临时组升级为完整组，alias 迁移后用户 disclosure 不变，成员向上扩展。
5. local command echo/stdout、compact summary 不成为截断组焦点。
6. 已完成历史在 `isUserScrolledUp` 从 false 变 true 时，成员集合不变。
7. 活跃且无后续可见 user 起点的截断前缀不生成组；实时尾随工具在贴底 `complete` 时收束，上滑或 `user_open` 时保持平铺。
8. 同一窗口同时存在截断组和完整组时，两者均可独立折叠与展开。
9. 前置分页插入同 intrinsic key 消息后，已存在焦点的尾部消歧 key、disclosure 状态与行 React key 保持稳定。

### 8.2 组件测试

1. 渲染截断历史时，摘要与焦点正文在 DOM 中，过程成员为 CSS 隐藏但仍保持挂载。
2. 用户展开临时组后加载更多历史，展开状态与既有工具详情状态保持；已挂载的 `ToolGroupContainer` / `MessageComponent` 不重挂载。
3. 历史回合上滑不会让已经折叠的尾随工具重新出现。
4. 实时完成且上滑时，不发生强制收束或滚动写入；旧历史回合不因新回合开始而重新平铺。

### 8.3 人工验收

- 打开工具数超过一页的已完成 WorkBuddy 对话：不滚动即可看到过程摘要和最终正文。
- 上滑加载更多：摘要可平滑升级，页面不闪动、不跳到尾部。
- 依次验证 Claude、Codex、WorkBuddy 的长工具回合。
- iOS H5：摘要点击面积、滚动和返回会话后刷新历史正常。

## 9. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 截断前缀误将不相关内容归组 | 仅处理窗口第一个 user 起点之前的连续前缀，且必须有焦点正文 |
| 历史补页后用户选择丢失 | disclosure key 固定使用焦点消息的消歧 key |
| 上滑时重新布局造成阅读跳动 | 已完成历史投影稳定；实时 deferred 状态不延迟自动收束 |
| attention 被隐藏 | 使用现有 attention 判定过滤成员，组件测试覆盖 |
| 额外复杂状态蔓延 | 状态仅存在于 ChatMessagesPane，派生逻辑仍保持纯函数 |

### WorkBuddy

> [!NOTE] 核实通过：§1 诊断与当前代码一致。`executionProcess.ts` 的扫描循环只在可见 user 起点后建回合（`turnStartIndex` 为 null 时 `processTurn` 直接返回），截断前缀确实不产组；`ChatMessagesPane.tsx:223` 的 `canCloseTail` 内联了 `!isUserScrolledUp`，上滑触发 useMemo 重算后尾随安全成员会退出过程组。两个缺陷均真实存在。

> [!WARNING] §4.2 截断组规则未限定"前缀回合已完成"。初始窗口 100 条（`useChatSessionState.ts:15`），活跃回合超过窗口时，实时会话同样从运行中回合中间开始；此时"前缀最后一条合格正文"会随后续流式正文到达而漂移，`disclosureKey` 跟着变（§5），用户 toggle 丢失、摘要行随焦点移动。建议：仅当前缀可判定完成时才生成截断组（窗口内存在后续可见 user 起点，或 `!isProcessing`）。

> [!WARNING] §5 用焦点消息 key 做身份，对完整回合是流式场景下的回归。现行 registry 按 user intrinsic key 存（`ChatMessagesPane.tsx:34-46`），回合内焦点从正文 A 移到正文 B 不影响身份；改为焦点 key 后，活跃回合每来一条新正文身份就变。建议混合策略：完整回合沿用 turnKey 身份，仅截断组用焦点 key，升级时把截断组记录的选择迁移（alias）到 turnKey 名下。

> [!WARNING] §5 要求"使用 `getMessageKey()` 的消歧结果"，但该消歧按窗口顺序的出现次数计数（`ChatMessagesPane.tsx:200-211`），`visibleMessages` 前端插入同 intrinsic key 的历史消息会把焦点消息的后缀平移（`k` 变 `k__1`），且恰好发生在"升级"这一刻：`disclosureKey` 变化导致用户选择丢失，React key 变化导致重挂载，直接违反 §4.3 第 4 条。§8.1 第 4 项测不到这类碰撞。建议 disclosureKey 的消歧改为从尾部计数（对前置分页稳定），或单独定义与位置无关的消歧规则。

> [!IMPORTANT] §6 的 `ExecutionTailClosure` 是 session 级单值，但收束是回合级事实。反例：用户上滑时 complete 到达，turn N 尾随进入 `deferred_live`；用户回底并发送下一条消息，turn N+1 贴底 complete。单值状态要么保持 deferred（turn N+1 尾巴不收），要么翻成 closed_live（turn N 被延迟收束、阅读中跳变）。建议 deferred 只作用于最新回合，新 user 回合开始时把更早回合的尾随一次性收束，并配合既有滚动补偿。

> [!IMPORTANT] §6 未定义"历史会话转实时"的边界。historical 会话里用户发送新消息后 `isProcessing=true`，现行实现会把之前所有已完成回合的尾随成员吐出（`executionProcess.ts:82` 的全局门控）。需明确 'historical' 是否粘住"运行开始前已完成的回合"，否则历史尾随会在发消息瞬间展开，与目标 3 冲突。

> [!TIP] §4.2 第 4 条与首屏收缩的交互：截断前缀含任一可见 attention 行（错误/拒绝在长回合中常见）时，`hasAttention` 使整组默认展开，首屏仍平铺，目标 1 落空。attention 行本就不进成员集合、折叠时保持可见，可考虑截断组默认折叠不受 hasAttention 影响，至少在 §4.2 写明预期行为。

> [!NOTE] §4.3 第 4 条与摘要行位置的矛盾：`ExecutionProcessSummary` 挂在 firstMemberKey 所在 Fragment（`ChatMessagesPane.tsx:359-361`、`419`），升级后 firstMemberKey 变为更早成员，摘要本身会从原位置卸载并重挂到新顶部。单帧提交无闪烁，但 user_open 时摘要可见位置上移，建议在 §4.3 明确说明。

### Claude

> [!IMPORTANT] §7 step 2「registry 从 turnKey 切到 disclosureKey」未穷尽组件侧所有按 turnKey 访问的调用点。当前 `ChatMessagesPane` 有 4 处直接读写 `group.turnKey`：`toggleExecutionProcess(turnKey, …)`（`ChatMessagesPane.tsx:249`）、`executionDisclosure[group.turnKey]`（`:233`、`:356-357`、`:413-414`）；另外行内通过 `executionProjection.memberTurnKeys.get(rowKey)` 反查所属组（`:350`、`:408`）。截断组的 `turnKey` 为 `undefined`（§5 类型定义为可选），任何漏改的 turnKey 读取会得到 undefined → `executionGroup` 查不到 → 该组永不折叠，§4.2 首屏收缩在真机直接落空。§5 的 `ExecutionProcessGroup` 类型还丢掉了组件实际依赖的 member→group 索引。建议 §7 step 2 显式列出上面 4 个读写点，同时把投影输出保留为一个 memberKey→disclosureKey 的 map（替代现有 `memberTurnKeys`），并补一个单测：同一窗口内同时存在一个截断组和一个完整组时，两个组都能被各自折叠。

> [!WARNING] §4.2 第 5 条的截断摘要文案只针对「焦点后无正文」的简单情形，未覆盖「焦点后仍挂着一条会漂移的实时正文」的中间态。当截断前缀恰好是一个运行中回合、且其 `final text` 之后还在持续到来新的正文时，该新正文会成为新的焦点（`isAssistantTextFocusCandidate` 取最后一条），`disclosureKey`（基于焦点消歧 key）随之改变，摘要文案/React Fragment key/已登记的展开选择一并漂移。这与 WorkBuddy 批注的实时前缀漂移同源，但 §4.2 第 6 条只兜底了「无焦点正文保持平铺」，没有兜底「焦点正文会漂移」的情形。建议：截断组生成时若前缀同时满足 `isProcessing` 且后续无可见 user 起点，则保守地平铺（同第 6 条），只在 `!isProcessing` 或前缀内已有完备 user/正文边界时才折叠，把「截断折叠」限定为确定的历史事实。

> [!TIP] §8.2 组件测试建议补一条针对「分页升级不重挂载」的直接断言。现有 §8.1/§8.2 只验证了 `disclosureKey` 不变与展开状态保持，但没有断言升级前后同一排消息的 DOM/组件实例被复用（§4.3 规则 4 的核心承诺）。可构造一个单元级测试：mock `getMessageKey` 对同 intrinsic key 返回随发生了前置插入而改变的消歧 key（`k`→`k__1`），断言尽管 `disclosureKey` 注册表查找可用事件对齐，已挂载的 `ToolGroupContainer`/`MessageComponent` 不因 key 变化而 remount。WorkBuddy 指出该碰撞现测不到，建议把这条从「人工留意」升级为显式组件测试，锁死 §4.3 第 4 条。

### 牵头结论

- 采纳：截断组仅用于可判定已完成的前缀；活跃且没有后续可见 user 起点的截断前缀保持平铺，避免焦点漂移和用户选择丢失。（来源：WorkBuddy、Claude）
- 采纳：完整回合继续以 user `turnKey` 作为 canonical disclosure identity；截断组使用尾部稳定焦点 key，并在升级时通过 alias 迁移用户选择。（来源：WorkBuddy）
- 采纳：消息行和临时 disclosure identity 都改用尾部消歧，确保向前分页 prepend 不改变已渲染尾部行的 key；补充不重挂载组件测试。（来源：WorkBuddy、Claude）
- 采纳：`ExecutionTailClosure` 改为按回合 registry；历史组的收束结论在后续新回合运行期间保持，不受全局 `isProcessing` 或上滑状态反向影响。（来源：WorkBuddy）
- 采纳：截断组中的 attention 项保持可见，但不阻止其他安全过程成员默认折叠。（来源：WorkBuddy）
- 采纳：将 Pane 中所有按 `turnKey` 读写 disclosure 的路径替换为 `disclosureKey` / `memberDisclosureKeys`，避免可选 user key 使截断组失效。（来源：Claude）
- 部分采纳：摘要在补页后会移动至真正的首个过程成员前；不承诺位置不变，但依赖现有分页锚点维持视口，并禁止自动跟底或行子树迁移。（来源：WorkBuddy）
