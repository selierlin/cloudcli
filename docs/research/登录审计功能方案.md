## 0. 结论先行

给 cloudcli 补上登录审计，一次成片，做四件事：

1. **新增 `auth_events` 表**（`server/modules/database/schema.ts`），记录 `login_success / login_failure / logout / register` 四类事件，带 `ip / user_agent / 时间 / 用户名`。
2. **在 auth service 的写路径落库**：成功登录/注册、**失败登录（重点）**、退出各写一条。失败尝试是当前唯一完全没落库、却又是攻击检测最关键的信号。
3. **读路径放 settings 模块**：受保护的 `GET /api/settings/auth-events`（分页 + 按类型过滤）。
4. **前端设置页新增独立「登录日志」Tab**（独立主 Tab，D12；三份 tab 清单 + 15 个 locale 共 6 处注册点），取数 **hook** 照抄 credentials 面板的写法（指 fetch 模式，非注册方式）。

三条关键承诺：

- **审计绝不阻断认证**：写库失败只 `console.error`，不改变登录/退出结果（对齐 `users.ts:70-80` `updateLastLogin` 的非致命模式）。
- **不重复造轮子**：既有 `[REQ]` 中间件（`index.ts:157-175`）继续负责 HTTP 层 IP+status；本表只补「**带用户名 + 带事件语义 + 可查询**」这一层。
- **明确「退出」的真实含义**：本方案记录的 `logout` 只证明「客户端清了 token」，**不证明服务端会话结束**（JWT 无状态、无吊销表，见 §1.2）。

### 1.2 缺口（这就是要做的事）

1. **失败登录完全无记录**：`login()` 在 `auth.service.ts:114-119` 直接抛 `AUTH_INVALID_CREDENTIALS`，**既不落库也不 console**。爆破尝试目前仅能从 `[REQ]` stdout 里看到一条 `401 POST /api/auth/login`（有 IP、无用户名、进程重启即丢）。
2. **成功登录只有粗粒度时间**：`users.last_login` 只记「最后一次成功」，无 IP/UA/失败次数。
3. **退出无任何记录，且前端根本不调接口**：`logout()`（`auth.service.ts:151-153`）是空实现；前端 `AuthContext.logout`（`AuthContext.tsx:374-378`）只 `clearSession()`，`api.ts:206-222` 里 **没有** `auth.logout`。
4. **无任何 audit 表**：全库无 `audit_log / login_history / event_log` 之类表。

### 1.3 一个必须写进文档的前提：`logout` 不是「会话结束」

JWT 无状态、7 天有效期、**无服务端 session / 无吊销表**（`auth.middleware.ts:106-115`）。因此：

- 前端点了退出 → 只有客户端清 token，**服务端签发的 JWT 在到期前仍可复用**。
- 关闭标签页 / token 自然过期 → **完全没有**退出事件。
- 结论：`logout` 事件只能标为「客户端主动退出」，**排查时不得当作「会话已结束」**。这是本方案对「退出审计」的定位边界（见 §4 决策 D3）。

## 3. 设计方案

### 3.1 事件模型与字段

新增表（挂进 `INIT_SCHEMA_SQL`，与 `API_KEYS_TABLE_SCHEMA_SQL` 并列声明于 `schema.ts`）：

```sql
CREATE TABLE IF NOT EXISTS auth_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    event_type TEXT NOT NULL,       -- 'login_success' | 'login_failure' | 'logout' | 'register'
    user_id INTEGER,                -- 成功/退出/注册为该用户；login_failure 恒为 NULL（不回填）
    username TEXT,                  -- 失败时记录「被尝试」的用户名（截断；见 §3.5）
    ip TEXT,                        -- req.ip（见 §3.5 可信度说明）
    user_agent TEXT,                -- 截断 512
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_auth_events_created_at ON auth_events(created_at);
CREATE INDEX IF NOT EXISTS idx_auth_events_type ON auth_events(event_type);
CREATE INDEX IF NOT EXISTS idx_auth_events_username ON auth_events(username);
```

> **第 4 轮修订（回应四审 T6.5）**：上方 DDL 原有一行 `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE SET NULL`，**已删除，以第 4 轮为准（不建 FK）**。理由：`ON DELETE SET NULL` 对恒为 NULL 的 `login_failure` 无意义，且 FK 会让建表隐式依赖「`PRAGMA foreign_keys` 在建表时已开」这一全局状态——等于把仓储与 `schema.ts` 的 pragma 状态绑死。§9.1 骨架实现时本就未建 FK，此处同步设计稿。

**事件语义**：

| event_type | 触发点 | user_id | username |
| --- | --- | --- | --- |
| `login_success` | `login()` 校验通过后 | 命中用户 | 命中用户 |
| `login_failure` | `login()` 抛 401 前 | **恒为 NULL**（不回填） | 尝试值（截断） |
| `register` | `register()` **commit 之后** | 新用户 | 新用户 |
| `logout` | `logout()` 被调用（**平台模式不产生**，见 D9） | 当前用户 | 当前用户 |

> Q3 已裁定：**不回填**——`login_failure` 的 `user_id` 恒为 NULL，避免审计表成为账号存在性的侧信道（**第 1 轮修订**，回应 Claude T1）。

### 3.2 采集点（写路径）

**分层选择：写进 service，不由 route 直接写库。** 理由：`$backend-module-standards` 要求 routes 薄、service 管逻辑；且 service 已经是「业务分支的唯一处」——失败抛异常也发生在这里，若在 route 捕获再补写会分散逻辑、且拿不到「用户名是否命中」的上下文。

改动（**第 1 轮修订**，回应 CodeBuddy T1 / W1 / W3、Claude W1）：

- `auth.service.ts`：`AuthDependencies` 增加 `audit: { record(event): void }`；新增 context 参数类型 **`AuthRequestContext = { ip?: string; userAgent?: string }`**（避免与前端 `AuthContext.tsx` 的 React context 同名，回应 CodeBuddy T1）。
  - `login(username, password, context?: AuthRequestContext)`：401 分支**先** `audit.record({ type:'login_failure', username, ip, userAgent })` 再 `throw`；成功分支在 `updateLastLogin` 旁写 `login_success`。context 设**可选**（默认 `{}`），以不破坏既有 `service.login('alice','wrong')` 两参调用与测试。
  - `register(username, password, context?)`：`register` 事件**必须在 `transaction.commit()` 之后**写入，与 `updateLastLogin`（`auth.service.ts:81`）同级——若写在 `commit()` 之前，后续异常走 `rollback()`（`:89`）会把审计行一起回滚且外部无感知（回应 CodeBuddy W1）。
  - `logout(user, context?)`：由空实现改为写 `logout`（签名新增 `user`）。`user` 沿用 `refreshSession`（`auth.service.ts:134-146`）现成的窄化样板；写 `user_id` 前**统一经 `numericUserId()`**（`:27-29`）转换，否则 better-sqlite3 收到 bigint 会抛错、又被硬约束静默吞掉（回应 CodeBuddy T1）。
- `auth.routes.ts`：`login` / `register` 的 body 解析后传 `{ ip: req.ip, userAgent: req.headers['user-agent'] }`；`logout` 传 `req.user` + context（该路由已有 `authenticateToken`，`auth.routes.ts:52`）。
- `auth.module.ts`：把 `authEventsDb.record` 绑进 service 依赖。
- **平台模式短路（回应 CodeBuddy N2）**：`IS_PLATFORM` 为真时（`server/shared/utils.ts:41`）无登录动作，**不写任何审计**；判定放在 service 内或 module 组合根注入的 no-op `audit` 上。前端**不在注册点做条件**，改为渲染处短路（见 §3.3 第 2 轮修订）。
- **退出路由不续期（第 2 轮新增，回应 CodeBuddy W6）**：`/api/auth/logout` 挂着 `authenticateToken`，其自动续期分支（`auth.middleware.ts:72-80`）会在响应塞 `X-Refreshed-Token`——退出请求**没有任何理由续期会话**。在 `auth.routes.ts` 的 logout handler 内 `res.removeHeader('X-Refreshed-Token')`（一行；或另起不复用续期分支的中间件）。

**硬约束 1（对应 G4）——审计绝不阻断认证**：`audit.record` 内部 try/catch，异常只 `console.error`，**绝不向上抛**；`login_failure` 的记录发生在 `throw AppError` **之前**，但记录失败不得吞掉原本的 401 语义。`record` 绝不做需要 await 的重活（纯同步插入）。

> **第 3 轮修订（回应 Claude T4 / CodeBuddy I4）——try/catch 必须覆盖 `getConnection()` 本身**：`getConnection()`（`connection.ts:109-127`）是**惰性单例**，首调会解析路径 / 建目录 / `migrateLegacyDatabase()` / `new Database()` / 建 `app_config`，**任一都可能抛**。若只把 try/catch 包住 SQL 插入、而 `getConnection()` 在其外，最靠前的失败点仍会漏到登录主路径，「绝不向上抛」在字面上成立、实现上不成立。照抄既有非致命范式 `updateLastLogin`（`users.ts:71-76`，把 `getConnection()` 放在 try 之内）：
> ```ts
> try { const db = getConnection(); db.prepare(...).run(...); }
> catch (err) { console.error('Failed to record auth event', { error: ... }); }
> ```

**硬约束 2（第 2 轮修订，回应 CodeBuddy C1→C2）——写入侧容量兜底**：`POST /api/auth/login` 是**公开无鉴权**端点（`index.ts:204`），D1 又明确不加限流，故 `login_failure` 是唯一一条「外部零成本可无限追加」的写路径（存储放大 / 磁盘 DoS）。`record` 对 `login_failure` 增加写入前容量闸：当 `auth_events` 行数达到上限（默认 10 万）时**停止写入 `login_failure`**（`login_success/logout/register` 照常），并只在**首次触顶时**打一条 console 告警。

> ⚠️ **以第 2 轮为准**：第 1 轮原文写「触顶判定结果在进程内缓存，只在首次 / 重启后各查一次 `COUNT(*)`」——这是**错**的：缓存的是「判定」而非「计数」，进程启动后第一次失败登录发生在表还小时（几乎必然），此后闸门永远认为未触顶，C1 的攻击面原封不动回来。
> **正确形态——缓存计数器，不缓存判定**：进程内维护模块级 `baseline`（启动、`pruneOlderThan` 之后读一次 `COUNT(*)`）与 `inserted`（每成功写一行 `login_failure` 递增），判定用 `baseline + inserted >= LIMIT`，**全程不再查库**。这既 O(1)、又永远准确。
> 量级校准：SQLite 无维护行数统计，`COUNT(*)` 在 10 万行表上是一次全表扫（约几十 ms）；若实现成「每次失败都查」，反而给爆破加了一条放大路径——所以「O(1) 计数器」是唯一同时正确且安全的形态。

> **第 3 轮修订（回应 CodeBuddy W7）——`baseline` 必须是惰性 `let`，不得在模块顶层求值**：D11 的「启动、prune 之后读一次 `COUNT(*)`」有两种落法，差别很大：**写法 A** `auth-events.ts` 顶层 `const baseline = countRows();` ❌；**写法 B** `baseline` 声明为 `let`，首次 `record` 调用时若为 `null` 则查一次 ✅。写法 A 为什么坏：模块求值发生在 **import 期**，而 `auth_events` 表要等 `initializeDatabase()`（`init-db.ts:8-14`）里的 `db.exec(INIT_SCHEMA_SQL)` 才建——顶层读表必然抛 `no such table: auth_events`；且要读表就得先 `getConnection()`（惰性首调含 `migrateLegacyDatabase`），把一次 **legacy 迁移 + 开库**提前到 `server/index.ts:25-31` 那批 import 期（其中 `auth.module.ts:18` 本就在 import 期开库，但那是幂等单例；顶层 `COUNT(*)` 是**一次真实查询**，会把「可恢复的未初始化」变成「启动期异常」）。**定稿形态：`baseline` 为 `let`、首次 `record` 惰性初始化；`pruneOlderThan` 仍由 `index.ts` 先跑（§3.4），基线因惰性而自然落在其后，无需额外 `init` 钩子、无需改 `index.ts` 调用序列。**

注意：这是**存储保护**，不是限流——请求照常返回 401，只是不再落库。触顶后闸门**粘滞**（运行期不自动恢复，直到重启/手动清理，见 §3.4 与 §7）。

### 3.3 读取路径与 UI

**分层选择：读端点放 settings 模块。** 理由：`/api/auth` 是**公开**挂载（`index.ts:204`，无 blanket auth），而 `/api/settings` 已整体在 `authenticateToken` 之后（`index.ts:231`），正是「用户在设置页看自己历史」的场景；放 auth 需逐路由加 `authenticateToken` 且把「会话生命周期」与「报表查询」混在一处。Q1 裁定：**settings**。

- `settings.service.ts`：新增 `listAuthEvents({ limit, offset, eventType, username, ip })`。
- `settings.routes.ts`：新增 `GET /api/settings/auth-events`。
- `settings.module.ts`：注入 `authEventsDb`。

返回体：`{ events: AuthEventRow[], total: number }`。**`total` 语义（第 2 轮修订，回应 CodeBuddy N3）**：`total` = **满足当前全部过滤条件**的行数（不是全表行数），分页器据此算页数。

查询参数与**校验归属**（**第 1 轮修订**，回应 CodeBuddy I1 / N1 与 Claude C1）：
- `limit`（默认 50）、`offset`（默认 0）：**必须在 service 内 clamp 下界**（`limit ∈ [1,200]`、`offset ≥ 0`）。只写「上限」不够：`limit=-1` 在 SQLite 里等于**不限行数**、一次拉全表；`offset=-1` 未定义；`limit=abc`→`NaN` 直接抛给 better-sqlite3。**`offset` 的上界还须有界**（第 4 轮修订，回应 N10）：原写 `Number.MAX_SAFE_INTEGER`，等于把「一次深分页」变成无界扫描 + 丢弃；现定为 100 000（UI 据 `total` 收敛页数，不会请求到这么深）。
- `eventType`：可选，**白名单**校验（仅 4 类）。
- `username` / `ip`：可选，等值过滤——让 G1 的「可按用户名/IP 查询」真正有查询路径，也让 `idx_auth_events_username` 名副其实。**两者都必须与写入侧截断对齐**（第 4 轮修订，回应 N10）：`username` ≤128、`ip` ≤64；否则用户输入一个超长值永远匹配不到，会被误读为「无记录」。
- 以上 clamp / 白名单**都在 `listAuthEvents` 内**；route 只透传原始 query（对齐 `settings.routes.ts:30-31` 的 `queryString()` 只做 trim 的既有惯例）。
- 索引取舍（第 2 轮修订，回应 CodeBuddy N3）：`ip` **不建索引**——`ip` / `event_type` 过滤在 ≤10 万行的有界表上扫描即可；过度建索引会给 `login_failure` 洪泛下的写入加放大（与 C2 的存储保护方向一致）。故 D6 措辞收敛为「best-effort 过滤」，不宣称索引命中。`username` 过滤是等值匹配、且 `login_failure.username` 截断到 128，故前端输入框须 `maxLength=128`（否则超长输入查不到会被误读为「无记录」）。

**排序（第 1 轮新增，回应 CodeBuddy W2）**：查询必须显式 `ORDER BY created_at DESC, id DESC`。否则 SQLite 在 `WHERE event_type=? LIMIT ? OFFSET ?` 下可能选 `idx_auth_events_type`，返回顺序变成「按类型分组、组内按 rowid」，翻页会出现**跨页重复 / 整段跳过**（`event_type` 仅 4 个取值，尤其明显）。`id DESC` 兜底同秒并列。

**退出请求的时序与副作用（第 2 轮修订，回应 CodeBuddy W4 + W5 + W6）**：`AuthContext.logout` **保持同步签名**（`logout: () => void`，`AuthContext.tsx:65`），改为**发后即忘**，绝不用 `await`。但「发后即忘」单靠 `.catch()` **不够**——必须同时**抑制该请求的认证副作用**：

```ts
const logout = useCallback(() => {
  // Fire-and-forget: the audit row is best-effort and must never delay the
  // local clear. The request must ALSO run without auth side effects — a late
  // 401 (X-Auth-Error) would pop a bogus "session expired" banner (W5), and a
  // late X-Refreshed-Token would write a live token back into localStorage,
  // silently re-logging-in the user the moment they reloaded (W6).
  void api.auth.logout().catch(() => undefined);
  clearSession();
}, [clearSession]);
```

实现要点（`api.auth.logout` 走**无副作用通道**）：

```ts
// api.ts — logout 专用：直接取 localStorage + 裸 fetch。
// 既不触发读取侧（getStoredAuthToken 的过期副作用），也不做响应侧处理。
// 第 3 轮修订，回应 CodeBuddy N9 —— 取代第 2 轮的 suppressAuthSideEffects 选项。
logout: () => {
  const token = localStorage.getItem('auth-token');
  return fetch('/api/auth/logout', {
    method: 'POST',
    headers: token ? { Authorization: `Bearer ${token}` } : {},
  });
},
```

> ⚠️ **以第 3 轮为准（回应 CodeBuddy N9）**：第 2 轮原文用 `suppressAuthSideEffects` 选项在 `authenticatedFetch` 内跳过两处**响应侧**副作用（`storeAuthToken` / `expireAuthSession`）。N9 指出这**挡不住读取侧**：`authenticatedFetch` 的**第一行**就是 `getStoredAuthToken()`（`api.ts:21`），它在 token 已过期时会先 `expireAuthSession()`（`authToken.ts:81-88`）→ 派发 `AUTH_SESSION_EXPIRED_EVENT` → `handleSessionExpired`（`AuthContext.tsx:198-201`）`setError`。即「token 已过期时点退出」这条路径，**即便完全抑制响应侧也仍会弹假横幅**，W5 在该分支上并未被覆盖，§6:289 的 DoD 会验收失败。故 logout 改为**完全绕过 `authenticatedFetch`**（选项①），读取侧与响应侧副作用一并消失。（N9 另指 `suppressAuthSideEffects` 混在 `ApiRequestOptions` 里会被 `fetch` 当未知字段——实测无害、TS 也不报错，属风格提示，本方案改用裸 fetch 后此关注点自然消解。）

- **W5（token 过期时点退出会弹「会话已过期」红条）**：`.catch()` 挡不住——它不是网络异常，是**副作用链**。**两处入口**：① **读取侧**（N9 补充，最易漏）`api.ts:21` `getStoredAuthToken()` 在 token 已过期时 `expireAuthSession()`；② **响应侧** `api.ts:45-47` 见 `X-Auth-Error` → `expireAuthSession()`（`authToken.ts:74-79`）。两者都派发 `AUTH_SESSION_EXPIRED_EVENT` → `handleSessionExpired`（`AuthContext.tsx:198-201`）`clearSession()` + `setError(sessionExpired)` → `LoginForm.tsx:90` 渲染成红色横幅。用户刚主动退出却看到「被踢下线」，正是 §1.3 想避免的语义误读。裸 fetch 通道把两处一并绕开。
- **W6（退出反而把新 token 写回 localStorage → 刷新后静默自动登录）**：`/api/auth/logout` 挂着 `authenticateToken`，token 过半衰期（3.5 天）时中间件 `res.setHeader('X-Refreshed-Token', newToken)`（`auth.middleware.ts:72-80`）；`api.ts:41-43` 见该头就 `storeAuthToken`（写 localStorage + 派发 `AUTH_TOKEN_REFRESHED_EVENT`）。时序：发请求（token 有效）→ `clearSession()` 删 token（`AuthContext.tsx:127`）→ 响应回来 → **token 被写回** → 下次刷新时 `checkAuthStatus` 读 `readStoredToken()`（`AuthContext.tsx:240`）→ `api.auth.user()` 成功 → **自动登录**。此链在改动前**不存在**（前端从不调 logout），是第 1 轮「发后即忘」把它变可达的。
- **两层处置（都做）**：① 前端 logout 走**裸 fetch 通道**（绕过 `authenticatedFetch`，既不存回 token、也不触发过期事件）；② 服务端 logout 路由 `res.removeHeader('X-Refreshed-Token')`（退出无理由续期，见 §3.2）。

理由（为何仍发后即忘、不改 async）：改 `async` 会连锁改动类型签名、`SidebarServerMenu.tsx:313` 调用点（floating promise → lint 报错）、`authTokenRefreshRemount.test.tsx:189` 时序断言；且「先 await 再清」会让慢网络下用户等一个往返才登出。发后即忘 + 无副作用通道则以上全不用动，且与「审计绝不阻断认证」一致。

### 3.4 保留策略（决策 D4：保留 90 天）

- 仓储提供 `pruneOlderThan(days): number`。
- 启动时调用一次：在 `server/index.ts` 完成 `initializeDatabase()` 之后调用 `authEventsDb.pruneOlderThan(90)`。单次删除，失败只告警。
- 不引入后台定时器（当前场景无需）。
- **已知限制（第 1 轮修订，回应 Claude N1）**：清理**只在启动时**发生——是「已知间隔行为」，不是实时策略。进程连续运行超过 90 天不重启，旧行会累积（上限由 §3.2 的写入侧容量闸兜住）。运维不应假设存在后台清理。本限制同步进 §7 风险表。
- **与容量闸的相互作用（第 2 轮新增，回应 CodeBuddy N4）**：启动顺序必须是 `pruneOlderThan(90)` **先于**读容量闸基线（§3.2），否则基线含已该删的旧行。运行期一旦触顶，`login_failure` 到下次重启前**永久停写**（prune 与基线都只在启动跑）；这对攻击场景正是想要的，但对「正常用户误触发」是静默丢数据——故告警文案须带「重启服务或手动清理后可恢复」，§7 补一行说明这个**粘滞**特性。

### 3.5 安全 / IP 可信度 / 输入截断

- **IP 可信度**：反代（home211 nginx）场景下 `trust proxy` 仅信任 `192.168.*` 的 `X-Forwarded-For`（`index.ts:93`），`req.ip` 为真实客户端；直连暴露时 `req.ip` 即 socket 地址，外部伪造的 XFF 被忽略。**文档与 UI 都应注明「IP 为来源地址，非本人身份证明」**。
- **输入截断**：`username` 截断至 128、`user_agent` 截断至 512，防超长/投毒内容撑大 DB 与 UI。
- **截断实现（定稿，以第 4 轮为准）**：按**码点**切，`Array.from(value).slice(0, N).join('')`；预算单位随之由「码元」改为「**码点**」（schema 列注释同步）。
  > **第 4 轮修订（回应四审 C3）**：上一段的「码元安全切片 `s.slice(0, N).replace(/[\uD800-\uDFFF]/g, '')`」**已作废**。`[\uD800-\uDFFF]` 覆盖**合法代理对的两半**，会把 emoji 与全部增补平面字符整段删除（作者独立复现：`'agent 😀 test'` → `'agent  test'`；纯 emoji 的 UA → 空串）。`Array.from` 按码点切，既不切断代理对、也不删内容，且仍能界定存储上界（一个码点最多 2 码元）。代价：调用方传入的**孤立代理**会被原样保留、由 better-sqlite3 存成 `U+FFFD`——对 UA/username 这类展示字段可接受，不再为它引入成对匹配正则。见 §5/§9.1/§9.6 与作者响应第 4 轮。
- **注入**：全部走 better-sqlite3 参数化，无拼接。
- **PII**：单用户自托管，IP+UA 属边界内数据；90 天保留即为最小化手段。

**② `server/modules/database/repositories/auth-events.ts`（新建）** — 照 `api-keys.ts` 的仓储风格（对象字面量、`getConnection()` 现取）：

```ts
import { getConnection } from '@/modules/database/connection.js';

export type AuthEventType = 'login_success' | 'login_failure' | 'logout' | 'register';
export type AuthEventInput = {
  type: AuthEventType;
  userId?: number | null;
  username?: string | null;
  ip?: string | null;
  userAgent?: string | null;
};
export type AuthEventRow = {
  id: number; event_type: AuthEventType; user_id: number | null;
  username: string | null; ip: string | null; user_agent: string | null; created_at: string;
};
export type AuthEventListParams = {
  limit: number; offset: number;
  eventType: AuthEventType | null; username: string | null; ip: string | null;
};

const MAX_LOGIN_FAILURE_ROWS = 100_000;
const USERNAME_MAX = 128;
const USER_AGENT_MAX = 512;
const IP_MAX = 64;

// Code-point truncation (D14, 以第 4 轮为准): slice the code-point array so a
// surrogate pair is never split. A code-unit slice + "drop lone surrogates"
// repair (the 3rd-round wording) deletes BOTH halves of every valid pair, i.e.
// every emoji and astral character — see C3.
const truncate = (value: string | null | undefined, max: number): string | null => {
  if (typeof value !== 'string') return null;
  return Array.from(value).slice(0, max).join('');
};

// Capacity gate (D7/D11): lazy baseline (W7 — must NOT be evaluated at import
// time) + inserted counter; the hot path never issues a COUNT(*).
let baseline: number | null = null;
let inserted = 0;
let capacityWarned = false;

const countAll = (): number =>
  (getConnection().prepare('SELECT COUNT(*) AS n FROM auth_events').get() as { n: number }).n;

export const authEventsDb = {
  /** Best-effort insert. Never throws — a logging failure must not break auth (G4/D13). */
  record(input: AuthEventInput): void {
    try {
      if (input.type === 'login_failure') {
        if (baseline === null) baseline = countAll(); // lazy → lands after startup prune (§3.4)
        if (baseline + inserted >= MAX_LOGIN_FAILURE_ROWS) {
          if (!capacityWarned) {
            capacityWarned = true;
            console.warn(
              `auth_events capacity (${MAX_LOGIN_FAILURE_ROWS}) reached — login_failure recording paused until restart/manual prune`,
            );
          }
          return;
        }
      }

      const db = getConnection();
      db.prepare(
        'INSERT INTO auth_events (event_type, user_id, username, ip, user_agent) VALUES (?, ?, ?, ?, ?)',
      ).run(
        input.type,
        input.userId ?? null,
        truncate(input.username, USERNAME_MAX),
        truncate(input.ip, IP_MAX),
        truncate(input.userAgent, USER_AGENT_MAX),
      );

      if (input.type === 'login_failure') inserted += 1;
    } catch (err) {
      console.error('Failed to record auth event', {
        error: err instanceof Error ? err.message : String(err),
      });
    }
  },

  /** Returns one page plus the total count under the SAME filters (N3). */
  list(params: AuthEventListParams): { events: AuthEventRow[]; total: number } {
    const db = getConnection();
    const where: string[] = [];
    const filters: unknown[] = [];
    if (params.eventType) { where.push('event_type = ?'); filters.push(params.eventType); }
    if (params.username) { where.push('username = ?'); filters.push(params.username); }
    if (params.ip) { where.push('ip = ?'); filters.push(params.ip); }
    const whereSql = where.length ? `WHERE ${where.join(' AND ')}` : '';

    const total = (
      db.prepare(`SELECT COUNT(*) AS n FROM auth_events ${whereSql}`).get(...filters) as { n: number }
    ).n;

    const events = db.prepare(
      `SELECT * FROM auth_events ${whereSql} ORDER BY created_at DESC, id DESC LIMIT ? OFFSET ?`,
    ).all(...filters, params.limit, params.offset) as AuthEventRow[];

    return { events, total };
  },

  /** Deletes rows older than `days`. Returns the number removed. Best-effort. */
  pruneOlderThan(days: number): number {
    const db = getConnection();
    return db.prepare("DELETE FROM auth_events WHERE created_at < datetime('now', ?)")
      .run(`-${days} days`).changes;
  },
};
```

> ⚠️ 关键点（三审）：`baseline` 是**模块级 `let`**，只在首次 `login_failure` 的 `record` 里初始化（W7/D11）——写成顶层 `const baseline = countAll()` 会在 import 期触发 `getConnection()`（含 legacy 迁移）且表未建抛 `no such table`。`try` 必须**包住 `getConnection()`**（D13/T4）。

> **落地实现说明（实现期）**：仓储改为 `createAuthEventsDb(maxLoginFailureRows = 100_000)` **工厂 + 单例 `authEventsDb`**。这样容量闸状态（`baseline`/`inserted`/`capacityWarned`）**按实例隔离**，测试可用 `createAuthEventsDb(3)` 的小上限覆盖闸门（§9.6 ⑲ 的「把 LIMIT 调小」），否则要写满 10 万行、且模块级状态会跨测试串味。语义与上面骨架一致，只是把闭包状态从模块级挪进了工厂。

```ts
const clampInt = (v: unknown, def: number, lo: number, hi: number): number => {

  return Number.isFinite(n) ? Math.min(hi, Math.max(lo, Math.trunc(n))) : def;
};

listAuthEvents(query: Record<string, unknown>) {
  const eventType = typeof query.eventType === 'string'
    && (AUTH_EVENT_TYPES as readonly string[]).includes(query.eventType)
    ? (query.eventType as AuthEventType) : null;
  const username = typeof query.username === 'string' && query.username.trim()
    ? query.username.trim().slice(0, 128) : null;         // 与写入侧截断一致（N3）
  const ip = typeof query.ip === 'string' && query.ip.trim()
    ? query.ip.trim().slice(0, 64) : null;                // 与写入侧 IP_MAX 一致（第 4 轮 N10）
  return dependencies.authEvents.list({
    limit: clampInt(query.limit, 50, 1, 200),
    // 有界上限（第 4 轮 N10）：MAX_SAFE_INTEGER 会让一次深分页变成无界扫描+丢弃。
    offset: clampInt(query.offset, 0, 0, 100_000),
    eventType, username, ip,
  });
}
```

> [!WARNING] W2 · **分页查询缺 `ORDER BY`，优化器可能走 `idx_auth_events_type` 导致跨页漏行/重复**（§3.3）
> `listAuthEvents({ limit, offset, eventType })` 描述里完全没有排序。SQLite 在 `WHERE event_type = ?` + `LIMIT ? OFFSET ?` 下大概率选 `idx_auth_events_type`，返回顺序变成「按 event_type 分组、组内按 rowid」——而 `event_type` 只有 1～4 个取值，所以**看起来像有时间序、实则在每个类型内分段**，翻页时同一条记录可能在第 1 页和第 2 页各出现一次，中间整段被跳过。三个索引（`created_at` / `type` / `username`）都会加剧这个不确定性。
> 修法一行：查询固定 `ORDER BY created_at DESC, id DESC`（`id` 兜底同秒并列）。建议在 §3.3 明确写出这条 ORDER BY，并作为 DoD 的分页验收前提。

> 方案写「改为先 `await api.auth.logout()` 再清本地」。当前 `logout` 是同步的（`AuthContext.tsx:374-378`），且类型签名是 `logout: () => void`（`:65`）。改成 await 后：
> - 类型须改 `() => void` → `() => Promise<void>`，`AuthContextValue` 与所有消费者跟着变；
> - `SidebarServerMenu.tsx:313` 的 `onClick={() => { setIsLogoutDialogOpen(false); logout(); }}` 会产生 **floating promise**，`npm run lint` 很可能报 `no-floating-promises`，需 `void logout()`；
> - `authTokenRefreshRemount.test.tsx:189` 的 `logout?.()` 是同步调用，改 async 后该测试的时序断言（紧接 `logout?.()` 就检查已登出）会失效，必须改成 await。

> ```ts
> const logout = useCallback(() => {
>   // JWT is stateless, so the request is fire-and-forget: the audit row it
>   // creates is best-effort and must never delay (or block) the local clear.
>   void api.auth.logout().catch(() => undefined);
>   clearSession();
> }, [clearSession]);
> ```
> 这样 `logout` 保持同步，签名、调用方、既有测试全不用动，与 §3.2「审计绝不阻断认证」的哲学也一致。

> [!IMPORTANT] I1 · **`limit` / `offset` 缺下界 clamp，`LIMIT -1` 在 SQLite 里等于「不限制」**（§3.3）

> [!CAUTION] C2 · **容量闸的「首次查一次 `COUNT(*)` 后永久缓存」把 D7 变成了纸面防护，攻击者只要等第一次查询过去就能灌到无限**（§3.2 硬约束 2 + D7）
> 原文：「触顶判定结果在进程内缓存，只在首次 / 重启后各查一次 `COUNT(*)`」。
> 这里的措辞把两件事混为一谈了。若实现为「**启动后第一次写 `login_failure` 时查一次 `COUNT(*)`，结果（未触顶）缓存起来不再查**」——这是最自然的读法，也是把开销压到 O(1) 的字面做法——那么进程启动后只要**第一次失败登录发生在表还很小的时候**（几乎必然如此），此后闸门永远认为「未触顶」，攻击者可以在这之后无限追加行。**C1 描述的攻击面原封不动地回来了**，只是多了一次无用的 `COUNT(*)`。
> 正确形态是**缓存计数器而非缓存判定**：进程内维护一个 `insertedCount`，启动时查一次 `COUNT(*)` 作基线，之后每写一行 `login_failure` 就 `insertedCount++`，用 `baseline + insertedCount` 与阈值比较。这样既是 O(1)（无查询）、又永远准确。
> 顺带一个量级校准：`COUNT(*)` 在 10 万行表上是一次全表扫（SQLite 无维护行数统计），单次约几十 ms。若真按「每次都查」实现，**每次失败登录都要付这个成本**——反而给爆破加了一条放大路径。所以「O(1) 计数器」不只是省一次查询，它是唯一同时正确且安全的形态。
> 建议改写为：「启动时读一次 `COUNT(*)` 作基线存入模块级 `loginFailureBaseline`；此后每成功写入一行 `login_failure` 递增内存计数，判定用 `baseline + counter >= LIMIT`，全程不查库」。

> [!WARNING] W5 · **`logout` 的「发后即忘」会与 `authenticatedFetch` 的 `X-Auth-Error` 副作用撞车：token 已过期时点退出，登录页会弹一条「会话已过期」红条**（§3.3 时序骨架）
> 骨架本身（token 在调用瞬间同步读取、`void` 发后即忘）我已核过成立。但漏了一条 `authenticatedFetch` 的副作用链（`src/shared/api.ts:38-42`）：
> ```ts
> if (response.headers.get('X-Auth-Error')) { expireAuthSession(); }
> ```
> `expireAuthSession()` 不只是清 token，它还 `window.dispatchEvent(new Event(AUTH_SESSION_EXPIRED_EVENT))`（`authToken.ts:74-79`），而 `AuthContext` 监听了这个事件 → `clearSession()` + **`setError(t(AUTH_SESSION_EXPIRED_MESSAGE))`**（`AuthContext.tsx:198-201`）。这个 `error` 最终由 `LoginForm.tsx:90` 的 `AuthErrorAlert` 渲染成一条红色横幅。
> 于是时序变成：用户 token 已过期（或即将过期）→ 点「退出」→ `clearSession()` 正常登出 → 异步的 logout 请求回来带 `X-Auth-Error: session-expired` → **登录页凭空多一条「会话已过期」错误**。用户刚主动退出，却看到像被踢下线的提示——这正好是 §1.3 一直想避免的「logout 语义被误读」，只是方向反了。
> `.catch(() => undefined)` 挡不住这条路径（它不是网络异常，是正常 401 响应里的 header副作用）。
> 建议二选一并写进 §3.3：①在 logout 请求上加一个「抑制 auth 副作用」的选项（如 `authenticatedFetch(url, { suppressAuthSideEffects: true })`，内部跳过 `X-Refreshed-Token` 存回与 `X-Auth-Error` 派发）；②或logout 后显式 `setError(null)`。倾向①——它顺带避免另一条隐患：**`X-Refreshed-Token` 会把新 token 写回 localStorage**（`api.ts:39-41` → `storeAuthToken`），即用户点了退出之后，那次 in-flight 请求可能又把 token 存回来（详见 W6）。

> [!WARNING] W6 · **`POST /api/auth/logout` 挂着 `authenticateToken`，其自动续期分支会在响应里塞 `X-Refreshed-Token`——「退出」可能反而把新 token 写回 localStorage**（§3.2 logout 事件 + §3.3 时序骨架）
> 这是我 W5 的近邻，但严重一级，且**第 1 轮修订把它变得可达了**。
> `auth.middleware.ts:72-80`：token 过了半衰期（`now > iat + (exp-iat)/2`，7 天有效期即3.5 天）时，中间件会 `generateToken(user)` 并 `res.setHeader('X-Refreshed-Token', newToken)`——**这个中间件挂在 `/api/auth/logout` 上**（`auth.routes.ts:52`）。而 `authenticatedFetch` 见到该头就 `storeAuthToken(refreshedToken)`（`api.ts:39-41`），写进 localStorage 并派发 `AUTH_TOKEN_REFRESHED_EVENT`。
> 配合 §3.3 的骨架，实际时序是：
> 1. `api.auth.logout()` 发起（此刻 header 里的 token 有效，服务端会正常处理）
> 2. `clearSession()` 同步执行 → `clearStoredToken()` 把 localStorage 的 token 删掉（`AuthContext.tsx:101-103`）
> 3. 网络往返返回，响应头带 `X-Refreshed-Token` → **`storeAuthToken` 把 token 写回 localStorage**，`handleTokenRefreshed` 再`setToken(nextToken)`
> 结果：**用户点了退出，token 却回来了**。`user` state 是 null所以界面停在登录页看起来正常，但下次刷新/重开标签页时 `checkAuthStatus` 走 `readStoredToken()` → 拿到这个残留 token → `api.auth.user()` 成功 → **静默自动登录**。

> `username` 截断 128、`user_agent` 截断 512 用 `slice(0, N)` 在 JS 里是**按 UTF-16 码元**切。若边界恰好落在多字节字符中间（UA 里很常见），会产出孤立代理对——better-sqlite3 绑定这种字符串可能抛或存成替换符，反而触碰 §3.2 的「record 不得抛」。建议用「截断到 ≤N 码元前先回退到合法码元边界」的助手（或按 `Buffer` 字节切），成本一行。属收尾级，与 CodeBuddy 二审 N3 的 `maxLength` 属同一关注域，此处补的是**后端写入侧**那一半。

> [!NOTE] N8 · **修正 Claude N7 的结论：better-sqlite3 绑定孤立代理对不抛，N7 描述的风险路径不存在**（§3.5 / 对 Claude 三审 N7）
> N7 说「可能抛**或**存成替换符，反而触碰 §3.2 的 record 不得抛」。我实测了后者，前者**不成立**：
> ```
> $ node -e "…db.prepare('INSERT INTO t VALUES (?)').run('a'.repeat(127)+'\uD83D')…"
> insert OK, stored len: 130
> tail: [ 'fffd', 'fffd', 'fffd' ]   含 U+FFFD: true   等值查询命中: 1
> ```
> 结论：孤立代理对被better-sqlite3 **静默替换成 U+FFFD**（3 个替换符 = 6 字节），**不抛异常**。所以 N7 担心的「触碰硬约束 1（record 不得抛）」这条风险路径是错的，按它去设计「防抛」逻辑属于为不存在的问题写代码。
> 但N7 的**建议本身仍然值得做**，理由变了：截断会产生 U+FFFD 污染，**使「截断到 128」这个不变量在存储层失效**——上例输入 128 码元，存储后length 变成 130。也就是说 `username` 列里可能存在超过 128 码元的行，而 §3.5 把「截断至 128」当作防撑大 DB/UI 的手段，**这个保证实际上不成立**。UA 截断 512 同理。
> 修正后的建议（比 N7 更轻）：用码元安全切片 `s.slice(0, N).replace(/[\uD800-\uDFFF]/g, '')` 或回退到合法边界（`Array.from(s).slice(0,N).join('')`）。前者一行、且顺带清掉**字符串内部**可能存在的其他孤立代理（不只是末尾切出来的）。这样「≤128 码元」的不变量才真的成立。等级从N7 的「避免抛错」降为「保证不变量 + 数据干净」，仍建议做，但**不要按「防抛」的紧迫度对待**。

> [!NOTE] N9 · **`suppressAuthSideEffects` 若挂在 `ApiRequestOptions` 上会被 `fetch` 当成未知字段，但更重要的是：它在 logout 场景下并非唯一需要抑制的副作用**（§3.3 实现要点 / §5 第 20 项）

> const truncate = (value: string | null | undefined, max: number): string | null => {
>   if (typeof value !== 'string') return null;
>   return value.slice(0, max).replace(/[\uD800-\uDFFF]/g, '');
> };
> ```
> `[\uD800-\uDFFF]` 是**整个代理项码元区间**，它匹配的是**代理对的两半**——所以一个合法 emoji（`😀` = `\uD83D\uDE00`）两个码元**都被删掉**，不是只删「孤立的那个」。我第 3 轮 N8 写「`replace(/[\uD800-\uDFFF]/g, '')` 或回退到合法边界」时，把这两者当成了等价选项，**前者是错的**，作者照抄了。实测：
> ```
> 'agent 😀 test'                        -> 'agent  test'      ← emoji 整段消失
> 'Mozilla/5.0 (iPhone…) 😀 Safari/…'   -> '…(iPhone…)  Safari/…'  ← 还留下双空格
> '中文测试 😀'                          -> '中文测试 '
> ```
> 影响不止于 emoji：**所有增补平面字符**（𝕳、𠜎、以及 CJK 扩展 B–G 区）在 UA / username 里都会被抹掉。对审计表的后果是「UA 被静默篡改、看不出原样」，这恰好落在 §3.5「输入截断：防超长/投毒内容撑大DB 与 UI」的语义里——**截断变成了内容破坏**。
> 更麻烦的是它与 §9.6 ⑲ 的验收用例**互相矛盾**：⑲ 断言「喂 `'a'.repeat(127)+'\uD83D'` → 存储码元 ≤128、无 `U+FFFD`」。这条用例只测「边界切断」，恰好是错误正则**唯一能通过**的场景；而它测不出「中间有 emoji 被误删」。所以骨架+验收**一起**把这个 bug 锁住了。
> 正确实现（按**码点**切，而不是按码元切后再删）：
> ```ts
> const truncate = (value: string | null | undefined, max: number): string | null => {
>   if (typeof value !== 'string') return null;
>   return Array.from(value).slice(0, max).join('');   // never splits a surrogate pair
> };
> ```
> 实测对比：
> ```
> 场景              现骨架(bad)                Array.from(good)
> 'agent 😀 test'   'agent  test'              'agent 😀 test'  ✅
> '中文测试 😀'      '中文测试 '                 '中文测试 😀'     ✅
> 'a'*127+'\uD83D'  127 码元（吞掉半个 emoji）   128 码元（保留完整代理对尾部）  ✅
> ```
> 注意 `good` 在边界切断场景下会留下**完整的 `\uD83D`（作为一个码点）**——这正确吗？`Array.from` 按码点切，`'a'.repeat(127)+'\uD83D'` 这个输入里 `\uD83D` 本身就是**孤立**代理（没有配对的低代理），`Array.from` 会把它当作一个码点保留。better-sqlite3 对孤立代理仍会存成 `U+FFFD`（N8 已实测）。要彻底避免，需要在切片后再删孤立代理——但**只能删孤立的那一半**，正则应是`/(?:[^\uD800-\uDBFF]|^)[\uDC00-\uDFFF]/` 之类的成对匹配，复杂度陡增。
> **我的建议是：到此为止，不要加复杂正则。** 理由：`Array.from` 已消除「切出半个代理」这个**主要**问题（也是 §9.6 ⑲ 关心的那半）；而 UA 里出现孤立代理是攻击者刻意构造的输入，让它存成 `U+FFFD` 完全可接受——它本来就只是「某个 UA 字符串」的展示，**不值得为它引入易错的正则**。这一条请作者在 §9.1 定稿时直接采用 `Array.from` 版本，并在 §9.6 ⑲ 的用例里**补一条「含 emoji 的 UA 原样保留」**（例如断言 `'agent 😀 test'` 截断后仍含 `😀`），否则同类回归还会再犯。

> [!WARNING] W8 · **§9.6 ⑲ 的「import 期不触发 DB」用例在当前结构下无法成立——barrel 会把 `connection.ts` 求值进来，而 `auth.module.ts:18` 早就调过 `getConnection()`**（§9.6 ⑲第6 条 / §9.1 ②）
> §9.6 要求「单独 import 仓储后 `getConnection()` 未被调用」。这条**方向正确**（正是 W7 要防的），但在当前代码结构下它很可能**测不出东西**：
> - `auth-events.ts` 用的是 `import { getConnection } from '@/modules/database/connection.js'`——这**不触发** `getConnection()`（只是绑定函数），✅ 这半没问题。
> - 但集成测试若从 barrel `import { authEventsDb } from '@/modules/database/index.js'` 进来（更符合仓库惯例），barrel 会连带求值 `init-db.js`、`connection.js` 以及**其余全部仓储**；`connection.js` 顶层只有函数声明（✅），但 `app-config.ts` 等仓储文件里若有顶层 `getConnection()` 调用就会连带触发。我核过 `api-keys.ts`：只有 `import`，无顶层调用（✅）；`auth.module.ts:18` 的 `getConnection()` 确实在 import 期执行，但那是 **auth 模块**、不是 database barrel——若测试文件同时 import 了 `auth.module.ts`（集成测试常会），**这条断言必然失败**。
> 建议把用例改写成**可判定的形式**：「import `@/modules/database/repositories/auth-events.js`（**具体路径，不走 barrel**）后，模块内`baseline === null`」——直接断言那个惰性状态未被初始化，而不是断言一个跨模块的全局副作用。这样既守住 W7 的意图，又不会因测试的 import 图谱变化而误报。若一定要断言「无 DB 访问」，得用 `require.cache` / spy `getConnection` 之类的手段，成本明显更高，收益不匹配。

> [!IMPORTANT] I5 · **§9.2 ⑦ 的两条服务测试断言与 §3.2 的「先记后抛」不可区分；且 `record` 抛错的用例没给出注入方式**（§9.2 ⑦ / §9.6 验收映射）
> §9.7 把「`record` 抛库错、`getConnection()` 抛 → 结果不变」映射到「⑦ 服务测试 + ⑲ 集成测试」，但 §9.2 ⑦ 的写法是「`audit.record` 抛错 → `login` 仍返回 401 / `register` 仍成功」。这里有个**测试设计问题**：`createDependencies()`（`:10-28`）里补的是 `audit: { record: () => undefined }`——一个 no-op。要测「record 抛错」，必须让这个 stub **可注入抛错**，即 `createDependencies` 的 override 要能替换 `audit`（它已经有 `overrides: Partial<AuthDependencies>` 参数，✅ 技术上可行），但文档没写这条测试**怎么构造**。
> 更要紧的是「先记后抛」这条断言的写法：若只断言「抛出的错误是 401」，那**无论 record 有没有被调用都通过**。真正的意图是验证**顺序**（record 在 throw 之前发生）。可行的写法是让 `record` 把调用记进一个数组，再断言数组内容 + 捕获到的 `AppError`；或者用一个「record 里同步抛」的 stub，断言最终抛出的是 401 而**不是** record 的错误——后者其实同时覆盖了「record 抛错不影响语义」这条。
> 建议 §9.2 ⑦ 把两条断言写成可执行形态（spies + 顺序断言），并明确 `createDependencies` 的 `audit` 可被 override。否则这两条最关键的 DoD 会退化成「跑过即通过」的空测试。

> [!NOTE] N10 · **§9.3 的 `clampInt` 有一处边界取值可疑；`ip` 过滤未做与写入侧一致的长度对齐**（§9.3 ⑧）
> 1. `offset` 用 `clampInt(query.offset, 0, 0, Number.MAX_SAFE_INTEGER)`。`MAX_SAFE_INTEGER` 作为 hi 传给 `Math.min(hi, Math.max(0, Math.trunc(n)))` 没问题，但 better-sqlite3 把这个值绑进 `LIMIT ?/OFFSET ?` 时，实际会生成 `OFFSET 9007199254740991`，配合 `ORDER BY` 需要扫描并丢弃这么多行——**一次 `?tab=loginLog&offset=999999999` 就能把单进程 SQLite 卡住**（全表排序 + 丢弃）。10 万行规模下大约是百毫秒级、可接受，但**这不是 clamp 的本意**（clamp 是防`NaN`/负数，不是防深分页）。建议给 `offset` 一个业务上限（如 `10_000`），并在 §3.3 补一句「深分页靠 `total` 收敛页数，不提供无限翻页」。
> 2. `username` 过滤做了 `.slice(0, 128)` 与写入侧对齐（✅ 好），但 **`ip` 过滤没有**——写入侧 `IP_MAX = 64` 会截断，而过滤侧不限长。用户粘贴一个超长 IP 查不到，会误判「无记录」。补一个 `.slice(0, 64)` 即可（成本一行）。
