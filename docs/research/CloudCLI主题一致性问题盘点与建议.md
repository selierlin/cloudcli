契约没规定、但影响面各异的三个族，**三个族的分布并不一致**（`[订正]` 原先写作「前四套与后六套不是一个口径」的三行表，把 `frost-50` 一行误记为「dracula 组也 ✓」；实测该组**不声明 frost**）：

|---|---|---|---|
| `cc-polar` / `cc-catppuccin` / `cc-onedark` / `cc-onedark-vivid` | ✗ | ✗ | ✗ |
| `cc-islands` | ✗ | ✓ | ✓ |
| `cc-dracula` / `cc-gruvbox` / `cc-kanagawa` / `cc-tokyo-night` | ✓ | **✗** | ✓ |

⇒ 逐族清点：**`gray` 4 套 / `frost-50` 仅 1 套 / `danger-800` 5 套**（复现命令见附录 A；`--palette-frost-50` 全文件仅 `src/index.css:79` 基座与 `:2113` `cc-islands` 两处声明）。「三代分化」这一层叙事**不成立**——真实形态是**逐族不同**，而非「按主题套数分三档」。

**这三个族的实际影响面差得很远，必须拆开看**（本文净增量）：

| 族 | 消费者 | 影响的界面 | 可见性（**推断**，依据在右） |
|---|---|---|---|
| `--palette-gray-*` | 经 `--n-gray-*` 别名层，**1287 处**字面工具类 | 滚动条、Tooltip 深色气泡、侧边栏按钮底/hover、编辑器顶部文件名与路径、各处次级文字 | `[订正]` **升级为真机读数，且须分档**：`cc-gruvbox`（暖棕，色相 ~35）vs `cc-catppuccin`（冷灰，色相 ~210~220）实测 **`--n-gray-700` ΔE76 ≈ 21、`:900` ≈ 18、`:50` 仅 ≈ 1.2** ⇒ **深档（tooltip／气泡实际消费的档）可见、浅档几乎无差**。「两套 A/B 看同一 tooltip 能分辨」成立，但**不可表述为「整族可见」** |
| `--palette-frost-50` | `--primary-foreground`、`--destructive-foreground`（`src/index.css:217 / 225`） | **主按钮与危险按钮上的文字色** | **实际不可见**（ΔE76 ≈ **2.2**，且落在**小面积文字**上）。基色 `210 40% 98%` vs `cc-islands` 的纯白 `0 0% 100%` |
| `--palette-danger-800` | `--destructive` 的**深色**填充（`src/index.css:502`） | 深色外观下的危险按钮底色 | **深色下可见**。基色是通用暗红，`cc-dracula` 等偏主题红 |

**关键点** `[订正]`：`gray` 这一族的规则**不是缺失，而是写在另一份文档里、且运作层已闭合为「可选」**——
`CloudCLI用户主题升内置方案.md` §3.1 把 gray 从「所有主题禁移」改成「**仅 `accent` 禁移**」，并在「显式约定」里写：**`full` 主题若动兼容层某一族，必须把那一族染完整 11 档**；§4.1「影响面」段更明写 `compat` **不是「必须动」、只是「可以动」**（理由：列为必移会让既有 5 套当场全红），§3.1 的结论句也是「`full` 主题**获得了**收掉接缝的**能力**」——**能力授予，不是义务**。

> 原文此处判「**留下一个未闭合的问题：`full` 是『可以』还是『应当』收掉接缝？**」——审阅指出**定性过重**：被引的 §3.1「证据二」（*"这些站点就是 app 自己的 chrome。一枚写着「完整」的徽标本来就该覆盖它们……"*）在原文语境里是**反对禁移的论据**，其落点句正是「获得了……能力」；「可以 / 应当」在 §4.1 已闭合为「可以」。留下的至多是**论证语气上的张力**，不是「实施口径未知」。**本文订正为：不对『可以 vs 应当』重开裁定。**

⇒ **但审阅另挖出一处真正的缺口**：那条「若染须整族 11 档」的约定**目前只是注释承诺，没有任何测试执行它**——`theme-overlays.spec.ts:477-513` 的 `beyondReach` 只拦「移出 `coverage` 可达范围」的令牌，**不会**在「只染了 11 档里的 3 档」时报错。所以「契约没规定」的准确表述是：**`compat` 不是 `full` 的必移面；且『一旦染就须整族』这一条件承诺不设防**。本文新增的建议见 §5.2。

## 4. 用户主题（八套自由式 CSS）

> 前置 `[订正]`：**用户 `.css` 主题没有覆盖「本文所述令牌族 / 页面配对 / 对比度」的守卫**（`theme-overlays.spec.ts:58` 与 `contrast.spec.ts:40` 都只筛 `BUILTIN_THEMES.filter(appearance === 'system')`，`code-block-surface.spec.ts:33-36` 也不遍历用户 CSS）；且 `.css` 走 `userThemeStyles.ts:201-210` **原样注入、不经令牌白名单**。所以下面每一条都是**静默**的。
> **但原文「一个守卫都没有」过宽**（审阅指出）：用户 CSS 另有**文件级 ＋ 注入级**的真实保护——`server/modules/themes/services/theme-files.service.ts:474-476` 拒绝含 `@import` 的文件，`tests/theme-tokens/user-theme-style.spec.ts:33-51` 实测注入生效与替换生命周期。本文要说的是**缺少颜色一致性断言**，不是「文件安全与注入路径均无校验」。
> 另一前置：`--code-block-bg`、`--editor-*`、`--n-gray-*` **都在白名单里**（`userThemeTokens.ts:179 / 226 / 219`）——即使将来改走 `.json` 主题也设得进去。**所以这些是「没写」，不是「不能写」。**

### 4.1 B-1：`console` / `tui` 在**浅色半**接管了编辑器页，却没写代码块底 `[订正]`

| 主题 | `--editor-*` 声明数 | 浅色半 / 深色半 | `--code-block-bg` | 后果 |
|---|---|---|---|---|
| `console` | **26** | **26 / 0** | **0** | **浅色**编辑器页绿纸 `hsl(150 15% 97%)`（`console.css:154`），代码块却是基座白 `var(--palette-white)` |
| `tui` | **26** | **26 / 0** | **0** | 同上（钢蓝纸 `hsl(220 15% 97%)`） |

> 复现：`--editor-*` 的 26 条全部落在 `:root:not(.dark)`（`console.css:49` 起）；`awk '/^:root\.dark/,0' console.css | grep -c -- '--editor-'` → **0**（tui 同，深色块自 `tui.css:143` 起）。**深色外观下两族都回落基座**，而基座「块 == 页」天然成立（见 §4.2）——**深色下不存在偏离**。
> （原文表格记「27 槽」系把 `console.css:39` 的注释行一并计入 `grep -c`；实际声明 26 条。）

契约里有一条不变量（内置侧由 `tests/theme-tokens/code-block-surface.spec.ts` 强制）：**代码块底板 == 该外观的编辑器页**。
`console` / `tui` 在**浅色半**移动了编辑器页却没动代码块 ⇒ **浅色下「块 ≠ 页」**。

这与 `CloudCLI用户主题补齐语法板与代码块底方案.md` §0.9 记录的那条偏离**是同一件事**——四套配色主题当时**明确裁定「有意接受 ＋ 记账」**（§8 决策 8 取 (ii)）；但那一次只覆盖了那四套，**`console.css` 被整份豁免出该方案**（同文档 §2.2），因此**这条偏离在 console/tui 上从未被记账**。

**可见性** `[订正 ×2]`：**只在浅色**——真机读数（2026-10-06）console 编辑器页 = 代码块 `rgb(246,248,247)` vs `rgb(255,255,255)`（**ΔE76 ≈ 2.6**）、tui ≈ 2.9；**深色**两者同为 `rgb(40,44,52)`（=`#282c34`，**块 == 页坐实**）。
> ⚠️ **不要用 `frost-50` 的「ΔE 2.2 不可见」来给这条背书**：frost 落在**小面积按钮文字**上，这里落在**直接贴边的大面积容器**上——人眼对色差的敏感度随**面积 × 相邻性**上升，同一 ΔE 在大底色上**更**易被感知。⇒ 正确表述是「**边缘量级、A/B 直接对比时可能可感知**（推断，未做主观测试）」，而非「轻微／不可见」。
> 原文「深色下编辑器是 console 自己的深绿」「色相从绿跳到青灰，**尤其深色**」**证伪**（深色半无任何 `--editor-*` 声明）。

### 4.2 B-2：其余 6 套 `--code-block-bg` 与 `--editor-*` 一律不写

| 主题 | `--editor-*` | `--code-block-bg` |
|---|---|---|
| `liquid-glass` / `neubrutalism` / `macos-native` / `win9x` / `clay` / `fluent` | 0 | 0 |

此时**基座自成一致**：`--editor-bg` 与 `--code-block-bg` 在基座同值（浅色都指向 `--palette-white`；深色 `#282c34` 与 `220 13% 18%` 是同一色的两种写法，逐通道相等）。所以对这 6 套而言，「块 = 页」**天然成立**，不存在 §4.1 那样的矛盾。
> `[订正]` 「逐通道相等」已**实算 ＋ 真机双证**（2026-10-06）：`#282c34` = `hsl(220 13% 18%)` = `rgb(40,44,52)`（三通道逐一相等）；浏览器注入 `console.css`/`tui.css` 后深色下 editor 与 codeBlock 探针读数同为 `rgb(40,44,52)`。

⇒ 于是问题变成**一个家族口径**，而不是六个缺陷：**自由式主题的「内容面」（编辑器页 ＋ 代码块）算不算它的地？** 见 §5.3。

### 4.3 B-3：`--n-gray-*` 八套里只有 `console` 染

只有 `console.css` 染兼容层（走 `--n-gray-*` 别名层，13 处；**不**染 `--palette-gray-*`）。
其余 7 套：`liquid-glass` 与 `tui` 在文件注释里**明确论证过「基座灰本就同温、不用染」**；`neubrutalism` / `macos-native` / `win9x` / `clay` / `fluent` 未见同样论证。

技能对这一点的现行措辞（`.agents/skills/theme-authoring/SKILL.md:130-133`）：

> **兼容层（`--n-*`）要按族整染**……四个中性族合计 **1380 处**……不染就是「外壳是主题色、内脏是冷灰」。

⇒ 技能把「整染」写成**建议**（"要"），契约把它写成**可选**（`full` 可以染、不强制）。**两者口径不同**，而用户主题根本不在契约内——所以 7 套不染**既不算错也无人提示**。

与 A-1 是同一个问题的用户侧投影，建议**合并裁定**。

## 5. 建议（按「改动量 / 收益」排序）

### 5.1 建议 1：改掉**两处**陈旧注释（A-2）—— **零视觉、零风险，建议直接做** `[订正]`

把 `cc-islands`（HEAD `:2061-2063`）与 `cc-onedark`（HEAD `:2367-2369`）的措辞改成与现行契约一致，例如：

> `--palette-white` and `--n-white` / `--n-black` are frozen for every theme (see `theme-overlays.spec.ts`). The `gray` / `zinc` / `slate` / `neutral` compatibility ramps are **optional**: a `full` theme may retint a family, but only as a complete eleven-step ramp — this theme leaves them at the base values.

要点：**删掉「enforces」的断言**（改为指向 `fixed` 三项），并点明 gray 是**可选**。
**`cc-onedark-vivid`（HEAD `:2612`）不改**：它只说「本主题不动」，未误归因守卫（见 §3.3）。

### 5.2 建议 2：`full` 是否必移 `compat`（A-1）—— **建议维持「可选」＋ 补写口径**

**推荐：维持可选**，并把「可选」这一点写进契约注释与技能，理由：

1. **契约族已经保证了「完整」徽标的下限**，`compat` 不在其中不影响徽标自洽；
2. 若改为必移，**现役 5 套主题会当场全红**（`CloudCLI用户主题升内置方案.md` §4.1 已预判此点），补 5×11×2 ＝ 110 条值 + 逐条对比度核算，收益不足；
3. `frost-50`（ΔE76 ≈ 2.2，且落在**小面积按钮文字**上，实际不可感知）**明确不该**为统一而补——这是「为一致而一致」的典型反例。

**同时建议补齐两件事**（`[订正]`：原写「闭合未闭合问题」，但审阅指出「可以 vs 应当」已在升内置方案 §4.1 闭合——这里补的是**另一处真缺口**）：

- 契约注释里写明：**`compat` 可选；一个 `full` 主题不收兼容层，是「保持中性纸面」的正当选择，不是遗漏**；
- **把「若染须整族 11 档」从「注释承诺」升级为「可执行断言」**——**二审独立复核成立**：该约定目前**无任何测试执行**（`theme-overlays.spec.ts:477-513` 的 `beyondReach` 只查 `moved ⊆ allowed`；`derivedMoves`（`:327-339`）会放行 `--n-gray-*` 的别名联动，故**只染 3 档时其余 8 档不动、无任何断言报错**；`grep -n "eleven" tests/theme-tokens/*.ts` 仅命中注释）。
  **升级方案已确认可行、且今日零误报**：`moved` 集合已在 per-theme test 现成算出，加一条「每个 compat 族的 moved 档数 ∈ {0, 11}」即可；反例检索确认现役**没有「合法半族」**（4 套染 gray 的均为完整 11 档；`cc-islands` 的 frost/danger-800 不属 compat 族、不受此约束）。⇒ **建议采纳执行**。

> 若你更认同 §3.1「证据二」的论据（"完整"徽标本就该覆盖 chrome），另一条路是：**保留可选，但新增一档 `coverage`**（例如 `full+compat`）给"真·完整"的主题。**我不推荐**——为一个不含验收断言的灰度差新增档位，代价大于收益。

### 5.3 建议 3：自由式用户主题的「内容面」归属（B-1 ＋ B-2）—— **建议写成家族口径**

**推荐口径**（用户主题家族，显式写进 skill 通道 B 一节）：

> **默认：内容面（编辑器页 ＋ 代码块底）交还基座。** 两族令牌都不写。
> **例外：想接管内容面的主题必须成对接管** —— 写了 `--editor-bg` 就必须给 `--code-block-bg` 同一个值（「块 = 页」不变量），否则就是一条必须单独记账的偏离。

按此口径的结算：

| 主题 | 现状 | 按口径判定 | 动作 |
|---|---|---|---|
| `liquid-glass` / `neubrutalism` / `macos-native` / `win9x` / `clay` / `fluent` | 两族都不写 | ✅ 合规（默认） | **无** |
| `console` / `tui` `[订正]` | 写了 `--editor-*`（**仅浅色半**），未写 `--code-block-bg` | ❌ 违反「成对」（**仅浅色**） | **浅色半各补 1 行**（或整份记一条偏离） |
| `macos-native` / `fluent` / `win9x` | — | ✅ | 特别正当：白纸文档窗口本就是它们的正确形态 |

推荐这个口径的理由：

1. 家族里**「白纸文档窗口」是多数套的正确形态**（mac / fluent / win9x / neo），把内容面纳入承诺会逼它们做错事；
2. **零改动即可让 6/8 合规**——只需补文档；
3. 与契约侧「块 = 页」的不变量**天然兼容**（基座两者同值）；
4. `console` / `tui` 的例外**代价极小**：**浅色半**各加一行 `--code-block-bg` 即可闭合（**实施期更正**：值取该主题 `--editor-bg` 的**三元组**形式，**不能**写 `var(--editor-bg)`——两个令牌形态不同，见文末实施记录），且这正是四套配色主题**已经记账接受过**的形态。

> **⚠️ 定性**（审阅指出）：§5.3 是一条**新增的家族政策**，**不是** skill / 既有方案已经裁定的口径——补齐方案 §8 决策 8 只是对「当时那四套主题」的「有意接受 ＋ 记账」，且 §2.2 另把 `console.css` 排除在范围外，不构成全体用户主题的先例。故本建议的措辞应写成「**本文新提议**」，并交代适用对象与对既有 `console`/`tui` 的具体处置。
> **备选（若你要视觉统一优先）**：让 8 套都补 `--code-block-bg`（指向各自的 `--muted` 或 `--card`）。这是**一次有意的视觉变更**，需按主题逐个拍板 —— 我**不推荐**作为默认，因为对 mac/win9x/fluent 会让「白纸代码块」变成「彩色代码块」，反而偏离这些主题的立意。

### 5.4 建议 4：把写死的站点数改成可复算（A-3）—— **零风险，建议做**

`theme-overlays.spec.ts:119-121`、`SKILL.md:131-139`、以及升内置方案的 §3.1/§4.1/附录 A，把「1380 / 1223 / 257」这类数字改成：

### 实施期更正（三处，均为「改之前是错的」）

1. **`--code-block-bg: var(--editor-bg)` 写不出来（§5.3 第 4 条的前提被证伪）**。两个令牌**形态不同**：`--editor-bg` 持 **full color**（`hsl(150 15% 97%)` / `#282c34`），`--code-block-bg` 持**三元组**（消费端 `hsl(var(--code-block-bg))`，`tailwind.config.js:67`）。照 §5.3 原文写会得到 `hsl(hsl(150 15% 97%))` —— **声明在 computed-value 期被丢**，正是本盘点 §4.2 判过的那种静默消失。实际写的是同色的**三元组**（`150 15% 97%` / `220 15% 97%`）。⇒ **判据**：一处「同色」的断言要先问**两侧是不是同一种写法**，否则「相等」只成立于某一个形态里。
2. **升内置方案的站点数「不改」**。§5.4 原文把该文档也列入「改数字」范围，但它**已实施完毕（2026-09-30）**、且其审阅记录逐条引这些数字当**当时**的复现证据——改它就等于篡改历史记录。处置：**保留**，只当带日期的快照；活文件（spec 注释 / SKILL）才改为「命令 ＋ 日期戳」。⇒ **判据**：「写死的数字」分**活文件**（会误导当下）与**已归档决策件**（其数字是证据）两桶，后者不动。
3. **在 `/* */` 注释里写 glob 把自己关掉了**。为给站点数配可运行命令，写了 `--glob '!**/tests/**'` —— 其中的 `**/` **含 `*/`**，块注释在那一行提前闭合，`tsc` 立即报 `TS1005`。改用不含该序列的等价命令 `rg -o 'n-gray-[0-9]+' src | grep -v '/tests/' | wc -l`（实测同为 1287）。⇒ **判据**：改注释也要跑 `tsc`；**注释里出现 `*/` 是硬错误，与「注释不影响行为」的直觉相反**。
