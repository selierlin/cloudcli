## 0. 结论先行与接力入口

用户报告：手机端在聊天会话里先上下滚动、再左右滑，侧边栏没反应。

其中最有价值的证据是用户自己做的对照实验：

- 上下滚动**完全停止**后，再从左边滑 → **有效**
- 上下滚动**还没停下来**（惯性仍在跑），再从左边滑 → **无效**，且「它会认为我是在上下滑」

由此只剩两个互斥候选：

| 代号 | 候选根因 | 现状 |
| --- | --- | --- |
| **H1** | 手势 hook 内部有**粘滞方向锁**：同一次触摸内首次位移偏纵向就把 `axis` 永久锁死，此后横向位移再大也直接 `return` | 已改（`7c9c04f9`），**待真机验证** |
| **H2** | iOS 原生滚动层（`-webkit-overflow-scrolling: touch` + `touch-action: pan-y`）在惯性期间吞掉或改判了新触摸 | **未验证**；本机无法复现，见 §4 |

**接力下一步只有一件事**：用 `7c9c04f9` 打真机，跑 §6 的判别实验。

- 结果 **A（能滑开）** → 根因是 H1，收工；顺带确认没有引入误触发（§8）。
- 结果 **B（还是没反应）** → 根因是 H2，按 §7 实施左边缘独立手势带。

**不要做**：不要重新去猜「起点不在左边缘」这个方向——用户已确认是从左边起手，该分支已排除（§8.2）。

## 1. 现象与复现

### 1.1 复现路径

1. 手机打开 CloudCLI，进入任一聊天会话（抽屉关闭）。
2. 在消息区快速上下滑动，让列表进入惯性滚动。
3. **趁惯性还没停**，从屏幕左边缘向右滑。
4. 观察：抽屉不打开；页面看起来仍在按纵向处理这次触摸。
5. 对照组：等惯性完全停下再滑，抽屉正常打开。

### 1.2 口径

- 「有效」= 抽屉打开/关闭。
- 关键变量是**触摸落下的那一刻惯性是否仍在进行**，而不是用户此前滚了多远。

### 2.2 H1：改动前的粘滞方向锁

`7c9c04f9` 之前，`handleTouchMove` 的判定是：

```ts
const dx = touch.clientX - gesture.startX;
const dy = touch.clientY - gesture.startY;

if (gesture.axis === null) {
  if (Math.max(Math.abs(dx), Math.abs(dy)) < AXIS_LOCK_SLOP_PX) return;   // 10px
  gesture.axis = Math.abs(dx) > Math.abs(dy) ? 'horizontal' : 'vertical'; // 打平算纵向
}
if (gesture.axis !== 'horizontal') return;   // ← 锁成纵向后，整个触摸周期弃权
```

两个后果：

1. `axis` 一旦为 `vertical`，同一次触摸内**永不改判**，横向位移再大也不看。
2. 判定用的是**相对触摸起点**的累计位移，所以「先纵向滚 150px，再横向滑 80px」即使取消粘滞锁也仍然判不出来（`|dx| < |dy|`）。

原单测把这个行为固化成了契约（旧的 `abandons a gesture that began vertically…` 用例），本次一并改掉了语义。

### 2.3 H2 的介质：滚动层与 `touch-action`

```css
@media (max-width: 768px) {
  .overflow-y-auto, [data-scroll-container] {
    touch-action: pan-y;
    -webkit-overflow-scrolling: touch;
  }
}
```

- `touch-action: pan-y` 的语义是「纵向平移交给浏览器，横向留给 JS」。**静止状态下**从边缘横滑是能拿到 `touchmove` 的（用户也确认平时能用）。
- `-webkit-overflow-scrolling: touch` 在 iOS 上让该容器成为原生滚动层（UIScrollView）。**惯性进行中**落在它上面的新触摸，属于滚动手势识别器的领域——这是 H2 怀疑的机制，但**未验证**。

## 3. 本机 Playwright 实验（Chromium 实测，可复现）

### 3.1 方法

搭一个与线上同构的最小页面：一个 `touch-action: pan-y` 的可滚动容器（60 行占位），外层 `#shell` 挂 `touchstart/move/end/cancel` 记录事件，滚动容器自身也挂 `passive` 监听。用 Playwright 的 Chromium（`viewport 390x844`、`hasTouch`、`isMobile`）+ CDP `Input.dispatchTouchEvent` 注入真实触摸序列。

### 3.2 结果

| 序列 | 外层是否收到事件 | 旧实现是否触发 | 是否出现 `touchcancel` |
| --- | --- | --- | --- |
| 不滚动，贴左边缘横滑（基线） | 全套正常 | 触发 | 无 |
| 先滚动 → **抬手** → 贴左边缘横滑 | 全套正常 | **触发** | 无 |
| 同一次触摸内，先纵后横（不抬手） | `touchmove` 仍在 | **拒绝**（方向锁已锁纵向） | **无** |

### 3.3 结论与边界

- 「滚动结束 + 抬手 + 贴边滑」在 Chromium 上是通的，滚动本身不污染后续触摸（每次 `touchstart` 都会重置并重新武装）。
- 同一次触摸内先纵后横会被方向锁拒掉——这是 H1，已由 `7c9c04f9` 处理。
- **边界**：CDP 合成触摸不产生真机那种惯性滚动，所以这套实验**测不到 H2**；第 3 行没出现 `touchcancel` 是合成环境的结果，真机行为可能不同，不要把它当成 H2 已被否定的证据。

## 4. 未验证的推断：iOS 惯性期间吞掉触摸（H2）

**这是当前唯一的阻断点，也是本机无法证伪的一条。**

推断链条：iOS 上滚动容器是原生滚动层；惯性进行中，滚动手势识别器对新触摸仍有优先权/方向继承，`touch-action: pan-y` 只约束静止状态下起手的手势，管不到这一窗口。表现就是用户说的「它会认为我是在上下滑」。

**需要什么才能确认**：真机上（iOS WKWebView / Safari）观察惯性未停时从边缘横滑，页面是否仍在继续纵向滚动。是 → H2 成立。

**不要**在缺乏真机证据的情况下把 H2 写成结论。

## 5. 已落地改动 `7c9c04f9`

### 5.1 语义变更

粘滞方向锁 → **锚点跟随**（`useSidebarSwipeGesture.ts:81-104`）：

```ts
const dx = touch.clientX - gesture.anchorX;
const dy = touch.clientY - gesture.anchorY;
const absDx = Math.abs(dx);
const absDy = Math.abs(dy);

if (absDx <= absDy) {
  // 偏纵向 = 在滚动：锚点跟着手指走，滚动不累积进横向计数
  if (absDy > absDx + SCROLL_HYSTERESIS_PX) {   // 10px
    gesture.anchorX = touch.clientX;
    gesture.anchorY = touch.clientY;
  }
  return;
}

const travel = direction === 'right' ? dx : -dx;
if (travel <= SWIPE_TRIGGER_PX) return;         // 60px
onSwipe();
```

要点：

- 不再有「锁死后永久弃权」——横向位移从**滚动停下的位置**重新起算。
- 打平仍算纵向（保守）。
- 滚动中的轻微横向抖动需要比纵向多出 `SCROLL_HYSTERESIS_PX`（10px）才会把锚点带走，避免抖动把横向计数反复清零。
- 数据结构由 `{startX, startY, axis}` 改为 `{anchorX, anchorY}`；`AXIS_LOCK_SLOP_PX` 被 `SCROLL_HYSTERESIS_PX` 取代。

### 5.2 测试变更

- 改语义：`abandons a gesture that began vertically even if the finger later drifts far sideways` → `hands a scroll over to the swipe once the finger turns decisively sideways`（现在**应当**触发）。
- 新增：纯滚动无论滑多远都不触发；滚动后只横移一小段（未过阈值）不触发。

### 5.3 已验证

- 目标文件单测 10/10 通过。
- `npx vitest run` 全量：121 文件 / 841 用例全过。
- `npx tsc --noEmit -p tsconfig.json` 干净；改动文件 `oxlint` 0 warning。

## 7. 结果 B 的候选方案：左边缘独立手势带（未实施）

思路：把左边缘那 32px 从滚动容器里「摘出来」。惯性期间触摸落在**非滚动元素**上，就不会进入滚动层的方向继承，`touch-action: none` 把事件全量交给 JS。

- 位置：挂在 `ProjectWorkspaceShell` 里、**滚动容器之外**（`position: fixed`，`left: 0`，宽 `EDGE_ZONE_PX`，`top: 0; bottom: 0`），移动端 + 抽屉关闭时渲染。
- 手势：沿用 `useSidebarSwipeGesture`（`direction: 'right'`，`startZonePx` 可去掉，因为整条带都是起手区）。
- `touch-action: none`。

代价（实施前必须让用户确认）：

- **该带内不能纵向滚动聊天**（触摸不穿透到下面的滚动容器）。32px 在 390px 宽屏幕约占 8%；可缩到 20–24px 减轻。
- 会挡掉该区域内的文本点选。
- 惯性期间按下这条带，**不会**停止下面滚动容器的惯性（触摸不在它身上），画面可能仍在滚——需要一并决定是否接受。
- 可能的缓解：在该带的 `touchstart` 里主动中断滚动容器的惯性（把 `overflow` 临时切 `hidden` 再恢复），但这是 hack，会触发重排，需实测。

不变量：

- 不要为了这条路把 `.chat-messages-pane` 的 `touch-action` 从 `pan-y` 改掉——那会连带废掉原生纵向滚动。
- 不要试图用 JS 自己实现聊天区滚动。

## 8. 风险与不变量

### 8.1 本次改动引入的误触发风险

锚点模型允许「先滚动后改判横向」，代价是**滚动时手指明显斜向漂移**可能被读成横滑：

- 触发条件是相对锚点的 `|dx| > |dy|` 且横向位移 > 60px。正常纵向滚动的横向漂移远达不到。
- 起手区仍限制在左边缘 32px（`startZonePx` 未动），所以只有从边缘起手才会进入这套判定。
- 真机回归时重点看这一条（§6）。

### 8.2 已排除的分支

- ~~横滑起点不在左边缘~~：用户确认是「从左边滑」，且对照实验显示与「滚动是否停止」相关，与起点无关。
- ~~`useChatSessionState` 的原生监听干扰~~：那组监听是 `passive`，既不 `preventDefault` 也不 `stopPropagation`。

### 8.3 保持成立的前提

- 每次 `touchstart` 都会重置手势状态（`useSidebarSwipeGesture.ts:52-68`），不存在跨触摸的脏状态。
- 面板的 `onTouchStart` 会 `stopPropagation`，外壳不会重复处理抽屉内的触摸（`ProjectSidebarRegion.tsx:178-182`）。
