# CloudCLI 当前正文焦点与执行过程折叠方案

> 状态：已实施，待手工验收
> 日期：2026-09-15
> 范围：聊天前端的回合内展示层；不改 Provider 协议、历史解析或会话持久化
> 前置方案：`docs/research/思考过程与工具活动体验优化方案.md`

## 0. 结论先行

本方案采用 **当前正文焦点 + 执行过程折叠**。

用户发送一条消息后，AI 往往交错产生思考、进度正文、工具调用和工具结果；最后才出现交付给用户的正文。Claude、Codex、WorkBuddy 都存在这种模式，但没有跨 Provider 可靠的“最终正文开始”事件。

因此不等待 `complete`，也不预测某段正文一定是最终答复。实时界面始终保持同一用户回合中**最新开始输出的普通 assistant 正文**可见；该正文之前的过程内容收进可展开的“执行过程”。若模型之后继续调用工具，过程继续追加；下次新的正文开始时，再把此前阶段收进过程区。运行结束后，最后的正文自然成为最终正文。

```text
用户问题                              始终可见
└─ 执行过程（折叠，可展开）             思考 / 过程正文 / 已完成工具
└─ 当前 assistant 正文（展开且流式）    当前焦点；完成后即最终正文
```

这样用户在最终正文流式期间可立即上滑回看自己的提问，不必等待整轮执行完成。

## 1. 背景与问题

当前 UI 的消息按原始时间线逐条渲染。虽然连续工具已有分组、Claude thinking 已支持独立 disclosure，但同一个用户回合中的过程正文、工具和最终正文仍处于同一视觉层级。

长工具链会造成两个问题：

1. 最终正文开始流式时，前置过程占据大量垂直空间；用户要回看自己的问题，需越过大量工具卡片和过程消息。
2. 仅依据 `complete` 自动收起太晚；用户最需要空间的恰是最终正文的流式阶段。

不能把“任意 assistant 正文”标记为最终答复。真实会话中大量正文是 preamble，例如“我先核对实现”，随后仍会有工具调用。`stream_end` 只结束一条 assistant 消息，也不代表这一用户回合结束。

## 2. 目标与边界

### 2.1 目标

| 目标 | 验收含义 |
| --- | --- |
| 当前回答优先 | 新的 assistant 正文开始流式后，它不被自动折叠 |
| 可回看提问 | 该正文上方只保留用户问题和一条紧凑的执行过程摘要 |
| 保真 | 过程消息不删除、不重排、不合并原始内容；一次点击可完整展开 |
| 可逆 | 后续工具调用不会让 UI 错误声称先前正文已是最终答案 |
| Provider 无关 | Claude、Codex、WorkBuddy 及其他输出 `ChatMessage` 的 Provider 使用同一规则 |
| 异常可见 | 失败、拒绝、停止、等待用户操作的项不被默认隐藏 |

### 2.2 非目标

- 不修改 `NormalizedMessage`、WebSocket 事件、Provider transcript 读取或数据库格式。
- 不试图展示 Codex 加密 reasoning，也不虚构 WorkBuddy 未持久化的思考内容。
- 不改变工具执行、权限、提问、任务通知或自动滚动的语义。
- 不持久化展开状态；首期仅在当前会话视图生命周期内保留用户选择。
- 不将不同用户回合合并为一个卡片，也不改变导出的完整 transcript。

## 3. 外部产品取舍

- Claude Code 使用 Normal / Verbose / Summary 三档显示粒度：工具可折叠或只保留最终答复；这是用户主动切换的全局密度策略。
- OpenCode 按用户消息组织一个 turn，保留该 turn 关联的 assistant parts；工具与推理分别折叠，不把前置正文自动视为最终答复。
- 本机 WorkBuddy/CodeBuddy Web UI 对完成且无异常的工具活动默认折叠，正文保持独立可见，thinking 有独立展开控制。

CloudCLI 采用更细的回合内渐进披露：不改变用户选定的全局“显示详细程度”，只在出现新的正文焦点时压缩已经结束的执行阶段。

## 4. 展示规则

### 4.1 回合边界

一个回合从 `type === 'user'` 的可见用户消息开始，到下一条可见用户消息前结束。系统注入、工具结果、附件和任务内部事件不会新建回合。

每个回合按当前渲染顺序派生三类区域：

| 区域 | 内容 | 默认状态 |
| --- | --- | --- |
| 用户问题 | 回合起点的 user 消息 | 展开 |
| 执行过程 | 当前正文焦点之前的可折叠过程项 | 有合格焦点时收起 |
| 当前正文焦点 | 回合内最后一条普通 assistant 正文 | 展开，流式更新 |

普通 assistant 正文候选满足：非 `isThinking`、非 `isToolUse`、非任务通知及其结果、非 `isCompactSummary`、非 `isLocalCommandStdout`，且正文非空。本地 slash 命令回显和 stdout 都不切断回合；stdout 作为过程成员展示，不能成为焦点。

### 4.2 焦点切换

```text
用户 → 思考 → 工具 → “正在核对…”
                    └─ 上方思考与工具折叠；“正在核对…”为当前焦点

               → 工具 → “已完成，结果如下…”
                    └─ 前一正文及新增工具折叠；最后正文成为新焦点
```

规则：

1. 新普通 assistant 正文到达时，若它之前存在可折叠过程项，创建或更新该回合的执行过程组。
2. 当前焦点正文在组外，正常流式渲染；更新的正文到达后，前一焦点正文转为过程成员。
3. 之后到达的工具、thinking、过程正文先保持正常显示；直到下一段普通 assistant 正文到达，才一并收入过程组。
4. 当前正文之后若只有工具/思考而没有新正文，这些尾随项先正常显示，保证实时执行可观察；收到本轮 `complete` 后，仅当用户仍贴底、过程组不是 `user_open`，且不存在运行中、异常或待用户操作项时，才把它们并入执行过程并自动收起。若过程组为 `user_open`，允许并入成员但必须保持展开；若用户已上滑，则不改变当前成员投影或可见性。这是**收束快照**，不是焦点切换前提：最终正文在首次流式时已可见、已腾出此前空间。
5. 历史加载时，回合最后一条普通 assistant 正文为焦点，之前合格过程默认折叠。

该规则不以 `complete` 作为焦点切换前提。`complete` 仍负责流式 flush、结束活动指示器、历史刷新及上述无歧义的尾随过程收束；这与“正文开始时不等待 complete”不冲突。

### 4.3 不可自动折叠的内容

以下内容保持在组外或使对应工具组默认展开：

- user 消息；
- `AskUserQuestion`、权限请求、计划确认、待办和其他需要用户动作的卡片；
- error、工具失败、拒绝、停止或尚在运行的工具；
- 当前正在流式的正文；
- 用户已手动展开的执行过程。

错误或被拒绝的工具若出现在其他过程项中，摘要必须展示失败状态与数量，默认展开该过程组；不能将排障入口藏进一层折叠后再要求用户二次寻找。

## 5. 前端实现设计

### 5.1 责任划分

| 位置 | 责任 | 是否修改 |
| --- | --- | --- |
| `useChatMessages.ts` | Provider 无关的 `NormalizedMessage → ChatMessage` 投影 | 否 |
| `useChatRealtimeHandlers.ts` | 流式缓冲、`stream_end` / `complete` 收尾 | 否 |
| `ChatMessagesPane.tsx` | 从 `visibleMessages` 按 user 回合派生焦点、过程摘要和行级可见性 | 是 |
| 新增 chat module 内部派生工具 | 纯函数：回合扫描、可折叠性、摘要和行级投影 | 是 |
| 新增 `ExecutionProcessSummary` | 过程摘要、展开状态和异常状态；不承载既有消息子树 | 是 |
| `MessageComponent.tsx` / `ToolGroupContainer.tsx` | 复用现有单条消息、工具分组和详情渲染 | 尽量不改 |

首期不改后端；所需字段（`type`、`isThinking`、`isToolUse`、`isStreaming`、工具状态、时间戳）均已在 `ChatMessage` 中存在。

### 5.2 派生数据结构

在 `src/modules/chat/` 内定义模块私有类型，避免污染跨模块共享类型：

```ts
type ExecutionProcessGroup = {
  kind: 'execution_process';
  turnKey: string;
  memberKeys: Set<string>;
  timestamp: ChatMessage['timestamp'];
  status: 'completed' | 'running' | 'attention';
  summary: string;
};

type TurnPresentationItem = ChatMessage | ToolGroupItem | ExecutionProcessGroup;
```

`turnKey` 必须复用 `getIntrinsicMessageKey(本轮 user 消息)`，而不是引入依赖扫描位置的回合序号。该现有 helper 已覆盖 id、messageId、toolId 与时间戳/内容回退，能适应 Codex 刷新时 id 变化。若 helper 无法产生稳定 key，本期保守地不对该回合自动折叠，也不保存展开选择。

扫描必须为 O(n)，并在 `visibleMessages`、`showThinking`、`isProcessing` 或会话 id 改变时通过 `useMemo` 重算。先为原始 `visibleMessages` 建立与顶层行完全一致的、已消歧 `getMessageKey()` 映射，再以其返回值填充 `memberKeys`；不得使用未消歧的 intrinsic key。回合边界使用新的 `isVisibleUserTurnStart`：排除 `isLocalCommand` 命令回显；焦点候选复用并扩展现有 `isFinalAnswerCandidate`，统一排除 `isCompactSummary` 和 `isLocalCommandStdout`。同一个谓词由 thinking disclosure 和过程投影共同使用，避免例外集合漂移。

过程投影**不重新 parent 既有消息行**。`ExecutionProcessSummary` 是插在首个过程行前的摘要行；原有 `LazyMessageRow`、`MessageComponent` 与工具组继续留在既有顶层顺序和 key 下，只接收 `isProcessCollapsed` 可见性标记。折叠成员必须保持 React 挂载，只以 CSS 改变视觉可见性；不得条件渲染为 `null` 或卸载行，并须避免折叠态覆盖其缓存的完整测量高度。这样焦点推进不会把已挂载行迁进新的 React 子树，thinking disclosure、工具详情展开状态、测量高度与文本选择不会因过程收拢被重置。现有工具组仍在同一过程阶段内工作，不增加新的嵌套业务容器。

### 5.3 展开状态与用户所有权

`ChatMessagesPane` 增加按 `turnKey` 存储的本地 disclosure registry：

```ts
type ExecutionProcessDisclosure = 'auto_collapsed' | 'user_open' | 'user_closed';
```

- 新建合格过程组时默认 `auto_collapsed`。
- 用户点击后写入 `user_open` 或 `user_closed`；同一会话视图内，后续流式更新不得覆盖其选择。
- 任一成员处于 `error`、`denied`、`stopped`、待授权/提问或运行中时，过程组处于 `attention`：自动收起被禁止，默认展开。用户仍可主动收起，但摘要持续显示红色/等待状态与数量。
- “异常消失”仅指实时行被历史行替换后不再具有上述 attention 状态；这时恢复原 registry 的 `user_open` / `user_closed`，若用户未操作则回到 `auto_collapsed`。不假设已经落盘的错误工具会自行变为成功。
- 会话切换时清空 registry；刷新、LazyMessageRow 卸载/挂载和历史尾页替换不能清空。

过程组 disclosure 只控制成员行的外层可见性，不调用或覆盖组内 thinking/工具自身的 disclosure reducer。组折叠后，thinking 的 `user_open` / `user_closed` 状态仍保留；用户重新展开过程组时，thinking 与工具恢复各自原来的展开状态。

### 5.4 摘要

摘要需要回答“做了什么、是否成功、能否展开”，不展示原始输出：

```text
⌄ 执行过程 · 已检查 4 个文件、运行 3 条命令
⌄ 执行过程 · 8 个工具 · 1 项失败
⌄ 执行过程 · 等待你的确认
```

工具详情仍交给现有 `ToolGroupContainer`。过程摘要仅是行级可见性投影，不能复制工具解析、Diff 统计或权限按钮实现。摘要与状态文案全部走 chat i18n 资源，不硬编码中文。

已完成的 `isSubagentContainer` 可成为过程成员，摘要附带其 activity count；`subagent.status` 为 `running` 或 `failed` 时按 `attention` 处理并保持可见，不能只依据 `toolStatus` 判断。子代理内需要用户操作的状态应以实际的顶层提问、权限或交互卡片为准，不虚构 `SubagentInfo.status` 未定义的取值。

### 5.5 滚动与无障碍

- 自动折叠只在用户仍贴底时触发；若已上滑阅读，保留当前布局，显示的当前正文仍正常流式。
- 焦点推进、thinking 自动收起和 `complete` 收束快照共用 pane 级滚动跟随调度；同一帧最多请求一次补偿/跟底，且仍受贴底与用户操作守卫约束。
- 过程组的展开按钮使用 `button`、`aria-expanded` 和清晰的文本摘要。
- 用户点击展开时暂停自动跟底一次，避免内容展开后立刻被拉回尾部。
- `prefers-reduced-motion: reduce` 时不做高度动画；其他情况高度/透明度过渡不超过 200ms。
- 导出模式忽略折叠：`buildTranscriptMarkdown` 继续导出完整、原始顺序的消息。

## 6. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 中间正文被暂时视为焦点，随后又调用工具 | 不称其为“最终答复”；工具照常出现，下一正文到来再推进焦点 |
| 用户正在审阅过程时布局突变 | 非贴底不自动收起；用户手动展开后取得本轮所有权 |
| 错误被隐藏 | 过程组摘要显示异常且默认展开 |
| 分页窗口从回合中间开始 | 信息不完整时保守不生成跨窗口过程组；加载更多后重算 |
| 流式/历史消息去重替换对象 | 使用稳定 `turnKey`，不依赖消息对象引用 |
| 折叠层级复杂 | 过程摘要只改变既有行可见性；工具组与 thinking 继续使用各自已有的 disclosure，不新增嵌套承载组件 |
| 末尾工具历史/实时不一致 | 流式时先展示；仅在 `complete` 的安全条件满足时做一次尾随过程收束，历史加载直接按已完整回合投影 |

## 7. 测试与验收

### 7.1 单元测试

新增纯函数测试，覆盖：

1. Claude：thinking → preamble → tool → final text，最终只保留 final text 在组外。
2. Codex：preamble → tool → final text；没有 thinking 也可折叠。
3. WorkBuddy：`output_text` 与顶层工具调用交错；按投影后的 `ChatMessage` 得到同样结果。
4. 后续工具到达后，当前焦点仍可见；下一正文到达后前一正文进入过程组。
5. user、提问、权限、失败、停止与运行中工具不被隐藏。
6. 同一回合多个正文、空正文、任务通知、分页截断回合。
7. 用户展开后新的流式更新不自动关闭；切换会话后 registry 重置；无稳定 user key 的回合保守平铺。
8. 正文后仅有尾随工具且无新正文：运行时先可见，`complete` 后在安全条件下收束；历史加载与该最终快照一致。
9. 本地 slash 命令回显与 stdout 都不切断回合；compact summary 与 stdout 都不成为焦点。
10. thinking 曾被用户展开后，过程组收起/再展开不改变其内部 disclosure；流式焦点推进不改变成员 React key。
11. 完成与运行中的 subagent 容器分别进入过程摘要与 `attention` 可见态。
12. `complete` 收束到达时，`user_open` 过程组合并后保持展开；用户已上滑时不改变成员投影或可见性。

### 7.2 组件测试

在聊天模块测试中断言：

- 当前流式正文首次出现时，过程组变为折叠且用户问题仍在 DOM；
- 点击过程摘要能恢复完整时间线和工具详情；
- 错误过程默认展开；
- 上滑状态下不自动收起；
- 焦点推进、thinking 自动收起与 `complete` 收束同帧发生时，最多触发一次滚动跟随；`user_open` 或上滑状态下的 `complete` 不强制折叠；
- 正文流式期间，用户问题与过程摘要同时可见；尾随工具在 `complete` 前后按收束规则转换；
- `AskUserQuestion`、权限卡片与运行中 subagent 不被过程投影隐藏；
- 导出路径仍能获得全部消息。

### 7.3 人工验收

- 桌面与 iOS H5：最终正文流式期间向上滑动，可在一次短滚动内看到用户问题。
- Claude、Codex、WorkBuddy 各抽一条有过程正文和多工具的真实会话。
- 文本选择、工具权限、`AskUserQuestion`、后台任务通知、失败工具、回到页面后刷新历史。

### 7.4 完成标准

1. 不改动 Provider parser 与服务端接口。
2. 三种 Provider 的投影消息均通过同一前端规则。
3. 当前流式正文、用户问题、异常和可交互卡片始终可达。
4. 全部新增定向测试通过，并执行 `npm run test:client`、`npm run typecheck`、`npm run lint`、`npm run build:client`。

## 8. 实施顺序

1. 编写回合过程派生纯函数和单元测试，先锁定顺序与例外。
2. 在 `ChatMessagesPane` 接入 `ExecutionProcessSummary` 与行级投影，复用现有消息和工具渲染器。
3. 接入 disclosure registry、贴底 guard 与异常默认展开。
4. 补齐组件测试与三 Provider 历史会话人工验收。

每一步均不改变 Provider 原始事件，只改变 `visibleMessages` 的展示投影；发生回归时可独立移除过程组投影并恢复当前逐条渲染。

> 第 144 行 `turnKey` 明确优先使用 user 稳定 transcript anchor / id，缺失时回退为"session id + 用户消息时间戳 + 当前回合序号"。Session id 在分页/刷新/重连时不变，时间戳不变，但***回合序号依赖扫描顺序***——分页窗口从回合中间开始、或加载更多后重算（第 146 行 useMemo），序号会漂移，导致同一回合的 `turnKey` 变化 → React key 变化 → 5.3 的本地 disclosure registry 里 `user_open`/`user_closed` 映射到错误组或直接丢失。这不满足 5.4 第 146 行"刷新、历史尾页替换不能清空 registry"的目标。建议：`turnKey` 只允许用稳定 anchor，若 anchor 缺失则明确该期不回退序号（此时改用"不可折叠/不持久化展开选择"的保守策略），而不是用易变序号硬凑。

> [!WARNING] thinking 的既有独立 disclosure 与过程组折叠的归属关系未定义
> 第 1 节背景明确 Claude thinking 已支持独立 disclosure。但当 thinking 被收入执行过程组后，其独立展开/收起是继续保留，还是被过程组的 `auto_collapsed`（5.3）一并吞掉？若收进折叠组，用户此前展开过的某条 thinking 会被无形折叠，与 2.1「可逆」「用户所有权」和第 159 行"异常消失后恢复原选择"的意图相悖。方案只定义了过程组这一层 disclosure，没有定义组内子项（thinking、工具）的既有展开状态如何与组级状态交互。建议明确：过程组展开后才响应内部 thinking/工具各自 disclosure，组级折叠只控制整组，二者互不覆盖；并在 7.1/7.2 补一条"组内已被用户展开的 thinking，组折叠后是否保持"的断言。

> [!NOTE] 4.3 与 5.3 的异常状态优先级及"异常消失"语义模糊
> 4.3 第 111 行说"错误/被拒绝工具出现在其他过程项中时，摘要展示失败状态与数量，默认展开该过程组"；而 5.3 第 159 行说"异常状态强制显示展开内容，但不抹去用户选择；异常消失后恢复原选择"。存在两个未定义点：(1) 同一过程组内既有 `user_open` 手动展开、又有异常项时，谁的显示优先级、以及后续用户再次点击时的归属如何判定；(2) "异常消失"具体指什么状态翻转——是错误工具被新消息替换，还是工具状态从 error 变回非 error？建议给出判定规则和一例带时序的验收用例。

> [!TIP] 测试覆盖缺实时流式下"正文后工具、无新正文"关键路径
> 7.1 的用例多基于历史消息推导（thinking → preamble → tool → final text），但本方案核心价值在于**实时流式**阶段的渐进披露。建议补两条：(1) 最终正文已在流式、用户回看提问的瞬间，后续工具到达且无新正文时，过程组/平铺布局如何维持（上文第一条已提）；(2) 回合中出现 `AskUserQuestion` 或等待用户输入、回合跨越用户操作继续延续的场景（4.3 第 105 行列为不可自动折叠，但未验证其与焦点推进的时序）。这两条直接决定 7.3 人工验收想看到的真实体感。

### 牵头结论

- 采纳：运行中“正文后仅有工具、无新正文”与历史快照不一致的问题。`complete` 现在只承担安全条件下的尾随过程收束；正文焦点仍在首次流式时立即建立，不等待完成。（来源：Claude、WorkBuddy）
- 采纳：删除依赖回合序号的 `turnKey` 回退，改为复用 `getIntrinsicMessageKey`；无稳定 key 时保守平铺。（来源：Claude、WorkBuddy）
- 采纳：过程摘要改为行级可见性投影，既有行不迁入新 React 父节点；保留 LazyMessageRow、工具详情和 thinking 的内部状态。（来源：WorkBuddy）
- 采纳：过程组只控制外层可见性，thinking 与工具的既有 disclosure 继续独立；复用焦点候选谓词与现有 reducer 语义，避免双重收起竞争。（来源：Claude、WorkBuddy）
- 采纳：补充 attention 状态优先级、异常状态恢复语义、本地命令回显、compact summary、subagent 容器、i18n 和实时流式验收。（来源：Claude、WorkBuddy）
- 部分采纳：现有 `reasoningDisclosure.ts` 的 `candidate.isStreaming || !isProcessing` 可作为 thinking handoff 的已有输入，但过程摘要不会照搬其“流式即最终”的副作用；焦点切换仍按新正文事件，尾随过程仅在 `complete` 安全收束。（来源：WorkBuddy）
