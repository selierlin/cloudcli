# CloudCLI 回到底部按钮思考态样式优化方案

> 状态：首轮评审完成（12 条批注已逐条裁定，正文已按采纳项修订；未实施）
> 日期：2026-09-14
> 范围：聊天记录窗「回到底部」圆钮在轮次运行中的图标表现
> 变更性质：纯展示层。不改位置、尺寸、配色、点击行为，不改滚动所有权，不改 Provider 协议与持久化
> 关联文档：`docs/architecture/05-scrolling.md`（§`Scrolling up mid-stream, and getting back` 需要同步）

## 0. 结论先行

本方案只改一件事：**圆钮里的图标随轮次状态切换**。

- 轮次在跑（有活动且没在等用户授权）时，圆钮里显示三个错峰上下跳动的点。
- 其余时候显示现在的下箭头。
- 两者叠在同一个网格格里做 200ms 交叉淡入，不做缩放或旋转。
- 状态来源直接复用已经算好的 `hasActivityIndicator`，不新增 state、不新增 prop、不新增 i18n key。
- 位置、尺寸、配色、点击行为全部保持现状，**包括 `-top-11` 不动**。首轮评审曾建议改为 `-top-16` 以避开活动条竖带，二轮核查发现该风险所依赖的「长状态文案」在本仓库不可能出现（§4.6），故不采纳。

方案包含一处结构性改动：把这段按钮从 `ChatInterface.tsx` 抽成模块内组件。理由是这次唯一的逻辑就是「哪个图标」这个分支，而仓库现有聊天测试全部走 `renderHook` 或直接渲染被抽取的子组件（`lazyMessageRow.test.tsx` 即为范例），内联分支没有可挂载的测试载体。抽取后 `ChatInterface.tsx` 侧的差异是一个导入加一行组件调用。

### 1.2 已确认事实

1. `sessionActivity` 与 `isProcessing` 恒等：`sessionActivity = (activeSessionId && processingSessions?.get(activeSessionId)) || null`，`isProcessing = sessionActivity !== null`（`useChatSessionState.ts:313-314`）。因此「用一个信号还是另一个」是伪命题，真正的分歧只在「等授权时要不要压掉」。
2. `hasActivityIndicator` 已在本组件算好：`Boolean(sessionActivity && pendingPermissionRequests.length === 0)`（`ChatInterface.tsx:431`），当前只用于给记录窗加底距。
3. 活动指示条与圆钮占据同一竖向带：活动条挂在 `absolute bottom-full`（`src/modules/chat/composer/ChatComposer.tsx:280`），高度 `h-8`；圆钮占 `-top-11` 起 32px。按类名推算，圆钮占 `-44px ~ -12px`，活动条占 `-32px ~ 0px`，竖向重叠 20px（此为类名推算，未在真机量取）。
4. 但两者横向不冲突：活动条是「标签靠左、Stop 靠右」的 `flex items-end justify-between`（`ActivityIndicator.tsx:91`），整行以面板中心为轴（`ChatComposer.tsx:280` 的 `left-1/2 -translate-x-1/2`）；圆钮容器 `left-0 right-0` 加 `justify-center`（`ChatInterface.tsx:510`），同以面板中心为轴。中间本来就是空的。
5. 等授权时活动条被整块移除：`{!hasPendingPermissions && (...)}`（`ChatComposer.tsx:279`）。
6. 本仓库没有任何测试渲染过 `ChatInterface`。聊天模块的组件级测试都是「抽取子组件 + RTL render」的形式，例如 `src/modules/chat/tests/lazyMessageRow.test.tsx:1-30` 直接渲染 `LazyMessageRow`。
7. `tailwind.config.js:65-88` 现有 `shimmer`、`dialog-overlay-show`、`dialog-content-show`、`bottom-sheet-content-show` 四组 keyframe，**没有三点跳动动画**。现有唯一的点动画是 `ActivityIndicator.tsx:93` 的 `animate-pulse` 单点，以及 `Shimmer` 文本。
8. `src/index.css:261-270` 已有全局 reduced-motion 兜底：`animation-duration: 0.01ms !important`、`animation-iteration-count: 1 !important`。注意它**不改** `animation-delay`。

## 2. 目标、指标与非目标

### 2.1 目标

1. 用户上滑离开底部时，圆钮能在不点击、不滚动的情况下表明「模型还在干活」。
2. 状态切换本身不产生闪烁：箭头与点之间是渐变过渡，不是硬切。
3. 不因这次美化引入任何新的状态源、接口面或文案面。
4. 不改变既有可访问性语义：圆钮的可访问名始终是它的动作。

### 2.2 可验证指标

| 指标 | 门槛 |
| --- | --- |
| 运行中 + 已上滑 | 圆钮内出现 3 个点，箭头不可见 |
| 空闲 + 已上滑 | 圆钮内出现箭头，点不可见 |
| 等待工具授权 + 已上滑 | 出现箭头，不出现点（与 `ChatComposer.tsx:279` 隐藏活动条一致） |
| 状态切换 | 200ms 透明度过渡，无 DOM 卸载重建，无尺寸变化。该指标仅适用于允许动效的环境；reduced-motion 下降级为硬切（见 §4.4） |
| 可见性条件 | 只在 `isUserScrolledUp && chatMessages.length > 0` 时挂载，贴底不显示 |
| 可访问名 | 始终等于 `input.scrollToBottom`，点容器 `aria-hidden` |
| reduced-motion | 点为静止三连点，不出现位移残留或半透明残影 |
| 新增 i18n key | 0 个 |
| 新增 state / prop / 依赖 | 0 个 state，0 个新增依赖 |
| 自动化回归 | 定向测试、`npm run test:client`、`typecheck`、`lint`、`build:client` 通过 |

### 2.3 非目标

- 不加未读数、小红点、新消息条数或任何「有多少条新内容」的指示。`docs/architecture/05-scrolling.md:193-194` 明确记载当前没有未读指示，本方案维持该决定。
- 不把圆钮改成 FAB 或搬到右下角，不改任何定位类名（含 `-top-11`，理由见 §4.6）。
- 不改 `scrollToBottom` 的瞬时跳转语义，不引入平滑滚动。
- 不改活动指示条，不合并「圆钮」与「活动条」两个指示器。
- 不给辅助技术新增思考态播报。仓库今天也不播报（`ActivityIndicator` 没有 `aria-live`），不在本轮扩权。
- 不新增 Provider 协议、不落库、不做全站动画系统或无关 UI 重构。

## 3. 方案选择

| 路线 | 做法 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- | --- |
| A. 保留内联，只换图标 | 在 `ChatInterface.tsx:518` 就地加三元 | 差异最小 | 唯一的逻辑分支没有测试载体；`ChatInterface` 已 600+ 行，继续堆嵌套标记 | 不选 |
| B. 抽取模块内组件 + 组件测试 | 新建 `ScrollToBottomAffordance.tsx`，ChatInterface 只传两个 prop | 分支可测，与 `lazyMessageRow.test.tsx` 同构；ChatInterface 净减少标记 | 新增一个文件 | **选择** |
| C. 做成 `src/shared/ui` 通用组件 | 放进共享 UI 层 | 未来可复用 | 只有一个消费方，违反「两个以上模块使用才上移共享层」的规则 | 拒绝 |
| D. 用 CSS 伪元素 / 纯 keyframes 切图标 | 不加组件，靠 class 切换 | 无新文件 | 两个图标共存需要额外 DOM，仍要改 ChatInterface，且更难断言 | 拒绝 |
| E. 顺手做平滑滚动 / 未读数 | 扩大范围 | 体验更完整 | 超出「只做样式」的既定边界，且未读数会触碰 `05-scrolling.md` 的既有规则 | 拒绝 |

## 4. 详细设计

### 4.1 状态输入

复用 `ChatInterface.tsx:431` 已有的：

```ts
const hasActivityIndicator = Boolean(sessionActivity && pendingPermissionRequests.length === 0);
```

传给组件的 prop 名用需求里的说法 `isThinking`，其真值来源是 `hasActivityIndicator`，**不是** `isProcessing`。

选它的理由：`isProcessing` 与 `sessionActivity` 恒等（§1.2 事实 1），二者都无法区分「模型在干活」和「模型在等你授权」。而等授权时活动条已被整块移除、屏幕上换成了权限横幅（§1.2 事实 5），此刻圆钮若继续蹦点，就和可见 UI 自相矛盾。`hasActivityIndicator` 恰好就是「有活动且没在等你授权」，且已在渲染点算好，零成本。

命名上的偏差在组件注释里写明来源，避免下一位读者去找一个不存在的 `isThinking` 状态。

还有一条更强的性质值得写明：**`hasActivityIndicator` 与活动条的渲染条件完全同构**。活动条渲染当且仅当 `activity` 非空且 `!hasPendingPermissions`（`ChatComposer.tsx:279`）；而 `hasActivityIndicator` 就是 `sessionActivity && pendingPermissionRequests.length === 0`（`ChatInterface.tsx:431`）。因此点与活动条**恒定同屏**，不会出现「一个说在跑、另一个说停了」的自相矛盾。唯一差别是活动条退出时多留 220ms（`ActivityIndicator.tsx:22` 的 `EXIT_ANIMATION_MS`），点是立刻回落；这点差异由 §4.2 的交叉淡入吸收，本方案不给点加同样的残留延时。

### 4.2 组件契约与结构

新增 `src/modules/chat/ScrollToBottomAffordance.tsx`：

```tsx
import { ArrowDownIcon } from 'lucide-react';
import { useTranslation } from 'react-i18next';

/** Per-dot animation offsets. The stagger is what reads as motion rather than a row of dots. */
const THINKING_DOT_DELAYS = ['0ms', '150ms', '300ms'];

type ScrollToBottomAffordanceProps = {
  /** True while the turn is visibly running and not blocked on a permission prompt. */
  isThinking: boolean;
  onScrollToBottom: () => void;
};

/**
 * Rendered by chat's ChatInterface above the composer. It is the sole way back to
 * the bottom once the user has scrolled away, so its accessible name describes the
 * action and never changes; the glyph only reports whether the turn is still running.
 */
export default function ScrollToBottomAffordance({ isThinking, onScrollToBottom }: ScrollToBottomAffordanceProps) {
  const { t } = useTranslation('chat');
  const label = t('input.scrollToBottom', { defaultValue: 'Scroll to bottom' });

  return (
    <button
      type="button"
      onClick={onScrollToBottom}
      aria-label={label}
      title={label}
      data-state={isThinking ? 'thinking' : 'idle'}
      className="pointer-events-auto flex h-8 w-8 items-center justify-center rounded-full border border-border/50 bg-card text-muted-foreground shadow-sm transition-all duration-200 hover:bg-accent hover:text-foreground"
    >
      {/* Both glyphs stay mounted and share one grid cell so the swap cross-fades
          instead of flashing, and the button never changes size. */}
      <span className="grid place-items-center" aria-hidden>
        <ArrowDownIcon
          className={`col-start-1 row-start-1 h-4 w-4 transition-opacity duration-200 ${
            isThinking ? 'opacity-0' : 'opacity-100'
          }`}
        />
        <span
          className={`col-start-1 row-start-1 flex items-center gap-1 transition-opacity duration-200 ${
            isThinking ? 'opacity-100' : 'opacity-0'
          }`}
        >
          {THINKING_DOT_DELAYS.map(delay => (
            <span
              key={delay}
              style={{ animationDelay: delay }}
              className={`h-1 w-1 rounded-full bg-current ${isThinking ? 'animate-dot-bounce' : ''}`}
            />
          ))}
        </span>
      </span>
    </button>
  );
}
```

要点：

- 点和箭头都不做条件挂载，靠透明度切换，避免硬切与重排。
- 点用 `bg-current` 描边，直接继承按钮的 `text-muted-foreground` 与 hover 的 `text-foreground`，不需要额外的颜色条件。
- `aria-hidden` 放在包住两个图标的网格层上；按钮的可访问名由 `aria-label` 提供，与状态无关。
- `data-state` 是给测试用的稳定钩子，避免 §6.1 去解析 class 名。它描述的是组件对外状态而非实现细节，不参与任何样式。
- 动画类名也是条件的：空闲态不挂 `animate-dot-bounce`。`opacity-0` 并不会停止 CSS 动画，若常驻挂载则空闲时仍有三个无限 transform 动画在跑；条件挂载后空闲态为零动画开销，而交叉淡入只依赖独立的 `transition-opacity`，不受影响。keyframe 的 `0%` 就是原位，所以切换瞬间不会产生位移跳变。
- 组件只在模块内被 `ChatInterface` 使用，因此**不进** `src/modules/chat/index.ts` 桶。

`ChatInterface.tsx` 的差异（原 `:508-521` 的 `<button>` 整块替换为一行）：

```tsx
<div className="relative flex-shrink-0">
  {isUserScrolledUp && chatMessages.length > 0 && (
    <div className="pointer-events-none absolute -top-11 left-0 right-0 z-20 flex justify-center">
      <ScrollToBottomAffordance isThinking={hasActivityIndicator} onScrollToBottom={scrollToBottomAndReset} />
    </div>
  )}
```

### 4.3 三点跳动 keyframe

加在 `tailwind.config.js:65-88` 的 `keyframes` / `animation` 里，紧邻同类环境动画 `shimmer`：

```js
keyframes: {
  'dot-bounce': {
    // reduced-motion freezes the animation on this frame, so 0% must stay at the
    // element's resting position; moving it would freeze the dots out of line.
    '0%, 80%, 100%': { transform: 'translateY(0)' },
    '40%': { transform: 'translateY(-3px)' },
  },
  // ...existing entries
},
animation: {
  'dot-bounce': 'dot-bounce 1.2s ease-in-out infinite',
  // ...existing entries
},
```

参数取 4px 点、4px 间距、上跳 3px、周期 1.2s、错峰 0/150/300ms。三点加间距共 20px，在 32px 圆内居中留白正常。

周期 1.2s 是有意的，但它与同屏既有的两个 2s 环境动画节奏不同：活动条的 `animate-pulse`（`ActivityIndicator.tsx:93`）与 `shimmer`（`tailwind.config.js:84`）都是 2s。1.2s 属于打字指示器的常见节奏，保留为首选；若真机同屏观察觉得杂乱，把周期调到 1.6-2s 对齐环境节奏即可，属纯参数改动（§7 已列观察项）。

**只做位移，不做透明度变化。** 这是为了 reduced-motion 的降级形态（§4.4）：动画被冻结时，留停在 `0%` 的是三个落在原位的实心点，是一个说得通的静止态；若用透明度做动画，冻结后会得到三个半透明的鬼影。

### 4.4 reduced-motion 与降级

`src/index.css:261-270` 的全局块压三样：`animation-duration: 0.01ms !important`、`animation-iteration-count: 1 !important`、`transition-duration: 0.01ms !important`（`index.css:267`）。它**不处理 `animation-delay`**。因此：

- 每个点在各自的 delay 期间停在自然样式（`translateY(0)`，因为 keyframe 的 `0%` 就是原位），delay 结束后动画在 `0.01ms` 内跑完并结束。
- 最终形态是三个静止实心点，位置正确、无残留位移。满足 §2.2 的 reduced-motion 门槛。
- `transition-duration` 同被压掉，所以 §4.2 的 200ms 交叉淡入在该模式下**同样瞬时完成**，直接落成箭头/点硬切。这是正确的降级形态；实现者不要误以为淡入失效而去「修复」，也不要在组件里加 `motion-reduce:` 覆盖。§2.2 的 200ms 指标因此只适用于允许动效的环境。
- 上述第一条依赖「keyframe 的 `0%` 等于元素基态」这一约定。§4.3 已在 `tailwind.config.js` 的 `dot-bounce` 定义旁加注释固化该约定；若日后有人把 `0%` 改成 `-3px`，冻结态会变成三个错位点，且从 TS/TSX 侧完全看不出来。
- 若日后有人把点改成透明度动画，同样会破坏这个降级形态，需要在 review 时挡回。

### 4.5 无障碍与文案

- `aria-label` / `title` 保持 `input.scrollToBottom`，不随状态变化。理由：可访问名应当描述**动作**，而动作恒为「回到底部」；状态是装饰。该 key 已在 10 个语言文件中存在（`src/modules/i18n/locales/*/chat.json`），本轮**不新增 i18n key**，也就不会产生「是否需要补齐其他语言」的问题。
- 点与箭头都是 `aria-hidden`，不进入可访问树。
- 按钮仍是原生 `<button type="button">`，键盘可达性、焦点环与 hover 态沿用现状。

### 4.6 布局：维持原位，不移动圆钮

首轮评审建议把 `-top-11` 改成 `-top-16`，理由是活动条左侧的状态文案可能横向伸到中央、被圆钮遮住（Claude C3、ZCode Z5）。二轮核查发现该风险在本仓库**不可能触发**，故维持原位。

先厘清一个容易混淆的点：由 §4.1，点与活动条恒定同屏，所以两者 20px 的**竖向共带是常态**。但「共带」不等于「碰撞」——碰撞还需要横向重叠，而横向由两个各自独立的事实决定：

1. **Stop 按钮在几何上安全。** 圆钮命中区固定在中央 32px 内。活动条是 `flex items-end justify-between`（`ActivityIndicator.tsx:91`），Stop 钉在右缘；要让 Stop 落进中央命中区，容器宽需降到约 170-205px（`2 × (Stop 宽度 + 内边距)` 粗估），320px 下仍有充裕余量。此项与评审结论一致。
2. **左侧标签的宽度是有界的，评审担心的「长状态文案」不存在。** 这是二轮核查推翻原结论的地方：

   - `ActivityIndicator.tsx:70` 的 `label` 取 `renderedActivity.statusText || 默认词`。要出现长文案，就必须有人真的产出 `statusText`。
   - 全仓库唯一发出带 `text` 的 `status` 帧的地方是 codex 的 `codex-runtime.provider.ts:426`，其 `text` 恒为 `'token_budget'`，而该值在 `useChatRealtimeHandlers.ts:334` 就被 `if (msg.text === 'token_budget' && msg.tokenBudget)` 拦截，永远走不到 `:341-344` 的 `statusText` 赋值。
   - 周期轮询那条路也注入不了：服务端 `listRunningSessions()` 返回 `{ sessionId, provider, startedAt, lastSeq }`，**没有 `statusText` 字段**（`server/modules/providers/services/sessions.service.ts:156-163`），所以 `SessionProtectionContext.tsx:104` 读到的永远是 `undefined`。
   - 唯一另一处写入是发送时的 `statusText: null`（`useChatComposerState.ts:870`）。

   因此 `label` 恒为六个有界默认词之一（`ActivityIndicator.tsx:13-21`，最长 "Processing"），每 4 秒轮换，再拼上耗时。

3. **按有界标签重算最坏宽度**：`px-3`(24) + 两个 `gap-2`(16) + 点(6) + 边框(2) ≈ 48px 固定开销，最长标签 ≈ 65px，耗时取极端 `120m 5s` ≈ 42px，合计约 155px。
   - 375px 宽（当前最小常见机型）：活动条行宽 359px、半宽 179.5px，标签右缘落在中心左侧约 24.5px 处，**距圆钮仍有约 8.5px 余量**。
   - 320px 宽：半宽 152px，最坏情况下标签右缘越过中心约 3px，与圆钮重叠约 19px。
   - 320px 对应 iPhone SE 一代 / iPhone 5，且还需叠加「单轮耗时超过 100 分钟」才构成最坏情况。

**结论：维持 `-top-11`。** 该移动修正的是一个在本仓库不可达的缺陷（375px 下有 8.5px 余量，320px 才是极限且已属淘汰机型），却会改变空闲态圆钮的高度（20px）——那是用户已经验收过的视觉。不值得。

**改为移动的触发条件（任一条成立即重新评估）**：任一 Provider 开始发出真实 `statusText`；或明确要求支持 320px 宽机型。

由于 `hasActivityIndicator` 不驱动位置，圆钮在状态切换时不会移动，不存在跳动。上述宽度数字为按类名与字号估算，**未在真机量取**；§7 保留一项量测记录以校正 §1.2 事实 3 与本节。

### 4.7 明确不做的事

- 不改任何定位类名（含 `-top-11`），不改尺寸、`z-index`；理由见 §4.6。
- 不给圆钮本身加挂载/卸载动画。它的进入退出仍是硬切，与现状一致；这次只解决图标之间的过渡。
- 不加未读数。见 §2.3。

## 8. 风险与回滚

| 风险 | 表现 | 控制 |
| --- | --- | --- |
| **运行中闪回箭头** | 轮次尚未结束，点瞬间变箭头再变回来，每次翻转都是一次 200ms 淡入，读作闪烁 | 真实机理**不是**「流式/工具数据间隙把 `sessionActivity` 清空」：加工地图的写入口只有三处（`useSessionProtection.ts:53/81/103`），流式间隙不触发其中任何一个。真正的窗口是 5s 周期轮询 `api.runningSessions`（`SessionProtectionContext.tsx:119-122`）整体替换地图时，本地条目在 10s 宽限期（`LOCAL_ACTIVITY_GRACE_MS`，`useSessionProtection.ts:8,130`）之外且未被服务端列出，就会被删掉。控制：§7 单列「连续跑完一整轮不闪回箭头」为必测项，单轮需超过 10s |

> [!IMPORTANT] 关键信息 (Q1 / §4.1 / §6.1)：本方案最承重的决策——「等授权时不蹦点」——在组件边界上无法被自动化覆盖。
> `isThinking` 是布尔 prop，一旦进组件，「运行中」与「等待授权」两个分支就坍缩成同一个 `isThinking=false`；§6.1 只能断言「false → 箭头」，区分不了「传错状态源」这个真实 bug。§8 风险表也自认「§6.1 不直接覆盖该分支，靠 §7 人工验收」。建议二选一：① 补一个极小的 ChatInterface 级接线测试（断言传入 `isThinking` 的来源是 `hasActivityIndicator` 而非 `isProcessing`，或 mock `pendingPermissionRequests>0` 时组件收 `isThinking=false`）；② 若坚持只测组件，至少在 §8 风险表里把该分支从「人工验收」升级为「必须真机验证」并写明回归方式，避免回滚热修。

> [!WARNING] 潜在风险 (Q10 / §2.1 目标2)：`isThinking` 全程是否持续为真未被验证，存在「运行中途闪回箭头」的可能。
> `processingSessions` 的状态翻转完全由协议事件（`markSessionProcessing`/`markSessionIdle`）驱动（`useChatRealtimeHandlers.ts:140-171`）、跨空闲间隙、工具调用边界与断线重连。若某段数据流间隙让 `sessionActivity` 瞬时落空，`hasActivityIndicator` 会 false→true 反复翻转，每次翻转都是一次 200ms 交叉淡入——恰好复现 §2.1 目标 2 要禁止的闪烁。建议：① §7 增加一条「运行中且轮次内部有流式间隙/工具调用间隙」的验收项，真机确认连续跑完一整轮不闪回箭头；② 若无法天然连续，考虑给 `isThinking` 加极短的去抖/hold（例如翻转后至少保持到下次流事件），本方案当前未覆盖。

> [!WARNING] 潜在风险 (Q6 / §4.6)：压叠窗口并非「320px+长文案」才出现，普通运行态就存在，且恰逢用户最需要 Stop 的时刻。
> §1.2 事实 5 说明活动条只在**等授权**时被移除；所以「点+活动条同屏」的运营常态恰恰是「运行中（非等授权）」，此时圆钮与活动条竖向重叠 20px 是常态，不是特例。而 §4.6 把它描述成「约 320px 宽 + 状态文案很长」才触发，低估了场景。更关键：运行中用户唯一的中断途径（活动条右侧的 Stop）此刻正位于一个 `pointer-events-auto z-20`、且因跳动点而更显眼的透明底按钮之下。这与现状（静态箭头）同构、非新增风险，但利害关系明显上升。建议优先直接落地 `-top-16`（一劳永逸），或至少在 §7 确认 320px 宽度下 Stop 不落在按钮命中区内，再决定保留兜底。

> [!TIP] 建议 (Q9 / §6.1)：加 `data-state="idle"|"thinking"` 作为稳定断言钩子，比读 class 更稳妥，且不算「为测试改产品代码」。
> 用透明度表达状态的代价是 §6.1 不得不解析 class 名才能区分箭头/点。补一个 `data-state` 属性（放在按钮或图标网格层上）既是常规、无副作用的测试钩子，也让断言从「实现细节（class 名）」解耦到「对外状态」，将来改 class 不必连带改测试，同时避免 §6.1 提出的「集中 helper 仍需跟随重命名」的脆弱性。可顺带用于 §2.2 的「切换不改尺寸」断言。

> [!NOTE] 补充说明 (Q3 / §4.3)：reduced-motion 的冻结形态推理成立，但依赖「delay 期间渲染基态」这一约定，建议在断言里显式兜住。
> 事实 8 确认只压 `duration` 与 `iteration-count`、不压 `animation-delay`：每个点会在自己的 delay（0/150/300ms）期间停在基态、随后 0.01ms 内跑完并落回 `translateY(0)`，最终静止三实心点、无位移残留——推理自洽。唯一脆弱点：这个结论依赖「keyframe `0%` 与元素基态都落在 `translateY(0)`」，一旦日后有人改动 keyframe 的 `0%`（例如改成 -3px），冻结态会变成「三个错位点」，review 时无法从代码判断。建议在 `tailwind.config.js` 的 `dot-bounce` 定义旁加一行注释：`/* reduced-motion relies on 0%==basic state (solid dots) */`，或让 §6.1 增加一条 `matchMedia('(prefers-reduced-motion)')` 下的渲染断言。

> [!NOTE] 补充说明 (§1.2 事实 3 / §4.6)：整条窄屏边界都压在「类名推算、未真机量取」的几何数字上。
> §1.2 事实 3 明确标注 20px 重叠、`-44 ~ -12`、`-32 ~ 0` 均为类名推算；§4.6 的 320px 结论与 §7 压叠项都建立在它之上。建议在 §7 真机验收时补一条量测记录（真机 320px + 手动量取实际渲染偏移），并回填校正数字，避免未经验证的几何模型长期成为后续决策依据。

> [!NOTE] 补充说明 (§4.4 / `src/index.css:267`)：reduced-motion 还会同时压掉 200ms 交叉淡入，方案正文漏了这一条。

> [!NOTE] 补充说明 (Q6 / §4.6)：几何上 Stop 抢不到点击，能压上的只有左侧状态标签，验收观察点应相应调整。

> [!TIP] 建议 (Q4 / §4.3)：留意与相邻环境动画的节奏协调，低风险审美项。

**1. `-top-16` 撤回，维持 `-top-11`（推翻本轮第一轮结论）**
