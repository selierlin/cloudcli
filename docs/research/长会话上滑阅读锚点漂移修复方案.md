## 0. 结论先行

用户报告「往上滚动有跳帧感、不够流畅、不知道当前划到哪去了」。定位结果不是流畅度问题，而是**阅读锚点被程序性破坏**：

1. 懒加载行「卸载后留占位」的方案，对**从未测量过**的行使用 100px 估算高度（`LazyMessageRow.tsx:25`），而真实行高由内容决定。上滑时，视口上方的占位行会在此位置被挂载成真实内容，**在唯一一次滚动还原之后**继续长高，把下方正在阅读的内容推走。
2. 应用对 prepend 只做**一次**同步还原（`useChatSessionState.ts:626-639`），且这次的几何基准是占位高度；此后没有任何再校正机制（chat 模块内无 `ResizeObserver`，跟随循环在用户上滑时主动退出 `useChatSessionState.ts:1050-1071`）。
3. 该设计明确把兜底交给浏览器 scroll anchoring（`LazyMessageRow.tsx:18-21`、`../architecture/05-scrolling.md:477-478,492-494`），但 **WebKit/Safari/iOS Safari 不实现该特性**（caniuse `css-overflow-anchor`，2026-09-15 复核：Safari 3.1–26.6、iOS Safari 3.2–26.6 逐版本均为「不支持」，仅 Technology Preview 为「支持」，全球覆盖 79.8%）。这直接违反本文关联方案已裁定的原则——「原生 scroll anchoring 只能视为平台优化，不能成为正确性前提」（`动态对话流布局稳定性场景与验证方案.md:386`）。
4. 即使不依赖平台差异，`loadAllMessages` 捕获的还原状态也存在**不被执行**与**过期后被执行**两条路径（§3.1 S8），说明「已捕获锚点」不等于「已校正」。

按本文关联方案 §1.4 的失败定义（「用户阅读的文本离开原位置超过 8px，且不是用户手势导致」），这是**已定义的用户可见失败**，而非观感问题。

本文给出机制链（§3）、与既有已决规则的关系（§4）、方案候选与取舍（§6）、推荐方案契约（§7）、验收标准（§8）与 harness 缺口（§9）。

### 3.2 针对 S4 的补充说明

S4 **不是实现疏漏，而是架构文档明示的取舍**：`loadEarlierMessages` 之后「只有浏览器的原生锚定在支撑位置」（`../architecture/05-scrolling.md:542-546`）。因此本方案对 S4 的主张不是「发现了未记录的缺陷」，而是**该依赖本身不成立**：

1. WebKit（含 iOS Safari / Capacitor WKWebView）没有这项浏览器特性（S3），此时是整个插入高度直接体现为位移。
2. 即使在 Chromium 上，插入的是占位（S1，其中新窗口首个可见 user turn 之前的行是 0px `hidden`、之后的行按 100px 占位），原生锚定只能按占位几何做一次校正；这些行其后扩张时还需要第二次校正，而这一次同样没有保障。
3. 触发条件明确且可达：`!hasMoreMessages && chatMessages.length > visibleMessageCount`（`ChatMessagesPane.tsx:405-418`），即「消息已全部在 store 中但未全部渲染」的会话（例如刚执行过加载全部、或非分页 Provider）。

所以 S4 是**最容易复现、也最容易修的一条**（D1）。

同一处门控还产生 S8：`loadAllMessages` **捕获了**锚点（架构文档 `:543-544` 也据此写「`loadOlderMessages` 和 `loadAllMessages` 都捕获锚点」），但消费它的 effect 只在 `chatMessages.length` 变化时运行。也就是说「已捕获」不等于「已校正」——这条与 S4 同源，说明缺陷不在某一次采样写错，而在**把还原绑定到错误的驱动信号**（D1 同时覆盖 S4 与 S8）。

## 6. 方案候选与取舍

### 方案 A：阅读锚点跟随器（推荐，主修）

**机制**：把「一次性还原」改为「锚点跟随至几何稳定」。**基线直接复用 W2 的采样**（`captureScrollRestoreState`，`useChatSessionState.ts:105-119`），W6 不二次捕获；此后在几何变化时重放偏移校正，直到连续两个不同 rAF 帧中同一锚点的 `getBoundingClientRect().top` 与 `scrollHeight` 均不再变化（沿用既有 §12.3 的收敛判据）。**首个校正必须发生在 paint 之前**（在 `ResizeObserver` delivery 内同步写，见 §7.2），否则会先被画出一帧 >8px 的位移。

- 改动面：`useChatSessionState.ts`（新增 W6 写入者与 claim）、一个新 hook（建议 `src/modules/chat/hooks/useReadingAnchorFollower.ts`）、`LazyMessageRow` / 内容容器上加一处 `ResizeObserver` 触发源。
- 优点：跨引擎有效（不依赖 `overflow-anchor`）；同时覆盖 S1/S2/S3/S5/S6/S8；对既有 writer 是叠加而非替换。
- 代价：新增一个滚动写入来源，必须纳入既有的所有权与同帧仲裁规则（`05-scrolling.md:229-245`）；收敛窗口需要明确上限与失败放弃路径。
- 覆盖范围的两条边界（本轮采纳）：**S5 的 0px↔真实高翻转没有可缓存的中间态，只能由 A 的跟随补偿**（Claude R4）；**隐藏行不参与缓存、也可能迟到挂载**（ZCode RS-9 (a)(b)）。
- 不覆盖：S7（需方案 B 的测量规则）、P1–P3。

### 方案 B：行高缓存按稳定身份持久化（**第 3 轮已移出本轮实施集**，仅保留候选分析）

**机制**：`measuredHeight` 目前是行组件局部 state（`LazyMessageRow.tsx:50`），行卸载、换 key、切会话即丢失。改为按稳定身份缓存到 transcript 级 Map，并按已决 T10 规则只写入稳定终态高度。

- **缓存键（本轮改定，采纳 Codex RS-4，否决 Claude R5 的裸 `timestamp`）**：改用**实际行身份**，即 `ChatMessagesPane.tsx:262-266` 的 `getMessageKey`（工具组用其现有 fragment key 对应的行 key，`ChatMessagesPane.tsx:431-458`），并以 `sessionId` 命名空间隔离（`sessionId + rowKey`）。
  - 理由：`ChatMessage.timestamp` 只声明为 `string | number | Date`、没有唯一性契约（`src/shared/types.ts:321`），现有测试就构造了同 timestamp 的多条工具消息（`src/modules/chat/tests/toolGrouping.test.ts:19,28,34`）；`getIntrinsicMessageKey` 最终回退到「类型 + timestamp + 工具名 + 内容前缀」（`messageKeys.ts:12-37`），工具组 wrapper 的 timestamp 只代表组内一条消息（`toolGrouping.ts:197`）。
  - **对一条支撑论证的修正**：`ChatMessagesPane.tsx:244-260` 的 occurrence 消歧**不是**「prepend 时新行占用 0..N 与既有行冲突」——它从尾部编号（`:253-258`），而 `visibleMessages` 始终是 `chatMessages` 的后缀切片（`:1038-1041`），后缀增长下既有行的编号不变。真正的弱点是该 key 是**每次渲染从可见窗口派生**的，不是跨会话/跨内容变化的持久身份，故需 `sessionId` 命名空间并接受「缓存只是误差优化」。
  - **rowKey 的可变性边界（本轮新增核验）**：该编号**只对 prepend 稳定，对追加不稳定**。编号自尾部向前（`:253-258`），`seen === 0` 者取得**裸 key**；当新消息追加到尾部且其 intrinsic key 与某既有行相同时，新行取得裸 key、原持有者前移为 `__1`——即**既有行的 key 变化**。仅当 `getIntrinsicMessageKey` 走到无 id 类字段的兜底分支（`messageKeys.ts:12-37`：`id`/`messageId`/`toolId`/`toolCallId`/`blobId`/`rowid`/`sequence` 全部缺失 → `type + timestamp + toolName + contentPrefix`）才会碰撞。因此：作为**本次渲染内的定位身份**可用；作为**持久缓存键**必须绑定该 caveat（建议缓存键只在行 key 落到 id 类分支时视为持久，兜底分支的行随内容/尾部变化失效）。
- **只能缓存非隐藏行的稳定终态**：`hidden` 行（`LazyMessageRow.tsx:80`）为 0px，没有可缓存的中间态，S5 的补偿归方案 A。
- **B 的前置：稳定视图行身份——本轮核验后发现该前置不存在，且提案的身份源不可用（第 3 轮新增）**。Codex RS-24 / ZCode RS-30 主张在 `normalizedToChatMessages` 定义「稳定视图行 id」，并让 React key / W2·W6 锚点 / `data-transcript-row-key` / B 缓存键**统一消费 `NormalizedMessage.id`**。牵头接受其**诊断**（见 §7.1 不变量 5），但**不接受该身份源**，三条核验如下：
  1. **该字段目前根本到不了前端**：`NormalizedMessage.id` 在类型上是必填（`src/shared/types.ts:441`），但 `ChatMessage` **没有显式 `id` 字段**（`types.ts:317-364`，只有末尾的索引签名 `[key: string]: unknown`），`getIntrinsicMessageKey` 仅**经索引签名**尝试读取它；而投影 `useChatMessages.ts` 的 `sharedMetadata`（`:189-201`）与 text 分支（`:204` 起）**从未写入 `id`**，且全文没有 `...msg` 整对象展开 ⇒ 前端 `ChatMessage.id` **恒为 `undefined`**，`getIntrinsicMessageKey` 的 `id` 分支今天从不生效。RS-24 的 (a) 成立。
     - **一处类型证据更正（第 4 轮，采纳 Codex RS-34 / ZCode RS-40）**：本文此前写的「`ChatMessage.id?` 存在（`:733`）」**是错的**——`:733` 的 `id?: string` 属 `TodoItem`（`types.ts:732` 起）。运行时结论不变（索引签名仍可读、当前恒 `undefined`），但该错写会误导后来的身份设计者以为前端类型已承诺该字段语义，故一并更正 §13 #22。
  2. **该字段本身不唯一**：WorkBuddy 把 `function_call` 的 `id` 设为**该批次父消息的 id**（`workbuddy-sessions.provider.ts:594-600` 同时写 `toolId: event.callId` 与 `id: event.id`），而一个 assistant 行可并行发出多个工具调用。复现会话 `93bb396f` 实测：`function_call` 194 行只有 174 个不同 id，**12 组重复**，最坏一组 **6 行同 id**（`f415d76e…` = 六个 `TaskCreate`）。此外 `id` 在适配器不提供时是**每次归一化新生成的随机值**（`server/shared/utils.ts:348-352` `id: fields.id || generateMessageId(...)` → `msg_${randomUUID()}`；`server/` 内 137 处 `createNormalizedMessage` 有 51 处不传 id，且**全部 runtime provider 都不传**）。
  3. **采信它会主动造成回归**：`getIntrinsicMessageKey` 的候选顺序是 `id, messageId, toolId, toolCallId, …`，**取第一个真值即返回**（`messageKeys.ts:13-28`）。今天 `id` 恒为 undefined，工具行于是落到 `toolId`（= 唯一 `callId`，已由投影传至前端，`useChatMessages.ts:110,291,386`）⇒ **工具行 key 今天是唯一的**。一旦按 RS-30 把 `id` 送达前端，`id` 将**反超**唯一的 `toolId`，上例那一批 6 个 `TaskCreate` 行会得到**相同的 React key**——从「key 在追加时可能重编号」退化为「key 直接重复」，属明确回归。
  - **对第 2 轮处置的自我更正**：我在第 2 轮把「rowKey 能作持久缓存键」的边界定为「只对 prepend 稳定、对追加不稳定」。该结论仍成立，但**不完整**——它默认了 `id` 分支可用；实际是 `id` 从不参与，碰撞面在**兜底分支**（`type + timestamp + toolName + content[:48]`）。兜底分支在本会话实测有 2 处碰撞（两条 `function_call_result` 同 timestamp 且内容前缀为空串），但**不在**纯文本 `message` 行上（45 行零碰撞）。故「追加碰撞」在本会话是可达的，但主要发生在工具行，而工具行今天恰好被 `toolId` 保护。
  - **因此**：B 的缓存键所依赖的「稳定行身份」**目前不存在**，B 无法在本轮实现。详见 §7.1 不变量 5（验收采样改用「元素 + 语义指纹」）与 §11（稳定行身份列为独立立项）。
- **缓存条目需要几何 epoch（采纳 Codex RS-5）**：行高同时取决于消息列宽（`ChatMessagesPane.tsx:348` 的 `max-w-[54.25rem]` 与内边距）、viewport、字体就绪、以及用户手动展开的 disclosure 状态。条目除行键外至少绑定容器宽度/布局版本，并在 resize、font ready、影响高度的展示偏好与 disclosure 变化时失效或重测；会话切换时隔离或释放。
- 优点：直接消灭「100px vs 真实高度」这一类误差；让占位在二次访问时几何精确。
- 不覆盖：首次访问该段历史（仍会从估算值扩张）→ 必须与 A 同时存在。**B 只降低校正量，正确性由 A 保证。**

| D3 | 上滑（detached）期间缩小上方挂载带、或延后上方行的挂载 | S1、S2（须权衡：会让上滑时内容到达变慢，**不建议默认开启**）。**本轮定性（采纳 Codex RS-17 / ZCode RS-19）**：D3 只**缩小或延后**挂载带（现有观察带为 `rootMargin: 1200px`，`useLazyRowObserver.ts:5,51`）；用户持续上滑时未测量行仍要进带、仍要从 100px 扩张到真实高度，**不消除 S1/S2**，且完全不覆盖 S5 与 RSC02。故 D3 只作为实验开关／取证对照，**不得作为等价修复候选** |

本节的四个方案分两个层次，不构成二选一：

- **本轮实施集（第 3 轮改定，采纳 Codex RS-27 / ZCode RS-32）**：**A + D1 + D2**。A 解决机制，D1/D2 消除两条确定性位移源。**方案 B 移出本轮实施集**，只保留其候选分析与前置条件（上面那条），触发指标预埋在 A 的诊断输出里（单次 prepend 的校正总量、RO 波次数、二次访问同段历史的校正频率）；A+D1+D2 落地后按数据决定是否立项。两条独立理由：其一，B 的缓存生命周期（session 命名空间、几何 epoch、字体/宽度/disclosure 失效、内存上界）会在修用户可见漂移的同时引入一套尚无性能数据支撑的复杂度；其二，B 的缓存键以「稳定行身份」为前提，而该前提经本轮核验**并不存在**。Claude R17 主张保留在「完整推荐集」，本裁定以 RS-27/RS-32 为准（R17 的「不与正确性耦合」这一内核完全一致，仅止于「是否仍列为本轮集」）。
- **正确性最小集 = 本轮实施集 = A + D1 + D2**（B 已移出，故两个层次本轮重合）。
- **删除 W6 的唯一条件**：实测证明**全部 P0 场景（尤其 RS05、RSC02）**在无 A 时仍满足 8px。不得以「去掉 S5 后的实测残差」为据删除——那等于把 S5 的漂移排除出测量范围再宣布通过。
- **B 的复位条件**：A+D1+D2 的诊断数据证明校正量、RO 波次或二次访问成本仍超预算时，以独立任务启用 B；启用前须先完成 §11 的「稳定行身份」立项。

## 7. 推荐方案的实现契约（待审阅）

### 7.1 不变量

1. **位移口径（本轮改定）**：在不含真实输入的帧序列中，固定阅读锚点相对基线的**最大绝对**位移不得超过 8px，**且**不得出现「先被画出、再回位」的可见位移；两项都记，互不替代（沿用 `动态...:384`、`:66`）。
   - **为什么不是「放宽到稳定后 ≤8px」**：Claude R1 认为「占位扩张 >8px」与「全程 ≤8px」在数学上不可兼得，因此应把阈值放宽。该推导漏掉了**校正可发生在 paint 之前**这一条路径：`ResizeObserver` delivery 位于同一帧的 layout 之后、paint 之前，在其中同步写 `scrollTop` 可以让该帧从未被画出（Codex RS-6）。所以二者并不互斥，本方案要求的是「没有已绘制的 >8px 帧」，而不是放宽阈值——放宽会推翻关联方案已裁定的「两类指标互不替代、不能只看最终帧」。
   - **诚实边界**：若某目标平台实测无法保证 pre-paint 校正，必须在本文件显式记录该平台并单独放宽，不允许在保留本不变量文字的同时用纯事后 rAF 实现（Codex RS-6）。
   - **必须与不变量 3 同句绑定（采纳 Claude R11）**：pre-paint 校正恰好落在「单次 `ResizeObserver` delivery 至多一次增量写入」的上限边缘——连锁 RO 的第二次校正会被静默丢弃。因此本不变量的实现口径是「pre-paint 校正 + 单次 delivery 至多一次增量写入，残余差交给下一帧的稳定判定」，两条不得分开实现；RS01 需同时断言不出现 RO loop 诊断（ZCode RS-11）。
2. 跟随器是**临时 claim**：真实 `wheel` / `touch` / 键盘手势在下一次视觉位移前终止跟随，且不得改写所有权。**定界（本轮补充）**：终止只作用于 W6；`isNearBottom()` 带内（`useChatSessionState.ts:511-516`，阈值 50px）的贴底跟随仍属 W1，不因手势被冻结——现有实现是从 `isNearBottom()` 反推 detached（`:583-584`），不是「任何手势即脱离」（否则会改变已决的近底语义，Claude R2 的建议需按此收窄）。
3. 跟随器不得让 `bottomGap` 恶化；`AUTO_FOLLOW` 路径下不得与之竞争。**同帧至多一次程序化 `scrollTop` 写入**，且单次 `ResizeObserver` delivery 内至多一次**增量**校正，残余差交给下一帧（Codex RS-6 / ZCode RS-11：RO 回调内重复写入受同帧 delivery 上限约束，超限后该帧后续通知会被静默丢弃）。
4. 收敛必须有上界，但**按波次而非墙钟**（ZCode RS-10 修正 Claude R3）：一次 prepend 的扩张集中在少数几波（IO 初始通知按 observer 批量派发 + React 18 批量提交），上界取「波数 × 每波稳定帧数」（沿用既有 2 帧判据），并对每波输出诊断；超时即放弃并记录，不得长期占用写入权。
5. **锚点身份与有效性**：取自卸载后仍在 DOM 的元素，即行 wrapper，而不是 `.chat-message`（后者随卸载消失，`MessageComponent.tsx:118-121` 与 `LazyMessageRow.tsx:76`；架构文档也承认现有锚点扫描「只可能命中当前已挂载的行」，`../architecture/05-scrolling.md:466-471`）。**但「常驻」不等于「有效」，且定位不能用 `timestamp`（本轮改定，采纳 Codex RS-15 / ZCode RS-21）**：
   - 定位属性改用 wrapper 上的 `data-transcript-row-key`，值与 `messageKeyMap` 派生一致（普通行取该行 `messageKey`，工具组行取**组首行** key，`ChatMessagesPane.tsx:447,499`）；**不再用 `data-message-timestamp` 定位**——`timestamp` 无唯一性契约（`src/shared/types.ts:321`），同 timestamp 多行与工具组 wrapper（`toolGrouping.ts:197`）都会让 `querySelector` 静默选中错误行。现有 `findRenderedMessageElement`（`useChatSessionState.ts:39-70`，仅用于搜索跳转 `:978`）就是「命中第一个精确匹配」的写法，属同一隐患面。
   - 该属性一份服务两处消费：§8.3/H2 的采样定位、本条与下条的锚点资格复检——避免为验收再引入第三套身份体系（ZCode RS-21）。**第 3 轮改定**：原列的第三处消费（方案 B 缓存键）随 B 移出本轮而撤销（§6）；且属性值**不得**被当作持久身份（见下条）。
   - 捕获时排除 `[hidden]`、零尺寸、以及 `truncated:` 组成员；每次校正前复检 `getClientRects().length > 0`；若原锚点被投影收起，必须用补页前同时记录的、不参与该组折叠的后继可见行做无跳交接。
   - **采样器不得重新查询定位**（Codex RS-15）：开始时持有具体 `HTMLElement`，每帧校验 `isConnected`。
   - **判定口径（第 3 轮改定，采纳 Codex RS-24 / ZCode RS-30 的诊断，推翻本人在第 2 轮的裁定）**：**「同一节点 + `isConnected`」不足以判定「锚点未换行」**。机制：`messageKeyMap` 的 occurrence 编号自尾部向前、`seen === 0` 者取裸 key（`ChatMessagesPane.tsx:248-262`）；尾部追加一条 intrinsic key 相同的行时，列表从 `[A: K]` 变为 `[A: K__1, B: K]`，React 按 key 协调会把**旧 `K` 节点复用给 B**，A 改由新建的 `K__1` 节点渲染。此时采样器持有的节点仍 `isConnected`、属性值仍为 `K`，**语义行已从 A 换成 B**——按节点身份会把它判为通过。**改定后的硬失败条件**：元素引用 + **语义指纹**（pin 时刻记录的该行稳定内容标识，如 `type + timestamp + 内容摘要`）二者同时保持一致；节点换而语义不变、或语义变而节点未换，都必须按明确规则处理——**语义指纹变化一律判失败**，节点被替换但指纹一致则记诊断。
     - **为什么不采纳 RS-24/RS-30 提出的身份源 `NormalizedMessage.id`**：该字段不唯一且在复现会话中确有重复（12 组、最坏 6 行同 id），且采信它会让 `id` 反超今天唯一可用的 `toolId`。完整证据与影响面见 §6 方案 B 的三条核验与 §13 #22–#24。**这一条同时是给 RS-24/RS-30 作者的回应：诊断采纳，身份源不采纳**，需其确认或给出「以 `id` 为身份且不产生重复 React key」的方案。
     - 需补的负向 fixture 相应改定为两类：重复 timestamp、以及**同 timestamp 同 48 字符前缀**的追加行（后者正是兜底分支的碰撞形态）。
     - **指纹判据自身的碰撞面与「受控锚点」前置（第 4 轮新增，采纳 Codex RS-36 / ZCode RS-41；Claude R22 的观察成立但严重性被低估）**：上述硬失败条件是「元素引用 + 语义指纹」同时不变，因此**它与指纹的唯一性同生共死**。复现会话里确有 2 条退化 `function_call_result`（同 timestamp、`toolName` 为空、内容前缀为空串），其指纹逐字符相同 ⇒ React 若在它们之间复用节点，两项检查**双双不变**，P0 的「锚点未换行」会在真实换锚时**通过**。这不是「多记一条诊断」，而是直接削弱正确性验收。反向问题同样成立：若采样锚点本身仍在流式更新，内容摘要指纹会在语义行未变时变化 → **假失败**。因此收紧为：
       1. **锚点必须由 fixture 受控选择**：内容不再更新（非流式、非当前进行中的回合）、且在采样时刻渲染窗口内**完整语义指纹恰好出现一次**的普通行。
       2. **唯一性是 pin 时的硬前置**，不是场景内检查：pin 前做一次 `querySelectorAll` 计数并要求 `=== 1`，不满足即**拒绝开始采样**（成本可忽略）。
       3. **指纹不使用 48 字符摘要**：用完整受控内容，或直接在 fixture 消息 content 末尾写入专用唯一标记，使唯一性由构造保证而非依赖碰撞概率。该标记只存在于 fixture 数据，不进入生产代码。
       4. **声明已知局限**：退化行（同 timestamp、空 `toolName`、空内容前缀）**不得作为采样锚点**；负向 fixture 按「工具批次」构造重复（而非两条文本，见 §14 第 3 轮新增项 #2），并断言非唯一候选在采样开始前被拒绝。
       **边界**：本条只修复**验收采样**的可信度，不产出稳定行身份（那是 §11 的独立立项）；因此它不改变 §7.1 前四条不变量，也不影响 W6 的校正逻辑。
6. **基线唯一性**：W6 的 `(anchor, anchorOffset)` 必须复用 W2 在 `captureScrollRestoreState`（`:105-119`）采样的同一份，不允许二次捕获；且每次**真实输入**都要推进该基线（Codex RS-3：异步分页等待期间的滚动不得被回程校正抵消）。

### 7.2 落点与顺序

- 写入者编号延续 `05-scrolling.md` 的 W1–W5 约定，新增 W6（阅读锚点跟随）。
- **基线衔接（采纳 ZCode RS-8）**：W6 不自行捕获基线，直接复用 W2 采样（`:105-119`）的 `(anchor, anchorOffset)`。若 W6 在首次 RO delivery 时才捕获，而 IO 扩张此时已 commit，W6 会把扩张后的位置当成基线，对 S1/S2 零补偿。
- **首个校正只允许出现在 RO delivery**，禁止用 `useLayoutEffect` 做 W6 的校正路径：React 的 layout effect 按 fiber 完成顺序执行（子先于父），W6 所在层级与持有 W2 的 hook 之间的先后无法由 hook 自身保证；而 RO delivery 天然晚于 W2 的 layout effect，也天然早于 paint。
- **W6 在贴底带内不启用**：`isNearBottom()` 为真（阈值 50px）的区间归 W1，否则不变量 3 的「同帧至多一次程序化写入」没有可执行的归属规则。
- 触发顺序：prepend 还原（W2）→ W6 接管后续帧直到收敛 → 收敛后释放。收敛按波次计数（不变量 4）。
- 与搜索跳转（W5）、初始 settle（W4）、跟底（W1）的互斥关系需在文档中显式定义，并补进 `05-scrolling.md`。
- **分页等待期的交错（采纳 Codex RS-3）**：`handleScroll` 在 `scrollTop < 100` 后 await `fetchMore`（`:578-615`），用户可在等待期间继续产生输入。W6 应按不变量 6 把真实输入推进为**新基线**，只补偿基线之后由 DOM 几何变化产生的增量；测试须覆盖「`fetchMore` 未决时连续 wheel」「commit 前最后一次 wheel」「commit 后首帧 wheel」三个交错点。

### 8.3 判据与采样

沿用 `动态...:376-384` 的口径：残差必须基于**场景指定的固定阅读锚点**（而非最后一行），由 `data-transcript-row-key` 定位（见 §7.1 不变量 5），并同时记录相邻帧位移与最终残差。阈值 8px 需在真机基线上重新校准后回写本文与测试配置。

**锚点固定方式（第 3 轮补充，第 4 轮收紧）**：定位**只在采样开始时进行一次**，随后持有 `HTMLElement` 引用 + pin 时刻的**语义指纹**，每帧校验二者；指纹变化一律判失败（§7.1 不变量 5）。不得每帧用 `querySelector` 重新定位——`querySelector('[data-transcript-row-key=…]')` 一旦 key 重编号或属性重复，会静默选中另一行。**第 4 轮收紧（Codex RS-36 / ZCode RS-41）**：指纹必须来自**受控**锚点——非流式、且在 pin 时刻渲染窗口内**完整指纹恰好出现一次**（`=== 1` 为硬前置，不满足即拒绝采样）；指纹用完整内容或 fixture 专用唯一标记，**不用 48 字符摘要**（摘要会让两条退化工具结果同指纹 → 真实换锚被判通过）。受控标记只存在于 fixture 数据，不进入生产代码。

**必须补两项采样能力（Codex RS-1，公式经 RS-14/RS-20 更正）**：

1. 现有写入拦截只记 API 名与时间（`tests/transcript-layout/transcript-layout.spec.ts:38`），**无法从 `scrollTop` 变化中分离用户滚动与 W6 校正**。需记录每次程序写入的**目标元素、写入前后值、来源（W1–W6）**；fixture 驱动的可控滚动标记为独立来源 `USER_INPUT` 并同样记录前后值，真实 wheel/touch 场景用事件区间与程序 writer 日志重建实际用户增量。
2. **残差定义（唯一口径）**：`residual = ΔanchorTop + U`，其中 `U` 为区间内**实际生效**（clamp 后）的用户滚动增量，带符号；无真实输入时 `U = 0`，退化为 `ΔanchorTop`。
   - **为什么不是 `Δ(anchorTop + scrollTop)`**：`anchorTop + scrollTop` 等于锚点在滚动内容坐标中的位置 `contentTop`（几何恒等式 `anchorTop = contentTop - scrollTop`）。prepend 或上方占位扩张使 `contentTop` 增加 `H`，而 W6 的正确动作正是 `scrollTop += H` 以保持屏幕位置——此时实现完全正确，`Δ(anchorTop + scrollTop) = H ≠ 0`。原公式会把**正确实现判为失败**（Codex RS-14 主动撤回其上一轮建议）。
   - **`ΔanchorTop = -ΔuserScroll` 也不是通用断言**：该恒等式只在**无布局变化**的帧成立；扩张帧中 W6 校正使 `ΔanchorTop = 0` 而用户仍滚动了 `u`，等式不成立（ZCode RS-20）。
   - 程序写入的 `scrollTop` 增量**不并入** `U`，只用于证明未越权、未重复写入。

### Codex · 审阅（2026-09-15）

我在当前工作区（含姊妹方案 WIP）核对了滚动还原、懒挂载、过程投影、消息键和浏览器 fixture。F3 → F4 → F6 的主因链成立，但推荐方案在锚点有效性、连续手势语义和验收度量上仍有三个会直接影响正确性的缺口。

> [!CAUTION] **RS-1 · 连续上滑场景不能直接用固定锚点的 `anchorTop` 判漂移**（§1.1、§8.1 RS02、§8.3）
> 证据：`tests/transcript-layout/transcript-layout.spec.ts:89-103` 只逐帧记录 `scrollTop` 和一个固定元素的 `anchorTop`；而 RS02 要求用户连续上滑。即使布局完全稳定，用户把 `scrollTop` 向上改动 `d`，同一元素的 `anchorTop` 也会自然向下改动 `d`，现有指标会把真实手势造成的位移计成漂移。当前写入拦截（`:32-70`）也只记 API 与时间，不记目标元素、写入前后值或来源，无法从 `scrollTop` 变化中分离用户滚动与 W6 校正。
> 建议：把自动验收拆成两类：分页触发后暂停输入、固定锚点验证稳定性的 RS01/RS03；以及持续手势下验证“布局残差”的 RS02。后者至少记录每帧 `anchorTop + scrollTop`（元素在滚动内容坐标中的位置）及程序写入的数值/来源，或由 fixture 注入可计量的用户滚动增量后断言 `ΔanchorTop = -ΔuserScroll`。在定义可分离手势与布局的公式前，不能用“全程 `anchorDrift ≤ 8px`”判 RS02。

> [!CAUTION] **RS-2 · 常驻 wrapper 不等于有效锚点：候选行可能在补页后变成 `display:none`**（§3.1 S5、§7.1 不变量 5）
> 证据：`LazyMessageRow.tsx:77-81` 把折叠成员的 wrapper 本身设为 `hidden`；`ChatMessagesPane.tsx:332-337,496,508-513` 会在窗口投影变化后把原行切换为折叠。这样的元素仍满足 `anchor.isConnected`，但已无可用布局框；当前还原仅检查 `isConnected`（`useChatSessionState.ts:626-633`），方案 A 若只把选择器从 `.chat-message` 改成 `[data-message-timestamp]`，仍可能对零尺寸锚点计算出错误的大幅补偿。摘要又是 wrapper 的兄弟节点（`ChatMessagesPane.tsx:498-508`），不能自然接替原行的身份。
> 建议：在 W6 契约中新增锚点资格与失效转移：捕获时排除 `[hidden]`、零尺寸和不在视口附近的 wrapper；每次校正前再次检查 `getClientRects().length > 0`。若原锚点被投影收起，必须用补页前同时记录的相邻“不会参与该组折叠”的后继可见行完成无跳交接，或用该后继行作为首选锚点。RS05 要增加“被选中的首个可见行恰好在翻转后被折叠”的用例，而不只测试其上方成组增删高度。

> [!WARNING] **RS-3 · “真实输入立即终止 W6”与异步分页期间持续滚动尚无闭环**（§1.2、§7.1 不变量 2、§8.1 RS02/RS07）
> 证据：`handleScroll` 在 `scrollTop < 100` 后等待异步 `fetchMore`（`useChatSessionState.ts:578-615`），用户可在等待期间继续产生 wheel/touch 输入。方案契约要求任一真实输入终止跟随；若终止后不重建，fetch commit 与后续 IO 扩张仍会在无原生锚定的平台上漂移；若按原捕获偏移重建，则会把等待期间用户有意产生的位移一起抵消。现有 `setIsUserScrolledUp` 会同步写 ref 并取消跟底 rAF（`:240-252`），但它只有“是否 detached”，没有“最近一次真实输入位置/序号”可供 W6 区分这两类位移。
> 建议：把 W6 定义为“布局增量补偿器”而不是“固定屏幕坐标锁”：每次真实输入先更新锚点基线/输入序号，W6 只补偿该基线之后由 DOM 几何变化产生的增量；或者明确分页等待与用户手势不重叠，收窄 RS02。无论采用哪种，都要在测试中覆盖 `fetchMore` 未决时连续 wheel、commit 前最后一次 wheel、commit 后首帧 wheel 三个交错点。

> [!IMPORTANT] **RS-4 · 方案 B 不能用裸 `timestamp` 作缓存键，应复用实际行身份并按会话命名空间隔离**（§6 方案 B、§12.7）
> 证据：`ChatMessage.timestamp` 只声明为 `string | number | Date`，没有唯一性契约（`src/shared/types.ts:317-322`）；现有测试已显式构造同 timestamp 的多条工具消息（`src/modules/chat/tests/toolGrouping.test.ts:19-34`）。`getIntrinsicMessageKey` 会优先使用 `id/messageId/toolId/...`，最后才回退到“类型 + timestamp + 工具名 + 内容前缀”（`messageKeys.ts:12-37`）；`ChatMessagesPane.tsx:244-260` 又从尾部做 occurrence 消歧，正是为了 prepend 后保住既有行 key。工具组 wrapper 的 timestamp 还只代表组内一条消息（`ChatMessagesPane.tsx:431-458`）。因此裸 timestamp 会串高，`timestamp + 内容指纹` 也会丢失已有 provider id 与工具组身份规则。
> 建议：把 `getMessageKey` 的最终行 key（工具组用其现有 fragment key 对应的行 key）显式传给 `LazyMessageRow`，缓存键至少为 `sessionId + rowKey`；不要另造 timestamp 身份体系。缓存只是误差优化，不作为正确性基础。若缓存需要跨 `visibleMessages` 重建，先用重复 intrinsic key + prepend 的单测固定 occurrence 规则，再决定是否需要更持久的 provider row id。

> [!WARNING] **RS-5 · 行高缓存还缺“几何 epoch”，仅按内容或 `showThinking` 失效会复用错误高度**（§6 方案 B、§10）
> 证据：行高不仅取决于消息内容；消息列宽由 `ChatMessagesPane.tsx:348` 的 `max-w`、横向 padding 和 viewport 决定，Markdown 换行会随宽度改变；用户手动展开工具/思考、图片或字体加载也会在 key 与内容不变时改变 `LazyMessageRow.tsx:57` 读到的高度。当前 `measuredHeight` 是组件局部 state（`:50`），组件重挂时自然丢弃，迁移到 transcript Map 后反而会跨宽度、偏好与 disclosure 状态保留陈旧值。
> 建议：缓存条目除稳定行键外至少绑定容器宽度/布局版本，并在 resize、字体就绪、影响高度的展示偏好和 disclosure 状态变化时失效或重测；会话切换时隔离或释放。首次访问与缓存失效仍必须由 A 保正确性，B 只降低校正量。补一个“测量后改变 viewport 宽度，再离开并返回该行”的用例。

> [!IMPORTANT] **RS-6 · 方案 A 必须规定首个校正发生在 paint 前，单写“ResizeObserver 触发 + rAF 跟随”不足以满足全程 8px**（§6 方案 A、§7.1 不变量 1）
> 证据：现有一次还原位于 `useLayoutEffect`，可在 commit 后首个 paint 前写 `scrollTop`（`useChatSessionState.ts:620-638`）；IO 再挂载真实内容由 effect 注册的观察器异步触发（`useLazyRowObserver.ts:33-52`、`LazyMessageRow.tsx:65-69`）。若 W6 只在观察到 resize 后“再申请一个 rAF”，浏览器可能已展示占位扩张后的中间帧；此后即使最终回到原位，也违反 §7.1 的全程阈值。反过来，在 `ResizeObserver` delivery 或同一次 pre-paint 阶段同步补偿，才有机会不暴露该帧。
> 建议：契约明确区分“首个 pre-paint 校正”和“后续稳定跟随”：W2 捕获后即武装 RO，RO delivery 中校正当次几何差，rAF 只负责跨帧稳定判定与超时；测试采样应从 commit 前一帧开始并断言任一已绘制帧的残差。若目标平台实测无法保证 pre-paint，则应诚实放宽“全程 ≤8px”，不能同时保留现有不变量和纯事后 rAF 实现。

> [!TIP] **RS-10 · 收敛波次：IO 初始通知按 observer 批量派发，单次分页的扩张是少数几波而非逐行**（§12.6，对 Claude R3 的修正）
